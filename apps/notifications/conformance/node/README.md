# Notifications protocol peers

These small Node clients exercise the PostgreSQL preference, append, terminal append, read-state, deletion, read-relation, and inbox-query contracts directly. The append client composes the existing preference check with the persistence-only append function on one function-only connection and in one transaction. The terminal-append client checks created-versus-existing results, immutable duplicate snapshots, rollback, and direct table denial using the same append capability LOGIN. Its target job UUID is opaque; the function reads no Jobs table. The read-state client checks current-user row scoping, no-op results, bulk counts, and rollback. The deletion client checks single-row scope, clear-read counts, invalid requests, rollback, and direct-delete denial on the same borrowed connection. The read-relation peer checks the public fact projection, owner-role/table isolation, and denied writes through the view. The inbox-query peer uses a separate function-only LOGIN and checks page/count results, exact bigint text, private helper/table denial, and denied writes. These are local interoperability checks, not a separate Notifications HTTP service.

Run `pnpm install --ignore-workspace --frozen-lockfile --ignore-scripts`, then `pnpm run check` for the schema self-checks. The owned database verifier supplies the corresponding connection and user IDs for the command peers, plus `NOTIFICATION_READ_RELATIONS_DATABASE_URL`, `NOTIFICATION_READ_RELATIONS_USER_ID`, and `NOTIFICATION_READ_RELATIONS_NOTIFICATION_ID` for the relation peer. It supplies `NOTIFICATION_INBOX_DATABASE_URL`, `NOTIFICATION_INBOX_USER_ID`, `NOTIFICATION_INBOX_NOTIFICATION_ID`, `NOTIFICATION_INBOX_PLATFORM_ROLE`, and `NOTIFICATION_INBOX_EXPECTED_ROLE` to `inbox_query_provider.mjs --live`. Command peers have only their fixed function grants; the read-relation peer uses the ordinary application role, which can select the facts view but cannot read the private table or write through the view.
