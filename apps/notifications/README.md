# Notifications owner capabilities

This package defines language-neutral Notifications contracts and bounded PostgreSQL capabilities. It does not start an HTTP service. API requests keep preference changes, notification inserts, read-state changes, deletions, and caller-owned changes in the same PostgreSQL transaction; the API remains the transaction coordinator.

The preference contract in `preferences.schema.json` covers reads, partial updates, and in-app mute checks. Migration `0311` installs `aap_notifications_v1.preference_command(jsonb)`. The policy JSON and owner SQL carry the same known types and toast defaults.

The append contract in `append.schema.json` carries a caller-generated notification UUID and returns the inserted row snapshot. Migration `0314` installs the persistence-only `aap_notifications_v1.append_notification(jsonb)` function. Callers must compose the existing preference-owner mute check before append; the append function does not apply product policy. It inserts with PostgreSQL's transaction timestamp, returns `read_at` and `created_at`, and never commits. The API rehydrates that snapshot into its existing SQLAlchemy identity map and preserves `notify`/`notify_many` return behavior.

The terminal append contract in `terminal_append.schema.json` covers `job.completed`, `job.failed`, and `job.cancelled` notifications. Migration `0321` installs `aap_notifications_v1.append_job_terminal_notification(jsonb)`, which serializes the `(user, type, async_job)` key with the same advisory-lock namespace as the frozen `0214` dataset-import helper, then returns whether this call created a row and the persisted snapshot. It performs no Jobs or Identity reads, has no 16 KiB payload cap, and never commits. The lock-and-read dedupe is supported at PostgreSQL `READ COMMITTED`; other transaction isolation levels receive a closed `unsupported_isolation` response before any write. The API keeps its existing terminal-kind/payload projection, mute preflight, and fast existence check; the native lock resolves races, and only the call that inserted a row publishes before the caller's commit. The API isolates this best-effort operation in a borrowed-connection savepoint without forcing a pending ORM flush.

The read-state contract in `read_state.schema.json` covers marking one notification or all current-user notifications read. Migration `0316` installs `aap_notifications_v1.read_state_command(jsonb)`. The caller supplies the API's UTC `read_at` value; the function scopes every update by `user_id`, changes only unread rows, and returns the affected IDs with the existing boolean/count result. Its SQLAlchemy binding respects `autoflush` and `no_autoflush`, uses the caller's transaction, and does not commit. The API reuses its pinned SQLAlchemy bulk-evaluate cache rules after the owner call, including dirty/expired identities and savepoint rollback bookkeeping. It compiles the legacy statement locally for cache synchronization and never sends another UPDATE or SELECT. Rebaseline this compatibility shim when upgrading SQLAlchemy.

The deletion contract in `delete.schema.json` covers one notification and all read notifications for the current user. Migration `0318` installs `aap_notifications_v1.delete_command(jsonb)`, which returns the existing boolean/count result without returning a potentially large ID list. Both commands use the caller's transaction, respect `autoflush` and `no_autoflush`, and never commit. The API preserves SQLAlchemy's identity-map delete synchronization, the single-delete 404 behavior, and commit-before-sync publication.

The read-relation contract in `read_relations.schema.json` publishes the fixed `aap_notifications_v1.notification_facts` projection. Migration `0319` owns the security-barrier view and selects only the eight fields required by API response mapping, filtering, ordering, and delivery checks. The view itself does not decide notification visibility.

The REST inbox contract in `inbox_query.schema.json` moves `list_for_user` and `unread_count` filtering, ordering, pagination, and counts behind the Notifications owner. Migration `0324` installs `inbox_page`, `inbox_total_count`, and `inbox_unread_count`; they share the private `_visible_inbox_rows` policy and return native rows/counts through the API's existing transaction. API supplies the authenticated actor ID and role from its immediately preceding Identity status snapshot. Project authorization composes the existing Workspace membership and project-search capabilities, Identity account facts, and Jobs notification-scope fact. The policy keeps the current super-admin, manager-owner, valid-membership/reviewer, actual-job-scope, and fail-closed unknown-job rules. It adds no endpoint-wide inactive-account rejection; membership authority still requires an active Identity profile. Only `audit_archive` and `dataset_import` remain global async-job kinds. The SQL preserves inbox JSONB `payload ->> 'project_id'` semantics; batched delivery keeps its distinct Python dict-only policy. The adapter maps rows with SQLAlchemy `from_statement`, preserving identity-map, dirty/expired state, caller autoflush mode, and caller commit/rollback; counts remain Python integers at the existing HTTP boundary. JSONB payloads stay native, including arrays and scalars. By-id, terminal precheck, delivery and WebSocket persisted-row consumers use the separate delivery-read capabilities below; API credentials have no direct fact-view access.

The delivery-read contract in `delivery_read.schema.json` moves notification-by-ID, terminal-notification existence, and delivery-scope facts behind seven fixed capabilities. Migration `0325` installs `read_notification`, `find_terminal_notification`, `delivery_job_scopes`, and separate member, reviewer, owner, and super-admin pair reads. The pure Notifications policy retains the API's Python dict-only payload parsing, actual Jobs scope precedence, unknown-job fail-closed behavior, ordered independent authorization snapshots, and best-effort unrestricted fallback. Calls borrow the API transaction and use existing Identity, Workspace, and Jobs public facts; they read no foreign private tables. The API remains responsible for its existing authentication, ORM identity-map and autoflush behavior, publication/error handling, and WebSocket lifecycle. This slice does not move Redis transport or WebSocket ownership.

The durable delivery contract in `notification_delivery_protocol.schema.json` defines the existing `aap-notifications-delivery/v1` policy, claim, and finish messages. Its PostgreSQL client calls only `identity_delivery_policy()`, `claim_identity_deliveries(jsonb)`, and `finish_identity_delivery(jsonb)`; the Redis publisher commits each claim before publishing and acknowledges the lease only after Redis accepts the message. Cancellation or a finish failure leaves the lease to expire and be reclaimed, so delivery remains at-least-once with the stable notification ID. Install `aap-notifications[runtime]` and run `aap-notifications-publisher` or `python -m aap_notifications.delivery_worker`; configure only the existing `NOTIFICATION_PUBLISH_DATABASE_URL(_FILE)` and `NOTIFICATION_PUBLISH_REDIS_URL(_FILE)` sources. No HTTP server or new runtime selectors are introduced.

`redis_pubsub.py` owns only the existing immediate API transport: it publishes standard `json.dumps` output to `notify:<user_id>` using one Redis URL client per message and closes it in `finally`. API authorization, commit timing, logging, and propagated-error policy remain with the caller. This raw transport stays separate from the durable publisher's compact UTF-8 encoding and lease protocol.

The `realtime_event.schema.json` contract defines the existing persisted-notification event and `notifications.sync` control message on that channel. It keeps business notification types open, event payloads as any native JSONB value, and sync reasons and extension fields optional/open. API and durable publishers share the event field contract while retaining their existing timestamp construction and JSON encoder settings; the API remains responsible for publication timing and each caller's best-effort or retry behavior. The Notifications owner now checks WebSocket credentials, current account activity, and each persisted notification before relay; the API keeps its compatibility route and gateway.

The optional `websocket` extra and `aap-notifications-socket` entry point run a separate Starlette WebSocket owner on port 8180, bound to `127.0.0.1` by default. Its `/ws/notifications` route reauthenticates each frame through Identity admission, checks the current active-account fact at handshake, and keeps the existing `notify:<user_id>` Redis channel, 30-second ping, raw event forwarding, and per-message authorization. Missing notification rows receive four reads with three 150 ms waits; a found row is reused for the second authorization check. The native adapter opens one read-only `READ COMMITTED` transaction per gated message, calls only fixed Notifications read functions, uses native JSONB values, and rolls the transaction back after the check. Startup verifies the LOGIN against all seven existing read capabilities. The socket has no publisher or business-write credentials.

The socket runtime requires exactly one of `NOTIFICATION_SOCKET_DATABASE_URL` or `NOTIFICATION_SOCKET_DATABASE_URL_FILE`, exactly one of `NOTIFICATION_SOCKET_REDIS_URL` or `NOTIFICATION_SOCKET_REDIS_URL_FILE`, and exactly one of `NOTIFICATION_SOCKET_IDENTITY_TOKEN` or `NOTIFICATION_SOCKET_IDENTITY_TOKEN_FILE`, plus `NOTIFICATION_SOCKET_IDENTITY_URL`. Secret files are bounded and their validation failures are redacted. `NOTIFICATION_SOCKET_HOST` and `NOTIFICATION_SOCKET_PORT` set the listener address; no host port is published by this package. Liveness is available at `/health/live`; `/health/ready` checks PostgreSQL and Redis without a business write.

`conformance/node/realtime_event_provider.mjs --stdio` validates one JSON event or sync sample from stdin and echoes the original bytes to stdout. It has no Redis connection and preserves timestamp strings and sync extensions for a separate transport test.

`Dockerfile` builds a non-editable runtime from this package's locked `runtime` extra and runs the same publisher entry point as a non-root user. It exposes no ports; provide the existing `NOTIFICATION_PUBLISH_*` settings through the runtime environment or secret files. The Identity image retains its old module and CLI as compatibility entry points.

`Dockerfile.socket` independently installs the locked `websocket` extra and runs
the socket entry point as the same non-root user. The optional
`docker-compose.notifications.yml` joins the selected Compose private network
without a host port. See the repository `DEV.md` for the API compatibility binding,
admission-only Identity bearer and function-only PostgreSQL / subscribe-only Redis
credentials. Run package checks with
`uv run --project apps/notifications --locked --extra websocket --extra test python -m pytest`.

`infra/docker/module-data-grants.sql` gives `notifications_code` the narrow notification write privileges needed by its owner functions. The preference grant script gives the existing API LOGIN and a function-only peer access to `preference_command(jsonb)`, then revokes direct preference-table access. The append grant script grants the API LOGIN and `notification_append_client` the append, read-state, and deletion functions; the peer also gets `preference_command(jsonb)` to compose policy and writes in one transaction. It revokes direct notification INSERT, UPDATE, and DELETE from the API LOGIN while retaining reads. Apply the strict grants only after the API and worker artifacts use the owner paths and old processes are drained.

The bounded acceptance covers package contracts, Node peers over borrowed transactions, and focused API transaction tests. `scripts/verify_module_data_boundary.py` exercises the function-only roles, read-relation access, and API grants against owned disposable PostgreSQL resources. The view contract does not move Jobs scope or project authorization into Notifications.

`conformance/node/inbox_query_provider.mjs --self-check` verifies the portable inbox schema, fixed SQL copies, role-snapshot boundary, and function-only surface without opening a database connection. Its `--live` mode expects `NOTIFICATION_INBOX_DATABASE_URL`, `NOTIFICATION_INBOX_USER_ID`, `NOTIFICATION_INBOX_NOTIFICATION_ID`, `NOTIFICATION_INBOX_PLATFORM_ROLE`, and `NOTIFICATION_INBOX_EXPECTED_ROLE` from an owned disposable fixture; it verifies the function-only login and the existing read-relation probe. The new API binding preserves the existing status→page→total→unread statement order; the HTTP routes and response model are unchanged.
