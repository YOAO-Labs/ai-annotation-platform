# Notifications owner capabilities

This package defines language-neutral Notifications contracts and bounded PostgreSQL capabilities. It does not start an HTTP service. API requests keep preference changes, notification inserts, read-state changes, and caller-owned changes in the same PostgreSQL transaction; the API remains the transaction coordinator.

The preference contract in `preferences.schema.json` covers reads, partial updates, and in-app mute checks. Migration `0311` installs `aap_notifications_v1.preference_command(jsonb)`. The policy JSON and owner SQL carry the same known types and toast defaults.

The append contract in `append.schema.json` carries a caller-generated notification UUID and returns the inserted row snapshot. Migration `0314` installs the persistence-only `aap_notifications_v1.append_notification(jsonb)` function. Callers must compose the existing preference-owner mute check before append; the append function does not apply product policy. It inserts with PostgreSQL's transaction timestamp, returns `read_at` and `created_at`, and never commits. The API rehydrates that snapshot into its existing SQLAlchemy identity map and preserves `notify`/`notify_many` return behavior.

The read-state contract in `read_state.schema.json` covers marking one notification or all current-user notifications read. Migration `0316` installs `aap_notifications_v1.read_state_command(jsonb)`. The caller supplies the API's UTC `read_at` value; the function scopes every update by `user_id`, changes only unread rows, and returns the affected IDs with the existing boolean/count result. Its SQLAlchemy binding respects `autoflush` and `no_autoflush`, uses the caller's transaction, and does not commit. The API reuses its pinned SQLAlchemy bulk-evaluate cache rules after the owner call, including dirty/expired identities and savepoint rollback bookkeeping. It compiles the legacy statement locally for cache synchronization and never sends another UPDATE or SELECT. Rebaseline this compatibility shim when upgrading SQLAlchemy.

`infra/docker/module-data-grants.sql` gives `notifications_code` only the `read_at` update column in addition to its existing notification privileges. The preference grant script gives the existing API LOGIN and a function-only peer access to `preference_command(jsonb)`, then revokes direct preference-table access. The append grant script grants the API LOGIN `append_notification(jsonb)` and `read_state_command(jsonb)`; the function-only `notification_append_client` gets those functions plus `preference_command(jsonb)` to compose policy in one transaction. It revokes direct notification INSERT and UPDATE from the API LOGIN while retaining reads and the separate delete endpoints. Apply the strict grants only after the API and worker artifacts use the owner paths and old processes are drained; old API images that directly insert or update notification rows will fail after the grants are applied.

The bounded acceptance covers package contracts, a Node peer that composes the commands over one borrowed transaction, and focused API transaction tests. `scripts/verify_module_data_boundary.py` exercises the function-only roles and API grants against owned disposable PostgreSQL resources. This capability closes the ordinary append and read-state write paths only; it does not qualify notification list visibility, dismissal, delivery, WebSocket authorization, or outbox deployment.
