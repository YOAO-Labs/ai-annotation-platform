# Runbook：员工项目角色迁移与回滚 {#runbook-员工项目角色迁移与回滚}

本手册执行「平台身份与项目职责分离」的**一次协调切换**（见 [ADR-0075](/dev/adr/0075-platform-identity-vs-project-authority)）：把账号级 `annotator` / `reviewer` 合并为平台 `employee`，授权改由项目成员角色决定，并在同一次切换中部署匹配的 API、worker 与前端。

增量边界：**Increment A（加性准备 + 贡献者证据记录）是可独立兼容部署的准备层**——它只增加向前 / 向后兼容的加性字段（可空列，或带默认值的非空列，如 `project_members.version`）并记录新工作的证据，不改变现有授权，旧二进制仍可运行；如果该功能最终不上线，平台保持可用。**完整的 Increment B 才是单次协调切换**，其内部工作包（B1…）是开发 / 评审包，**不是**可分别部署的阶段；不要只升级数据库或只升级某一层。

::: warning 数据安全
`0174` 只转换 `users.role`（全局 `annotator` / `reviewer` → `employee`）并回填**待处理**邀请的项目角色；它**不改写成员关系行或成员角色**。成员关系歧义只能来自单独批准的**行级修复清单**，本手册不做自动猜测或补建。下面的演练与切换命令会改写账号与邀请数据，只对**隔离的演练库**（从受保护的许可快照恢复）或明确批准的目标库执行；不要在普通开发库或未备份的生产库上直接跑。迁移前后保留可恢复的备份与迁移前快照。
:::

## 何时使用 {#何时使用}

- 准备把员工身份与项目角色模型上线到目标环境。
- 切换后出现角色不一致、预览 409、权限拒绝激增或 worker 用旧权限继续写。
- 需要判断能否回滚、回滚到哪一边界。

## 前置条件 {#前置条件}

- 已确认目标环境可停写维护窗口；API、worker、前端可同版本切换。
- 已通过评审的**行级修复清单**（若有角色 / 成员关系歧义）；本手册不做自动猜测或补建成员关系。
- 已确认遗留审阅证据的处置范围，并约定受影响审核任务的恢复方式；**平台不附带自动贡献者回填工具**。
- Worker 源码是挂载还是镜像内已判定；挂载 Python 代码需要真实刷新 worker，依赖 / 源码烘焙需要重建。
- 授权证据只有在**所有** API / worker 写入生产者都已部署（旧写入经过排空边界）后才可信；混合新旧写入者无法建立完整来源。

## 1. 只读审计（迁移前） {#1-只读审计迁移前}

审计在 `0173` 存在**之前**也可运行，缺失的加性列按 `NULL` / “未知”报告，不会虚构完整性。

```bash
cd apps/api
uv run python scripts/audit_project_roles.py --pretty
# 或落盘版本化 JSON 报告（含 run_id / baseline / 计数与必要 ID，绝不含哈希、token 或签名 URL）
uv run python scripts/audit_project_roles.py --output /tmp/role-audit-before.json
```

退出码 `0` 表示审计完成（发现项本身不失败）；`2` 表示连接或 schema 错误，先修复再继续。报告应覆盖：

- 全局 / 成员角色不一致、未知 / 空角色、非法管理 owner、管理员成员关系。
- 无有效成员身份的生效任务 / 继承批次指派；停用账号仍有未完成工作。启用的超级管理员和具有合法管理身份的本项目负责人可以经管理通道代标 / 代审，不需要为消除审计报告而补建成员关系；其他项目管理员、非管理身份的 owner 和停用账号不能套用该例外。
- 合法的跨项目混合角色与真正的不一致**分开**列出。
- 待处理邀请按“仅账号 / 项目目标”、角色、过期与目标已删除分类。
- 完整 / 不完整 / 缺失的审阅轮次贡献者证据。

## 2. 演练（隔离库） {#2-演练隔离库}

1. 从许可、受保护的快照恢复一个一次性隔离库。
2. 校验完整 Alembic 图与数据库 revision；不要臆造迁移号或对不兼容数据库降级。
3. 在演练库按顺序应用加性准备与转换，运行审计并按批准清单逐项对账（**没有自动的贡献者证据回填工具**，证据修复见下文）。检查成员过滤后的仪表盘 / 候选查询的计划，避免把整个项目历史装入单个交接事务。
4. 用两个项目负责人 MA/MB 与员工 U/V（U 为 A-annotator/B-reviewer，V 相反）加一个不可访问项目 C，验证 A/B/C 三个方向的可见与写入，以及邀请接受、角色变更、自审拒绝与结果交付。

没有现成快照时，可以在维护者明确许可后，对**仍处于转换前版本**的 dev 数据库做只读一致性备份；不要为取得快照而迁移 dev。备份放在 Git 之外的受限目录（目录 `0700`、文件 `0600`），记录来源 revision、时间和 SHA-256。dev 快照仅用于演练，不能替代实际切换目标在停写窗口内的新备份。

恢复验收不能只看命令退出成功：转换后再恢复原快照，比对原始角色、逐表数据、序列、物化视图内容及 schema，并验证拒绝 downgrade 后没有数据变化。PostgreSQL 恢复可能把 CHECK 中的数组类型转换改写为语义等价的逐元素转换；应核实具体差异，不能因此跳过约束校验。若复用已有的归属明确的隔离库，先备份其原状态，演练结束后恢复并复核；不终止未知连接、不操作共享测试库或对象存储。审计中的缺失成员关系和未知审核证据应保留并单独决策，备份许可不等于数据修复许可。

## 3. 冻结与备份 {#3-冻结与备份}

1. 冻结应用写入、成员 / 邀请变更与受影响的队列消费者；排空在途写入。
2. 保留一份经测试、可恢复的备份与**迁移前快照**（受保护、受限访问）。快照包含源角色值，是受限回滚的唯一依据。

## 4. 转换与部署 {#4-转换与部署}

1. 应用最终 schema / 数据转换（`0173` → `0174`）：只把全局 `annotator` / `reviewer` 转为 `employee`（含停用账号，但不重新激活），保留 ID、成员角色与历史；管理员 / 观察者身份不变；待处理项目邀请先回填项目角色再规范平台角色。
2. 部署**匹配的** API / worker / 前端产物。阻止所有旧 API 与旧 worker 二进制继续写入员工数据库。
3. 按实际挂载方式刷新受影响 worker；依赖 / 源码烘焙变更需重建。

## 5. 复核与重开 {#5-复核与重开}

1. 对目标库再跑一次审计并对比迁移前报告，确认账号、成员关系、待处理邀请、指派与历史绩效按批准的转换对账。
2. 跑验收矩阵：A-annotate/B-review/C-denied、邀请接受、角色变更（预检 → CAS 写入）、自审拒绝、导出拒绝标注员 / 观察者、结果交付。
3. 业务事实对账通过后再重开写入与消费者。
4. 观察权限拒绝、角色不一致、预览版本 / 快照冲突、死锁 / 资源占用与已撤销的 worker 写入；日志用请求 / 实体 ID，不要用无界项目 ID 作为指标标签。

## 回滚 {#回滚}

::: danger 0174 的 downgrade 在任何窗口都拒绝
`0174` 不提供 schema downgrade：其 downgrade 实现**始终抛错**，即使在重开写入之前的冻结窗口内也一样。不能用“旧二进制 + 自动降级”回退到全局角色模型。
:::

- **重开写入之前**：唯一的前置恢复是**恢复精确的迁移前快照**并回退到旧二进制；恢复后旧模型与旧数据一致可用。这是业务数据回滚，不是自动 downgrade。
- **重开写入之后**：跨项目职责或员工邀请一旦写入，旧全局角色模型无法无损表达，只能二选一——回退到**支持新 schema / 模型的新二进制**向前修复（推荐），或把旧的数据库备份恢复视为一次显式业务数据回滚（会丢失快照之后的业务写入，需业务确认）。
- 允许旧二进制在加性 `0173` 之后运行，但它们不再维护加性列。若在回滚后重开写入，必须归档已收集的授权证据，并把受影响的可变任务标记为“完整性未知”；重新启用前审计该区间，**不能**信任早前记录部署遗留的数组。

完整回滚边界与部署顺序见 [完整计划](/dev/adr/0075-platform-identity-vs-project-authority) 的 Notes 与仓库 `docs/plans/1789807315_project-scoped-employee-roles.md`。

## 遗留审阅证据 {#遗留审阅证据}

任务的贡献者证据有三种状态，不能互相替代：

- **已知为空**：`annotation_contributor_ids = []` 表示尚无已记录的贡献者；它本身不能证明审核轮次完整。
- **未知**：列为 `NULL`（旧二进制或迁移前创建）、结构畸形，或审核轮次缺少有效的 `review_round_id` + `review_submitter_id` + 完整集合，都视为未知。
- **完整**：当前审核轮次有有效的冻结集合与提交者。

未知证据阻断对应审核写入（`409 review_contributors_unknown`），不按全局角色回退，也不把未知当空。**平台不附带自动的贡献者回填命令**：只能从保留且可信的提交与变更历史，经维护者单独批准的数据修复重建，或用单独归属的新任务替换；仅有“活跃作者快照”不足以证明没有其他编辑者。保留原任务与审计历史，并在上线准备中识别由此产生的不可用任务、约定恢复方式。

若日志起始时间晚于任务的历史提交，或活动记录标为未验证采集，就不能据此宣称贡献者集合完整。已完成任务保留其原有状态、绩效与未知证据，不补造审核轮次；仍待审核的旧任务需选择可信历史重建或新建重标任务。替代任务必须由已启用证据记录的新版本创建并实际标注、提交，不能复制旧证据或仅重新提交旧任务（未知状态不会因此变为完整）；替代也不改变原任务的历史证据结论。

## 已签发 URL 的边界 {#已签发-url-的边界}

撤销成员 / 角色后，新写入立即失败，但**已签发的直接存储 URL 在到期前仍可用**，当前默认值保持不变：

- 下载链接：1 小时有效期，实际到期向下一个 10 分钟缓存窗口边界对齐。
- 评论附件：5 分钟，无对齐。
- 导出：7 天（调用方另受同样的 10 分钟对齐约束）。

撤销后的新 URL 不再签发；立即失效旧 URL 需要单独的存储 / 代理改造，不在本次角色迁移范围内。
