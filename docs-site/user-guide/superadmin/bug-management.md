# BUG 反馈管理

面向超级管理员与项目管理员的问题反馈追踪与工单治理指南。汇总用户在标注工作台及各业务页面上报的缺陷反馈、控制台错误日志与现场截图。

工作台顶栏及其他页面右下角的反馈入口收集到的反馈会持久化在系统中。`super_admin` 和 `project_admin` 均可查阅工单列表并按状态与严重度进行筛选（详见 [筛选操作说明](/user-guide/reference/filtering)）。侧边栏 **管理 → BUG 反馈**（`/bugs`）入口仅对 `super_admin` 开放。

> 非管理员用户提交反馈后只能在「设置 → 我的反馈」里查看自己提交的工单。

提交者可编辑自身工单的标题、描述与严重程度；处理状态、分派、重复关系和处理结果由管理员维护。标题、描述和严重程度不能清空为 null。提交者需要重开已关闭工单时，通过发表评论触发下述重开流程。

## 截图附件约束

用户提交反馈时最多可上传 **5 个**附件，每个文件限制如下：

- 最大文件大小：**10 MiB**
- 支持格式：**PNG / JPEG / WebP**（服务端同时核验实际图片格式与像素数，最多 4,000 万像素）

## 列表与筛选

![BUG 反馈列表](../images/superadmin/bugs/list.png)

进入后默认展示最近 50 条工单，支持按 **状态 + 严重度** 两个维度过滤：

这两个条件保存在地址中，刷新及浏览器前进后退可恢复。快速切换筛选时以最新条件的结果为准；切换账号会退出旧工单详情，迟到的详情或评论结果不会覆盖新账号页面。

| 状态                 | 含义             |
| -------------------- | ---------------- |
| `new` 新提交         | 未经分诊         |
| `triaged` 已确认     | 已被认领，需排期 |
| `in_progress` 处理中 | 已在修复         |
| `fixed` 已修复       | 修复已上线       |
| `wont_fix` 不修复    | 复现失败或非缺陷 |
| `duplicate` 重复     | 关联到已存在工单 |

| 严重度     | 触发场景               |
| ---------- | ---------------------- |
| `low`      | 文案、对齐、不影响流程 |
| `medium`   | 单点功能问题           |
| `high`     | 工作流被阻断           |
| `critical` | 数据丢失或安全风险     |

列表每行展示 `display_id`（B-1、B-2 …）、标题、严重度徽标、状态、提交时间。如果该工单被重开过，状态后会显示 `↻N` 徽标，鼠标悬停可看最近一次重开时间。

支持以 Markdown 格式导出当前筛选结果：`GET /api/v1/bug_reports?format=markdown&status=new`。

## 编写描述与评论

提交、修改反馈和发表评论时，可以直接使用工具栏排版，也可以切换到 Markdown 源码或预览。描述和评论采用紧凑编辑器，支持列表、链接、表格和代码块；评论可用 **Ctrl / Cmd + Enter** 发送，在表格单元格内刚完成的修改也会一并提交。

描述最多 20,000 个字符，评论最多 10,000 个字符；描述限额包含系统追加的诊断内容。超过限制或提交失败时，正文会保留，修改后可再次提交。

在新反馈中粘贴截图，会加入独立的截图附件列表。每份反馈最多五张截图，支持 PNG、JPEG 和 WebP，单张不超过 10 MiB。正文和截图随同一次提交保存。

截图上传失败会保留草稿，可重试上传或跳过截图提交；已成功上传的截图在当前表单内重试时无需重复上传。上传期间关闭反馈或切换账号后，旧操作不会继续发送创建请求。已发送提交的迟到结果不会清空重新打开的表单，也不会在新账号界面显示提交结果。

## 详情面板

![BUG 反馈详情面板](../images/superadmin/bugs/detail-panel.png)

点击行打开详情面板，自上而下包含：

1. **元信息**：用户提交时所在路由（`route`）、提交者角色、视口尺寸（`viewport`）、重开次数。
2. **描述正文**：按标题、列表、表格、代码和图片展示用户填写的 Markdown。
3. **截图附件**：附件以下载按钮列出，文件大小标注在右侧。点击后使用当前登录身份获取已核验的图片并下载，按钮会显示下载进度；失败原因显示在该附件下方，可再次点击重试。关闭详情、切换工单或账号后，旧下载结果不会触发保存。附件保留 180 天，到期后仍可查看反馈记录，但不能继续下载原文件。历史未登记的附件需要重新上传，请联系管理员核对；系统不会从当前存储位置猜测文件。
4. **处理结果（resolution）**：若已填写，显示在状态按钮上方。
5. **状态切换按钮**：6 个状态按钮并排，点击直接落库并广播 `bug_report.status_changed` 通知给提交者。当前状态高亮显示，不可重复点击。
6. **评论区**：内联 markdown 评论，所有评论者的 `author_role` 会跟在名字后；评论会作为 `bug_report.commented` 通知发给提交者。

![BUG 工单状态切换：6 个状态按钮并排，当前状态高亮](../images/superadmin/bugs/status-transitions.png)

## 重开机制

工单重开由**提交者（reporter）在评论区发评论**触发，而非管理员手动改状态：

- 触发条件：提交者在 `fixed` / `wont_fix` / `duplicate` 状态的工单上发表评论
- 触发后：工单自动转为 `triaged` 状态，`reopen_count` +1，`last_reopened_at` 更新为当前时间
- 速率限制：每个用户对同一工单每日最多触发 **5 次**重开（超限返回 429）；整体评论限制 **60 次/小时**
- 审计：重开事件记录 `bug_report.reopened` 审计日志

管理员直接通过「状态切换按钮」修改状态**不会**触发重开逻辑（直接写库，不计入 reopen_count）。

## 通知触达

详细规约见 [开发文档 · 审计与通知](../../dev/concepts/audit-and-notifications)。BUG 工单相关的 in-app 通知 type：

- `bug_report.commented` — 工单被评论
- `bug_report.status_changed` — 状态被改动
- `bug_report.reopened` — 已关闭工单被提交者重开

用户可在 **设置 → 通知偏好** 中单独静音以上 type。

## 反馈循环

- 用户在「设置 → 我的反馈」中可看到自己提交的所有工单及其当前状态、resolution、最新评论。
- 触发 `bug_report.reopened` 后，超管侧详情面板中元信息行会显示 `曾重开 N 次` 徽标，便于识别高频回归。

## 后端 API

详见 [API 文档](../../api/) 的 `/api/v1/bug_reports/*` 端点；服务实现位于 `apps/api/app/services/bug_report.py`。

::: tip 提交者排查路径
当用户报告问题时，可让其点击工作台顶栏或其他页面右下角的反馈按钮提交：系统会**自动附带**最近 10 条 API 调用日志与 console error 日志，大幅减少复现成本。无需手工抓 HAR / DevTools。
:::
