# 实例分割在线学习验收

本页将项目人工回流、训练故障恢复、推理 Backend 生命周期和 GPU 仲裁分别验收。每项记录自己的通过证据；小样本训练成功不能代替目标部署资格。

## 准备当前开发环境

确认浏览器、API、Worker 和训练执行器属于同一开发环境，再运行夹具：

```bash
cd apps/api
PYTHONPATH=. uv run python scripts/seed.py --profile online-training
```

夹具在「COCO8 在线训练（dev）」中准备 8 张已审核图片、30 个检测框和 30 个原图实例 RLE。分割来源为官方 COCO8-seg 多边形，经 COCO 栅格化保存；两个素材包的原图逐字节一致。检测、分割各有独立初始版本，均保留官方 4/4 划分。旧夹具增补前会检查原任务未被人工修改，已有分割重跑不会恢复人工删改的掩膜。

默认开发账号为 `pm` / `qa` / `anno`，密码 `123456`；已有账号不会被重置。夹具不创建实验、不启用策略、不发布模型。离线和缓存选项见 [DEV.md](https://github.com/yyq19990828/ai-annotation-platform/blob/main/DEV.md#coco8-在线训练夹具)。

## 人工验收第一轮

1. 用 `pm` 登录，打开项目「训练数据」，将「数据集任务」设为「图片实例分割」。打开「COCO8 实例分割初始数据（原生 RLE · 4 train / 4 val）」。应为已就绪、8 张图片、80 类、30 个实例，训练与验证各 4 张。
2. 在「冻结样本」预览训练、验证各一张，确认原图和实例掩膜均可读取，掩膜与目标对齐。查看不同实例以及背景；仅有检测框不算通过。下载训练包应包含 `manifest.json` 和逐图实例 RLE JSON。
3. 点击「使用此版本新建实验」。选择 Ultralytics、`yolo11n-seg`，保留全部 80 类及原顺序。建议 `epochs=3`、`batch=1`、`imgsz=640`、`seed=42`。本夹具在该输入分辨率及验证器 160 × 160 平面均没有实例完全消失。更低输入分辨率应重新检查 tiny 目标，不能忽略阻断后继续。
4. 启动执行，观察尝试记录、训练日志、分割 loss 和验证指标，最终状态为成功。下载 Best 权重及指标，核对任务为分割、数据版本和执行尝试准确。记录 run ID、attempt ID、镜像身份和 Best SHA-256。
5. 到「模型与发布」切换分割，添加本次成功实验的候选，核对区域类别绑定，在指定 YOLO 实例「加载并试用」。应展示冻结验证原图和原尺寸实例掩膜；只有图片和掩膜实际加载成功后才确认发布。
6. 发布后新建分割预标注，检查候选来自刚发布的模型和代次。接纳一个候选后，应形成区域工具的实例掩膜，可用画笔修正并保存。再检查检测任务的原发布记录，检测与分割应各自保留代次。

COCO8 是流程夹具，指标不适合评判泛化质量。逐样本比较应固定同一验证版本、类别、阈值和推理协议；TP／FP／FN 与匹配实例 Dice 一起查看，Dice 不能替代漏检统计或 COCO AP。

扩展模型验收时，在新建实验中依次选任务、框架、家族和规格；每个组合单独记录结果。需要训练集 Precision／Recall／mAP 时开启「评估训练集」，并核对训练表现与验证表现分别来自各自分区。模型初始化还应分别检查预训练、从头训练和同身份候选初始化。YOLO26 分割另核对 L1／语义分割损失及其预算限制；低分辨率、batch 1 的成功不能证明 640 分辨率或更大 batch 的容量。

## 人工修正回流第二轮

选择原始训练图片 `000000000009.jpg`，或另一张明确属于训练分区的图片。用原标注员 `anno` 登录工作台，已完成的任务先点击「继续编辑」，再修改一个实例的实际像素、保存并提交，由 `qa` 审核通过。仅打开、原样保存或编辑版本号变化不算有效数据增长。

1. `pm` 准备新分割数据版本，以第一轮分割版本为父版本，继承原分区。检查预检和版本比较，应只有预期的训练标注发生变化，验证图片保持原分区。
2. 冻结后预览新旧掩膜，确认修改进入新版本，旧版本的原图和 RLE 没有变化。
3. 新实验选择第一轮已核验、同规格同类别顺序的分割候选作为初始化来源。冻结配置应记录该候选及权重摘要。训练成功后添加第二个候选，继续由负责人比较、试用和决定发布；训练成功不自动替换当前模型。
4. 验收自动训练时，切换「自动训练」中的分割任务，选择同任务基线，设置变化门槛 `1`、间隔 `1` 分钟、冷却 `0`，明确保存并启用。再做一次训练分区实际像素修改和审核，使用「立即检查与同步」或等待 beat，观察只创建一次新候选。验收结束关闭策略。
5. 仅修改验证分区不应触发训练；重复检查不应重复创建实验。已有构建、运行或失联尝试时，另一个任务应等待，不能争用执行器。

本夹具 8 张图均已审核，且属于历史训练数据，没有主动学习所需的未标注池。验收主动选样需另外导入真实未标注图片，再比较同预算随机对照、接纳为人工批次；复制同一图片内容不能绕过历史排除。

## 训练 GPU 故障与恢复

在目标部署使用专用验收项目和专用执行器，固定物理 GPU UUID、镜像 digest、配置身份和持久 `/state`。故障注入只能作用于该执行器、该 attempt 或其专用代理，保留 GPU 文件锁和原状态目录。先做正常停止与恢复，再做进程和网络故障。

| 场景                 | 操作                                                                                        | 通过条件                                                                     |
| -------------------- | ------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| 正常停止再续训       | 用足够长的分割实验，等待 `0 < checkpoint_epoch < epochs` 后点击停止，确认旧进程退出再点续训 | 同 run、新 attempt；检查点摘要和归属匹配，`start_epoch` 延续，优化器状态恢复 |
| 执行器进程被杀       | 在中间检查点持久化后，只对专用执行器发 SIGKILL，再使用同 `/state` 重启                      | 旧尝试、租约和进程状态可核对；旧 GPU 锁释放后才允许新尝试；不重复领取        |
| 心跳或 API 网络中断  | 用专用代理阻断该执行器到 API 的流量，再恢复                                                 | 显示失联但不推断已停止；未确认旧进程停止时拒绝续训；恢复后没有并行重复执行   |
| 检查点或结果上传中断 | 只阻断该验收任务的对象上传链路，再恢复                                                      | 上传重试不重复登记产物；摘要一致后才可恢复或成功回传                         |
| 损坏或身份不兼容     | 对验收副本改变检查点内容或执行器兼容身份，再请求恢复                                        | 明确拒绝；不回退随机初始化或另一实验的检查点                                 |
| 尚无可续中间检查点   | 首轮尚未完成，或已达到目标轮数时请求恢复                                                    | 不可续原因明确，不伪造可续状态                                               |
| 候选初始化后再续训   | 先从同规格候选初始化，形成中间检查点后停止恢复                                              | 恢复本 run 的完整检查点，不重新从初始化候选开始                              |

恢复状态读取 `GET /api/v1/projects/{project_id}/training-runs/{run_id}/recovery`；续训使用同 run 的 `POST .../{run_id}/resume`，无请求体。`eligible=true` 可以同时伴随执行器离线，表示允许排队，不表示已经领取。失联不等于旧进程已停止，不能通过删除 lease、锁文件或状态目录强行恢复。

每项保存 run／旧新 attempt、检查点 epoch／SHA、旧进程退出与租约释放时间、新 `start_epoch`、最终产物摘要，以及 GPU UUID、驱动、CUDA／Torch／Ultralytics 和镜像身份。当前开发栈上的普通正常训练结果不覆盖这张故障表；CPU 资格工具也不构成 GPU 故障验收。

## 受控分割模型生命周期

使用包含最新脚本的目标 YOLO 镜像，在目标 UUID 的独占 GPU 上运行 `apps/yolo-backend/scripts/validate_managed_lifecycle.py`。先准备已核验的真实训练权重、代表性原图及严格 JSON 夹具。以下以 `yolo26n-seg` 为例；三个家族的 15 个分割组合应按实际部署范围分别验收：

```json
{
  "schema": 3,
  "task": "segment",
  "base_model": "yolo26n-seg",
  "framework_version": "8.4.183",
  "frozen_model_ref": {
    "model_version_id": "00000000-0000-0000-0000-000000000001",
    "sha256": "<实际权重的64位SHA-256>",
    "classes_digest": "<按顺序类别JSON的规范摘要>"
  },
  "classes": ["person"],
  "confidence": 0.01,
  "max_det": 20,
  "min_instances": 1
}
```

以上 UUID 和类别是格式示例，部署验收必须换成实际候选身份与完整类别顺序。代表图必须能产生至少一个非空实例，不能以空结果证明 RLE 路径通过。三个输入环境变量必须一起提供：

```bash
export VALIDATION_CONTROLLED_MODEL_WEIGHTS=/fixtures/best.pt
export VALIDATION_CONTROLLED_MODEL_FIXTURE=/fixtures/controlled.json
export VALIDATION_CONTROLLED_MODEL_IMAGE=/fixtures/image.jpg
```

`base_model`、`framework_version` 必须对应实际 checkpoint 和目标镜像。旧 schema 1 固定为 `yolo11n-seg`／Ultralytics `8.4.177`；schema 2 支持显式分割身份。原有 `VALIDATION_CONTROLLED_SEGMENT_*` 输入组仍可用，但两组变量不能混用，也不能用旧身份的报告覆盖新身份。

将输入只读挂到资格容器，另外提供原有四任务权重摘要、批准引用、Git commit、实际镜像 ID 和 GPU UUID，再按 [YOLO Backend README](https://github.com/yyq19990828/ai-annotation-platform/blob/main/apps/yolo-backend/README.md) 的完整命令运行。输入路径是容器内路径；`set -o pipefail` 保留脚本退出码。原有普通 YOLO 模式可以继续使用，但没有 `controlled_segment` 证据的报告只覆盖普通模型。

新模式实际通过 HTTP 安装训练权重、读取收据，比较冻结引用、原生头和类别；错误摘要或重新绑定应拒绝。两轮分别用 `trained:<版本>` 冷加载，验证原图 RLE、实例和类别对齐，再执行同一共享池的卸载。第二轮故障矩阵使用受控分割预测请求，覆盖 busy unload、取消计数、旧代次、重放和不完整准入头。

报告必须同时满足：

- `passed=true`、`blockers=[]`、`runtime_ephemera_clean=true`，两轮显存工作集回收率均至少 90%，卸载稳定样本不少于 5 个、波动不超过 64 MiB。
- `contract_checks` 全部为真，`deployment.pool_topology.controlled_segment` 包含准确权重、冻结引用、安装收据和两轮非空实例证据。
- 最终 `residency.state=unloaded`、`gpu_loaded=false`，所有池为空，active／builder／borrower 为零，PyTorch allocated／reserved 为零。

失败时保持 `YOLO_MANAGED_LIFECYCLE_VERIFIED=0`。通过后也须先复核镜像、权重、物理卡、驱动和池容量，再按部署流程启用并重创目标实例。更换任一资格身份后重验；本机另一块卡或另一组模型的报告不能替代目标部署。取消计数验收不等于中断真实 GPU kernel，也不覆盖硬件掉卡或驱动复位。

受控检测模型使用同一工具单独运行：schema 3 设 `task="detect"`，基础模型改为实际检测规格。报告必须包含 `controlled_detect_*` 全真检查及 `deployment.pool_topology.controlled_detect` 两轮非空原生检测框证据。普通 `YOLO(name)` 检测结果不能代替该受控路径。LibreYOLO 使用独立插件；CPU 原生资格或本地独占 GPU 检查不能代替目标平台的 CUDA 显存回收和生命周期验收。其训练 GPU 恢复仍按前面的故障表验收。

受控检测的预测元数据须包含精确模型身份；安装收据已冻结 `inference_runtime` 时，还须携带完全一致的推理环境。缺失、漂移或多余的元数据均不通过验收。

## GPU 仲裁与硬件范围

跨 Backend 的单卡共驻、驱逐、容量拒绝、双卡并行和跨主机，以及响应丢失、授权后取消、健康超时，按 [GPU 仲裁验收手册](/ops/runbooks/gpu-arbitration-acceptance) 创建 manifest，依次运行 `preflight`、`run`，对普通场景运行 `verify`。该流程需要已完成生命周期资格的 Backend、真实资源成员关系和 GPU control Worker，不能用单进程生命周期报告替代。

硬件 Xid、GPU reset、宿主机掉电或重启是另一类运维故障。安排专用目标节点和维护窗口，先保存检查点、队列与发布状态；恢复后核对驱动健康、UUID、旧进程和 GPU 锁、租约收敛、新尝试唯一性及模型收据。共享开发机上的逻辑故障验收不覆盖这些情况。

验收完成后恢复临时停止的服务，删除专用容器、测试项目、对象、缓存和故障代理，保留仓库外受限目录中的脱敏证据。日常开发 COCO8 夹具和人工验收记录继续保留。
