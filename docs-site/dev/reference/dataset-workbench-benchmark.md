# 数据集工作台规模测量

`scripts/benchmark_dataset_workbench.py` 测量已登记索引的分页、组合条件、检查器和关联项目统计。它使用真实 PostgreSQL、Redis 和 MinIO，通过正常鉴权与 API 数据库会话执行请求，不替换业务依赖。

## 数据与方法

脚本只接受当前工作树已核验归属的 `e2e` 环境。`seed` 要求用户、数据集、项目与任务为空，拒绝清空或重置已有业务数据。每个数据集的规模为 1,000 或 10,000 条索引，其中各 40 张 48×32 PNG 经过真实目录扫描、内容登记与 WebP 预览生成；其他 960／9,960 条明确为 unverified 合成索引，没有物理原件、Asset、Reference 或预览。每档关联两个项目，每项目有同规模任务，每十个任务一个有效人工标注对象。

真实 PNG 平均 119.05 B、最大 120 B；WebP 预览平均 160.15 B、最大 172 B。这种小图测数据库成本、分页边界和请求组织，不代表生产图片传输、解码或扫描吞吐。两个数据集总计 11,000 条索引、80 张真实图片、22,000 个任务、2,200 个标注对象；数据集列表本身只有两条，不能据此推断一万个数据集的列表性能。

`measure` 用已核验的迁移账号在本次命名空间执行 `ANALYZE`，核对连接的数据库名、归属注释及实际 `pg_class.reltuples`，提交并关闭 owner 连接，再使用普通运行账号测量。普通运行账号没有迁移表的所有权，其 `ANALYZE` 可能只告警而跳过，不能据命令返回推断统计已准备。

每组预热 2 次、正式采样 10 次、并发 1、页大小 20；记录实际 SQL 条数／执行时间、响应字节／行数、HTTP 完成时间和托管对象存储调用。p50 用中位数，p95 用 nearest rank；十次采样的 p95 即最大值。API 时间是进程内 ASGI 时间，包含真实数据库与 Redis，区别于浏览器 TCP 时间。连接池和应用缓存沿用现有行为，不重启共享服务或调整全局数据库参数。

## 复现

在已准备本地虚拟环境和 Node 依赖的工作树根运行，先确认 `e2e` 可丢弃且没有其他占用；人工验收使用的 `dev` 不参与测量。

```bash
pnpm dev:worktree -- doctor --mode dev
pnpm dev:worktree -- exec --mode e2e --api-port 8200 --web-port 3200 -- \
  apps/api/.venv/bin/python scripts/benchmark_dataset_workbench.py seed \
  --fixture /tmp/aap-dataset-benchmark/fixture.json
pnpm dev:worktree -- exec --mode e2e --skip-migrations --api-port 8200 --web-port 3200 -- \
  apps/api/.venv/bin/python scripts/benchmark_dataset_workbench.py measure \
  --fixture /tmp/aap-dataset-benchmark/fixture.json \
  --output /tmp/aap-dataset-benchmark/api.json
pnpm dev:worktree -- up --mode e2e --skip-migrations --api-port 8200 --web-port 3200
```

浏览器使用独立会话，在实际 `up` 输出的地址登录 fixture 中的临时账号（工厂密码 `Test1234`）。记录表格／网格切换、前后页、组合条件、检查器、所选项目统计的请求和 Resource Timing；不 mock 响应，也不把预览 GET 数当成 MinIO GET 数。

结束后通过启动器 `stop --mode e2e`，等待所属会话结束，再运行 `doctor --mode e2e` 读取 `resources.confirmation`，以其准确值执行 `destroy --mode e2e --confirm WORKTREE_ID:e2e`。复查数据库、Redis 和九个用途桶均已销毁；关闭专用浏览器，删除临时源、原始网络记录及测试缓存，保留所需的不含凭据的汇总读数。完整隔离规则见[多工作树环境](../how-to/worktree-environments.md)。

## 本机读数

环境为 Linux、Xeon Gold 6238R、112 逻辑核、251.5 GiB 内存、ext4、本地 PostgreSQL 16.14／Redis／MinIO；Python 3.12.11，API／浏览器均走本机网络。机器同时运行原有开发环境，未隔离 CPU 或模拟生产网络。没有为 E08 预先规定数值延迟 SLO，本报告建立本地合成索引基线，不据此宣称生产性能达标。

所有分页均核对 total、20 项上限和前两页真实成员；组合条件返回 960／9,960 条未核验索引，来源条件只匹配 40 张真实图片；两个项目分别统计 1,000／10,000 个任务和 100／1,000 个对象。上述纯元数据请求观察到的托管 S3 调用均为零，未进行源目录枚举。SQL 数保持有界，但深分页和状态聚合明显变慢；本报告保留这些结果，不以有界请求量代替延迟结论。

准备期间曾出现约 130 ms 与约 3.2 s 的不同分页读数。只读查询计划核对发现，统计不完整时一万条分页的估算成本约 562,944，启用 245 个 JIT 函数及优化／内联，而一千条未启用；这与 CPU 活跃、无锁等待的慢路径一致，未据此断言全部延迟来自 JIT。修正 namespace owner 统计准备后重新采集上表，旧轮次仅作方法诊断，不混入正式样本。正式末页仍有 499–2,699 ms 的跨度，后续性能排查应同时保留计划、统计和 prepared-plan 条件，而非筛掉慢样本。

浏览器为 Headless Chrome 150、1440×1000、日间主题、Vite 开发模式。页面加载稳定后，每档每项操作采样 5 次，共 60 次；从真实控件事件的捕获阶段计时，到相应数据进入 DOM 为止，不把 CLI 启动／派发时间算作交互延迟。Resource Timing 分开记录网络完成时间；网格“就绪”指当前页 20 个成功预览响应及 20 个 Blob 图片节点已挂载，不等于屏外图片均已完成浏览器解码。

每页成功预览恰好 20 次、唯一 ID 与该页成员完全相同，成功响应的请求并发峰值为 2。开发模式 StrictMode 初次挂载还各观察到 2 次无成功响应的取消尝试：每页共 22 次尝试，包含取消尝试的网络瞬时峰值为 4，不能把“两个调度槽”写成所有底层请求始终只有两个。检查器打开不读图，点击预览只增加 1 次成功读取。共 410 次成功预览、40 次开发模式取消尝试；这些交互没有自动读取原图，未出现页面未捕获异常或横向溢出。生产构建的取消次数与网络峰值未在本轮测量。

另以实际浏览器 HAR 核对两档组合条件的首／次页，共 4 个成功样本查询：均带 `search=synthetic-`、`extension=png`、`dimension_state=known`、`min_width=48`、`limit=20`，offset 分别为 0／20；total 分别 960／9,960，每页 20 个未核验索引，没有预览或原图请求。保存的汇总只包含条件、状态和数量，原始 HAR 在清理时删除。

## 解释边界

样本响应遵循服务端 count 后 limit／offset；UI 默认每页 20，可选 10／20／50／100，API 上限 200。网格的 reference 预览在当前页组件挂载后排队，应用以两个槽调度；取消尝试与新请求可能短暂重叠。`img loading="lazy"` 不会推迟此前的认证 Blob 请求，因此不能描述成“滚动到可视区才发起请求”。表格与检查器默认不读图片；检查器点击“读取只读预览”后独立读取一张。原图和预览是不同操作。

分页响应和 SQL 条数有界，不表示数据库计算成本恒定。可用性观察关系、过滤计数、深 offset、项目聚合和 PostgreSQL 执行计划仍可能随索引规模增长；应保留慢读数与统计准备方法。已有每页逐项归属查询也体现在 SQL 数中，本测量不把它描述成单 SQL 分页。

真实生产文件分布、来源数量、跨站点延迟、高并发和大图成本仍需按实际部署另测。共享视图、近似重复、Tracker 或审核专项不因这份基线成为数据集与存储交付的新前置。
