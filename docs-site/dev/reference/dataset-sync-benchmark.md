# 本地增量同步资源基线

`scripts/benchmark_dataset_sync.py` 测量已采纳目录来源的一整轮增量同步，补充[目录扫描](./dataset-scan-benchmark)和[原图读取](./dataset-read-benchmark)的资源记录。现有普通Worker实际运行调度推进、扫描、完整预检及必要的新增登记；以调度回到idle且最后一个任务实际收尾作为结束，不能把扫描完成当作同步完成。

## 复现与清理

工具只接受当前工作树完整核验归属、业务为空的e2e数据库、独立Redis和九用途桶，拒绝复用人工dev数据。Worker只接收普通运行账号，不携带迁移／测试DSN。无需启动Web、API、Beat或重建镜像。

```bash
mkdir -m 700 /tmp/aap-sync-benchmark
pnpm dev:worktree -- doctor --mode dev
pnpm dev:worktree -- exec --mode e2e -- env \
  DEBUG=false LOG_LEVEL=WARNING PYTHONDONTWRITEBYTECODE=1 \
  apps/api/.venv/bin/python scripts/benchmark_dataset_sync.py \
  --output /tmp/aap-sync-benchmark/report.json
```

默认运行1,000和10,000文件两档，`--sizes 1000`可只运行小档。报告独占创建、权限0600，并保存代码提交及观测工具SHA；运行中修改工具会使结果无效。每十秒更新当前阶段和进度，超时只报告证据未完成，不自动重启。失败报告保留已完成分项，另保存最多1MiB的私有Worker诊断日志。

脚本退出时等待自己启动的Worker结束，删除自建文件树、逐任务观测文件和日志。数据库中的合成记录及所属基础资源仍由启动器持有，按doctor给出的精确确认值停止并销毁，再独立核对数据库、Redis和九桶不存在；不要手工清表后复用。

```bash
pnpm dev:worktree -- doctor --mode e2e
pnpm dev:worktree -- stop --mode e2e
pnpm dev:worktree -- destroy --mode e2e --confirm '<resources.confirmation>'
PYTHONDONTWRITEBYTECODE=1 apps/api/.venv/bin/python -m unittest discover \
  -s scripts -p 'test_benchmark_dataset_s*.py' -v
```

保留脱敏核验摘要后删除本次报告、失败日志及测试缓存，保留人工环境和本地虚拟环境。相关运行规则见[工作树环境](../how-to/worktree-environments)。

## 工作负载与计量

每档实际写入1,000或10,000张PNG，每组最多1,000文件，包含三种目录深度和32×24、256×192、1024×768三种图片尺寸。图片由三种固定颜色真实编码，不代表生产压缩率或真实图片复杂度。通过现有纯新增策略实际扫描、预检和登记建立reference采纳基线，不用合成业务行代替内容证明；这段准备时间单列，不计入随后两轮同步耗时。

第一轮源文件保持不变；第二轮增加1%的真实图片，分别为10和100张，以纯新增自动采纳结束。每轮准确核对采纳成员集合、Item／Asset摘要与大小，旧Item、Asset和采纳修订身份必须保持，源目录前后全量摘要与元信息一致。来源缓存策略为none，不生成预览或持久原图缓存；本片不测变化内容的人工采纳、删除、慢文件系统或跨站点。

两档复用同一数据集和Worker；大档开始时，小档的1,010条采纳记录仍保留，其调度已关闭。每轮只推进相应来源，两档结果也包含这个数据库上下文和复用进程的差异，不能把全部差异归因于单一文件数。

工具只在上一个领域阶段已经终结后，显式将该合成来源的下一检查时间置为到期，再沿真实claim与Celery发布推进。保留15分钟配置值，但排除实际周期等待和60秒阶段检查间隔，不启动Beat，也不声称测得真实定时调度SLO。整轮墙钟包含这些受控唤醒、Broker往返、协调进程轮询和数据库等待。

观测bootstrap只包装调用与计时，不改变业务返回值。按每个Celery任务独立落盘，再汇总完整轮次所有扫描、调度和登记分块。SQL数量／耗时属于Worker的SQLAlchemy cursor执行，不含协调进程查询、协议事务控制或数据库服务器CPU。任务执行时间之外的差值包含派发、轮询及等待，不能全部称为队列排队。

源读取会话统计实际进入 `reference_storage.content_file` 的次数，read次数和字节取真实返回值；它与安全打开器的普通文件打开次数分别记录。通过夹具的base／new文件名区分旧文件重读与新增字节；末端身份复核可能再次打开文件，却不一定读取正文。目录遍历与DirEntry.stat为逻辑调用数，不等于内核系统调用数。

协调进程以至少100ms的间隔采样整个复用Worker的RSS、CPU、源FD和专属TMPDIR中的匿名临时文件逻辑字节；数据库查询会延长采样间隔，瞬时峰值可能遗漏。CPU不包含协调进程、PostgreSQL、Redis或文件系统服务。原文件和基线刚建立，未清空操作系统缓存；第一次测量也是暖目录。每档各运行一次，不能从单次墙钟推断p95或生产吞吐上限。

## 实测记录

1,000和10,000文件档均已完成，每档各运行一次无变化及1%纯新增轮次。主机为Linux／ext4、Xeon Gold 6238R、112逻辑核，Python 3.12.11；未使用GPU。采纳基线实际建立分别耗时251.54和2,533.30秒，单列排除在下表同步耗时之外。

| 文件档／轮次        | 整轮耗时（s） | Worker CPU（s） | 采样峰值RSS（MiB） | SQL条数／执行时间（s） | 全轮任务数 |
| ------------------- | ------------: | --------------: | -----------------: | ---------------------- | ---------: |
| 1,000／无变化       |        93.107 |           57.64 |             303.01 | 118,055／29.974        |         45 |
| 1,000／新增10文件   |        96.832 |           60.21 |             314.44 | 121,878／31.172        |         47 |
| 10,000／无变化      |       933.155 |          578.71 |             375.80 | 1,176,509／302.353     |        405 |
| 10,000／新增100文件 |       968.287 |          604.95 |             378.62 | 1,211,882／313.235     |        415 |

四轮均核对旧Item、Asset及采纳修订身份不变，源文件字节与元信息保持；新增轮次分别只增加10和100个实际成员。两档每轮仍完整读取1,000／10,000份旧文件，共1,566,860／15,681,860字节，不能将“增量同步”解释为只读取新增文件。

新增文件实际共14,210／155,360字节，但新增路径在预检、确认和登记中分别出现31／301次内容读取会话，累计43,219／466,175字节；大档新增整轮读取共16,148,035字节。四轮结束后源文件／目录及匿名临时文件描述符和临时字节均为零；采样匿名临时文件峰值均4,021字节，不能解释为资源上界。

大档新增轮次与独立test模式的训练准备基准及隔离子树的有限检查重叠，共用本机PostgreSQL／MinIO。数据／Broker／桶各有独立归属，但主机资源并非独占；这些单次暖目录结果不证明生产瓶颈、p95或吞吐上限。已观测到完整预检、大量SQL及旧文件重读成本，不据此自动新增优化或发布门槛。

最终进程正常退出，六份观测工具SHA前后完全一致。所属e2e已停止／销毁并独立核对数据库、Redis及九桶不存在，保留脱敏有界摘要并清理原报告／日志；人工dev及独立训练test保持。11项不同辅助检查沿工具交付时的通过证据复用，未重复累计。本结果完成本地增量同步测量分项；生产定时周期、真实部署和[训练准备](./dataset-training-benchmark)仍有各自范围，不能据此勾完完整E12。
