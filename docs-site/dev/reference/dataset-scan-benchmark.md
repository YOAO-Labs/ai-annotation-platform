# 目录扫描资源基线

原图完整核验与HTTP传输另见[目录原图读取资源基线](./dataset-read-benchmark)；本页只测目录索引，不将不打开图片正文的扫描结果当作读取性能。

`scripts/benchmark_dataset_scan.py` 测量真实 Celery Worker 对文件树的元信息扫描、取消及恢复。它通过既有服务创建扫描，派发到已核验的专属 Worker，使用真实 PostgreSQL、Redis 和受控目录；不替换扫描算法、数据库会话或来源授权。已登记索引的页面性能另见[数据集工作台规模测量](dataset-workbench-benchmark.md)。

## 数据与计量

工具只接受当前工作树已核验归属、业务表为空的 `e2e` 环境，不重置已有数据。数据库归属注释、Redis 容器、九用途桶与全部连接覆盖均须匹配；普通 Worker 不继承迁移或测试账号连接。临时受控根和 Worker 由工具创建与收尾，数据库、Redis 和桶由工作树启动器负责销毁。

默认档位为 1,000／10,000／40,000 个真实文件，每组最多 1,000 文件，包含中文同名文件和三种目录深度。图片为 4×3 PNG，部分文件写为损坏图片；每百项一份 `.tmp` 排除文件。扫描只登记元信息，不校验图像内容或创建 DatasetItem。单目录另放 5,001 个不同文件，单轮另放 50,001 文件，验证既有预算拒绝，不调高预算。

Worker 内记录 `DirEntry.stat` 逻辑调用次数、目录遍历次数、安全打开器的普通文件打开次数、SQL 条数与执行耗时，以及每次目录扫描和应用尝试的耗时。stat 数量不能当作内核系统调用数量；应用尝试包含失败调用，也不包含随后事务提交的时间。目录扫描 p95 使用 nearest rank，整体用时从派发前开始，到终态与 `task_postrun` 测量文件均可见为止。

夹具创建和前后完整对账不计入扫描用时。协调进程为准确对账保留期望路径集合，它的内存不计入 Worker RSS；本报告不代表整套工具或数据库服务器的峰值内存。

协调进程以至少 50 ms 的间隔采样 Worker RSS，数据库轮询会延长间隔，因此采样峰值可能漏掉瞬时峰值；另保存 Linux VmHWM，它是同一复用 Worker 的累计高水位。数据刚写入，未清空操作系统缓存，也未隔离共享主机负载。工具摘要保存代码提交和测量脚本 SHA，运行期间脚本变化会使结果无效。

取消档位使用 10,000 文件，观测到部分目录提交后请求取消。分别记录取消事务提交耗时和观测到 Worker 实际收尾的耗时，核对源目录描述符为零、检查点不再增长，然后恢复同一运行。旧 attempt 必须失去写资格；恢复完成后逐项核对目录／文件集合、排除计数、无重复和源文件内容不变。恢复阶段的目录重验次数单列，不能把它算作零重复工作。

索引列表通过实际列表处理函数读取 25 项，同时禁止来源安全打开和目录扫描，核对 SQL 次数及没有物理遍历。它不包含 HTTP、浏览器或图片正文传输时间。

## 复现与清理

在工作树根运行，先确认 `e2e` 可丢弃且没有其他使用者。人工验收的 `dev` 不参与。

```bash
mkdir -p /tmp/aap-scan-benchmark
pnpm dev:worktree -- doctor --mode dev
pnpm dev:worktree -- exec --mode e2e -- sh -c \
  'DEBUG=false LOG_LEVEL=WARNING PYTHONDONTWRITEBYTECODE=1 apps/api/.venv/bin/python scripts/benchmark_dataset_scan.py --output /tmp/aap-scan-benchmark/report.json'
```

`--sizes` 可选择 `1000 10000 40000` 中的档位；取消恢复和两个预算边界仍会执行。输出文件已存在时拒绝覆盖。业务库非空也会拒绝，重跑前应按归属销毁该可丢弃环境后重新准备，不手工清表。失败时仅在输出旁保留最多 1 MiB 的 Worker 排障日志，工具创建的临时文件树和子进程仍收尾。

```bash
pnpm dev:worktree -- doctor --mode e2e
pnpm dev:worktree -- destroy --mode e2e --confirm '<resources.confirmation>'
PYTHONDONTWRITEBYTECODE=1 apps/api/.venv/bin/python -m unittest discover \
  -s scripts -p 'test_benchmark_dataset_scan.py' -v
```

保留需要的脱敏摘要后，删除本次报告与排障日志。归属、环境或未知连接检查失败时，不强制删除资源。扫描错误的处理见[目录观测扫描未完成](../how-to/debug-celery.md#目录观测扫描未完成)。

## 本地结果与限制

测量在 Linux、ext4、Xeon Gold 6238R（112 逻辑 CPU）和约 251.5 GiB 内存的主机完成。Worker 启动后基线 RSS 为 237.4 MiB；下表来自一次完整正式运行，每档一次，不能作为多次运行的延迟分布。p95 仅用于该档各次目录遍历耗时。

| 输入文件／子目录 | 完成时间（s） | 采样峰值 RSS（MiB） | Worker SQL 次数／执行时间（s） | 目录遍历／stat 调用 | 目录遍历 p95（ms） |
| ---------------- | ------------- | ------------------- | ------------------------------ | ------------------- | ------------------ |
| 1,000／1         | 0.611         | 242.4               | 307／0.175                     | 4／2,002            | 15.69              |
| 10,000／19       | 3.959         | 244.1               | 2,161／1.102                   | 40／20,038          | 14.86              |
| 40,000／79       | 16.189        | 244.5               | 8,341／5.118                   | 160／80,158         | 15.40              |

文件数包含被排除项，三个完成档分别保留 990／9,900／39,600 个选中文件和 10／100／400 个排除项。目录数不含来源根。完成前会再验证目录清单，所以遍历与 stat 数量包含枚举和最终重验；这不是每文件只访问一次的算法。三档的精确路径／类型集合均匹配，未创建 DatasetItem，原文件内容和元信息保持不变，普通文件打开为零。每次任务收尾后源文件描述符为零。

10,000 文件取消档在已保存 11 个目录、3,018 行检查点时提交取消：事务耗时 36.1 ms，93.9 ms 后观测到任务收尾及源 FD 为零。检查点随后未增长，旧 attempt 写资格拒绝。恢复先重验 11 个目录，再枚举 9 个待处理目录，最后验证全部 20 个目录；恢复用时 3.154 s。取消轮另执行过 12 次目录调用尝试，两轮共遍历 52 次、stat 24,055 次；同规模完整扫描为 40 次和 20,038 次，因此恢复存在实际重复工作。最终 10,000 文件与 19 个子目录准确对账。

5,001 项单目录在 0.510 s 后返回 `directory_too_large`，执行 5,000 次 stat，未把部分目录清单提交为成功。50,001 文件／102 子目录在 14.963 s 后返回 `scan_budget_exceeded`，保留部分检查点但 `complete=false`；不把部分结果当成文件缺失或可消费样本。该轮 Worker 累计高水位约 249.1 MiB。六档索引列表均最多 25 行、10 条 SQL，没有遍历或打开物理来源，单次处理时间为 12.9–31.5 ms。

当前读数显示，主要成本随目录和清单规模增长，40,000 文件档的 Worker SQL 执行约占总时长 31.6%；这提示后续排查应先分解数据库往返和服务校验开销，而不是先扩大缓存或改扫描算法。本轮没有修改生产实现，也没有据此新增性能门槛。一次运行与小文件树不足以证明生产瓶颈或达到任意并发 SLO；当前单目录 5,000 项、单轮 50,000 项／5,000 目录和超时限制保持。

首轮工具校准发现超限夹具同名覆盖，以及计时起点、p95 和连接归属检查的问题；校准结果未纳入上表。修正后重建一次性环境，固定测量脚本完成上述全部六档。工具仅验证本机合成目录的元信息扫描；CephFS／NFS／跨站点、慢文件系统、原图读取、同步与训练准备性能仍需对应场景测量。
