# 目录原图读取资源基线

`scripts/benchmark_dataset_read.py` 测量目录引用原图的完整核验和 HTTP 传输。它通过真实扫描及严格登记服务建立引用，再以实际 JWT 调用现有 `GET /api/v1/dataset-items/{item_id}/content`；每次完整读取核对返回 SHA-256、长度和实际响应字节。来源策略为 `none`，不使用持久原图或预览缓存。

这份结果补充[目录扫描](./dataset-scan-benchmark)和[索引／预览查询](./dataset-workbench-benchmark)测量。它只描述本地目录图片读取，不改变现有资源预算，也不建立新的发布性能前置。

## 运行与清理

在工作树根使用本地 API 虚拟环境；`e2e` 必须可丢弃且无其他使用者。脚本复用现有完整资源归属核验，要求空业务库；它不会清空已有业务数据。九桶、数据库及 Redis 均由工作树启动器独立配置，人工验收的 `dev` 不参与。

```bash
mkdir -m 700 /tmp/aap-dataset-read
pnpm dev:worktree -- doctor --mode e2e
DEBUG=false LOG_LEVEL=WARNING PYTHONDONTWRITEBYTECODE=1 \
  pnpm dev:worktree -- exec --mode e2e --api-port 18100 --web-port 13100 -- \
  apps/api/.venv/bin/python scripts/benchmark_dataset_read.py \
  --output /tmp/aap-dataset-read/measurement.json
```

首次 doctor 的资源不存在提示不代表初始化失败；`exec` 会准备该模式。脚本输出文件必须不存在；默认每个负载20次，可用 `--rounds` 指定20至50次。端口由启动器保留，独立 API 使用实际分配端口；无需启动 Web、Celery 或重建镜像。子 API 只接收普通运行连接，不携带迁移／测试 DSN。

就绪检查使用 `/health/db`、`/health/redis` 和 `/health/minio`。综合 `/health` 还要求 Celery Worker 响应，不适用于这项只读 HTTP 测量。

脚本退出时等待自建 API 进程组结束，清理自建目录和匿名快照。失败时只保存至多1 MiB的 API 日志供诊断，不出具成功测量；观察超时不自动重启。基础资源仍保留，记录结果后按 doctor 返回的准确 `resources.confirmation` 执行 `stop`、`destroy`，再独立确认数据库、Redis及九桶不存在。最后删除本轮报告、失败日志及测试缓存，保留人工环境。

辅助测试不连接数据库或对象存储：

```bash
PYTHONDONTWRITEBYTECODE=1 apps/api/.venv/bin/python \
  -m unittest discover -s scripts -p test_benchmark_dataset_read.py -v
```

## 工作负载与计量边界

夹具包含1024×768 PNG、1920×1080 JPEG和4096×2048 PNG，使用固定种子生成 RGB 像素；PNG采用无压缩编码，JPEG质量90。图片均真实编码、完整核验并登记，另保留登记 helper 的小型控制图。源文件在运行前后全量核对 SHA，不用合成数据库行冒充可读取媒体。

每张图片先记录该 API 进程的首次请求，再分别以单路／四路发起20次完整读取。客户端通过信号量覆盖请求、完整响应体及服务端收尾观察；单次延迟不含在此信号量前排队的时间，整组耗时包含排队。p95采用 nearest-rank，不从平均值推断。源文件刚生成并已登记，操作系统缓存未清空；首次请求也不代表冷盘。

观测 wrapper 不修改业务返回值或依赖。请求上下文传入实际读取线程，记录内容读取会话／read次数、源字节、图片检查时间，以及 SQLAlchemy cursor 执行次数和耗时。内容读取会话是进入 `reference_storage.content_file` 的次数，不是操作系统 open 次数，末端身份复核还可能再次打开文件；SQL计数不等于数据库网络往返总数，也不含协议级事务控制。到响应头的时间包含完整源读取、摘要和图片检查，完整响应时间再包含 HTTP 传输和客户端摘要计算。并发时各阶段可能重叠，不能简单相加判断瓶颈。

每20 ms观察独立 API 的 RSS、CPU、来源文件／目录 FD和该进程位于专属 TMPDIR 的匿名临时文件。临时字节是文件逻辑长度，不是底层磁盘块或提供方物理占用；峰值采样可能遗漏短时分配。RSS属于整个 API 进程，内存分配器可保留已释放内存，不能将前后 RSS 差异直接称为泄漏。CPU不包括客户端、数据库、Redis及文件系统服务的进程成本。

最大图片另在完整核验后的响应体传输中断开连接，分别记录客户端关闭耗时、服务端实际收尾与轮询观察延迟。若服务端在关闭前已结束则单列，不能算作取消收尾。该场景不证明读取前或源读取中的取消时延；收尾后还会完整读取一次控制档，确认后续请求可用。

## 本地实测结果

2026-10-25 在 Linux 5.15、ext4、Python 3.12.11 上完成；CPU 为 Xeon Gold 6238R、112 个逻辑核，宿主机总内存约251.5 GiB。机器由其他任务共享，未设置独占 CPU 或清空文件缓存；本轮不使用 GPU。API 初始 RSS 为372.72 MiB。下表只汇总工具定版后的最终一轮，不混入就绪诊断或前一轮校准。

三档共125次真实请求：123次首次／负载完整读取、一次响应体断开、一次断开后完整读取；124次完整响应逐次核对 SHA 和长度。源文件前后 SHA 全部一致。

| 1920×1080 JPEG |  1,862,268 |                            100.64 |
| 4096×2048 PNG  | 25,175,958 |                            317.16 |

每行20次；单次延迟不含信号量前等待，整组墙钟包含等待和收尾观察。

六个负载结束后的源常规文件FD、源目录FD、匿名临时FD和临时逻辑字节均为零。最大档四路的临时峰值为100,703,832 B，即四份已核验图片的逻辑长度；API峰值RSS约522.72 MiB，最后一组结束为396.56 MiB。它们只证明本次负载的观测值，不是所有尺寸／并发的内存上界。

断开场景在完整核验25,175,958 B后，只接收65,536 B响应体即关闭。客户端关闭耗时1.09 ms；服务端在关闭开始后5.57 ms完成实际收尾，随后16.52 ms才被客户端轮询观察到。观察后源／临时FD和临时字节均为零；后续小档完整读取88.90 ms成功。这不是源读取中取消的时延。

本次四路提高了整组吞吐，但单次响应尾延迟变长；JPEG虽字节更小，解码检查时间仍高于小PNG。大PNG还包含完整核验和约24 MiB的HTTP传输成本。固定65次cursor执行及并发时执行时间上升是可复现的后续分析线索；本工具没有拆分全部连接等待、授权和调度成本，不能将其余耗时归为磁盘瓶颈，也不据此自动改读取流程或增加性能门槛。

## 适用范围

结果限本机文件系统、三张合成内容图片、无持久缓存和同机 TCP。它不证明冷盘、真实图片分布、S3／SFTP、跨站点、高并发或十万张媒体全量吞吐。同步、训练准备和生产目标仍按各自原始要求测量；Tracker、会话和审核专项不因本基线成为验收前置。
