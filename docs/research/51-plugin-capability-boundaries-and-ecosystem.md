# 核心能力与扩展边界：OpenCode 插件、Supervisely App 生态及后端重构衔接

> 调研日期：2026-10-28。
> 状态：研究建议，不是已批准的替代实施计划；未改变旧计划状态、取消既定目标或实施插件安装机制。
> 范围：合入主线在线学习、数据集原件和受控存储后的当前工作树；参考 OpenCode v2 与 Supervisely 的公开文档、SDK 和应用源码。
> 证据口径：**事实**来自源码、官方资料或本轮只读运行；**建议**是本项目的目标设计；没有运行验证的外部机制不视为已取得部署或安全资格。

## 1. 结论

建议采用 **OpenCode 式核心插件装配 + Supervisely 式扩展 App 生态**，同时保留本项目已经建立的数据所有权、权限、事务、作业恢复和原件身份约束。

核心能力掌握业务规则、权威状态和最终提交权；扩展能力提供可替换的算法、外部接入、工作流组合和交互界面。插件化不是给现有 API 增加一个包扫描器，也不等于把每个模块都变成独立服务。

对旧后端重构计划的建议是**继承式替代，而非先全量做完或直接作废**：

- 不把全部模块独立部署与语言替换验收作为开始插件化的前置条件。
- 保留旧计划的业务边界、不变量、已落地实现和有效证据。
- 把 Assets、Learning、Insights 及装配中的未闭合工作，按实际插件能力涉及的调用链迁入新主线；不能只更新规范而保留越界实现。
- 对独立部署、跨语言实现、生产采用等目标分别决定是否继续、调整次序或取消。原计划的明确范围在维护者批准变更前仍有效。
- 新执行计划承接每项未完成工作、正式架构说明同步之后，才可把旧计划标记为被替代并归档；不能标为全部完成。

本报告记录上述建议，未执行计划退役。当前状态与剩余工作的权威入口仍是[模块部署与解耦台账](../../docs-site/dev/concepts/module-deployment.md)，不在研究报告中维护另一份实时待办。

## 3. 核心与扩展的判断方法

### 3.1 三条独立的轴

| 维度     | 要回答的问题                         | 不应混淆的概念                         |
| -------- | ------------------------------------ | -------------------------------------- |
| 发布方式 | 随平台发布，还是独立安装？           | 官方模型可以默认内置，但仍是可替换实现 |
| 业务责任 | 谁拥有规则、状态和最终提交权？       | 独立进程不自动成为独立业务 owner       |
| 信任等级 | 谁维护代码，获得哪些权限，如何执行？ | 使用同一插件清单不等于获得相同特权     |

内置不等于始终启用。Learning、Insights 等内置领域能力可以按部署需求选择启用，但不能停用仍被其他已启用能力依赖的模块。核心插件可以拥有自己的私有数据；跨模块只能使用明确的公开能力。

### 3.2 目标能力边界

下表是建议边界，不是当前实现完成声明。

| 领域         | 核心／内置领域插件负责                                                       | 可安装扩展负责                                              |
| ------------ | ---------------------------------------------------------------------------- | ----------------------------------------------------------- |
| 身份与项目   | 主体、账号有效性、成员、角色与授权、项目配置、类别体系                       | SSO／身份源连接、外部组织同步、项目模板；不自行授予平台权限 |
| 数据集与存储 | 素材身份、原件摘要与版本、数据集成员关系、保存位置、访问授权、保留与删除规则 | 数据源连接器、外部格式解析、转换及同步适配                  |
| 标注与审核   | Task／Scene／Frame 关联、规范几何、标注版本、并发与审核、原子提交及历史      | 辅助标注、交互分割、跟踪算法、批量变换、行业工作流          |
| 推理与预标注 | 能力目录、实例注册、路由与准入、执行身份、取消和迟到结果隔离                 | YOLO、SAM、OCR、自定义模型服务、后处理实现                  |
| 在线学习     | 冻结数据版本、Run／Attempt、评估与产物账本、模型谱系、发布与回退规则         | 训练框架、训练器、增强算法、搜索策略、主动学习评分器        |
| 作业与资源   | 通用作业身份、进度、派发、幂等、取消与恢复、资源准入；领域终态仍由领域解释   | 具体执行器和计算后端，不另建权威作业账本                    |
| 质量与分析   | 必需的结构／几何合法性底线、结果归属、审核状态、授权读取和保存视图           | 质检算法、评估指标实现、行业报表和结果可视化                |
| 审计与通知   | 审计事实、接收者权限、通知偏好、站内记录和投递交接                           | 邮件、飞书、Slack、Webhook 等通道                           |
| 工作台与 UI  | 会话、任务上下文、编辑状态、撤销与提交协议、稳定界面扩展点                   | 侧栏、上下文操作、配置表单、专用操作面板                    |

存储不能被一个泛化 Blob 插件抹平所有权：源媒体由 Assets 维护，标注 Mask 由 Labeling 维护，训练包与权重由 Learning 维护，导出产物由其任务所有者维护。公共存储 transport 不获得这些领域的删除决策权。

### 3.3 不能外包给扩展的不变量

1. **授权与最终提交**：扩展可以提交登记请求、预测结果或变更命令；核心在落库前重新核对当前权限、版本、来源和执行状态。允许自动化提交，不等于允许绕过核心入口。
2. **停用后的数据可读性**：移除模型、格式插件或 App 后，已有原件、标注、数据快照和训练谱系仍可读取与审计；受影响的新操作明确拒绝或等待替换。
3. **业务语义演进**：新增平台无法表达的几何类型、修改审核规则或原件身份语义，属于核心协议演进，不能靠允许任意 JSON 规避。
4. **原子性与执行所有权**：已有同事务 Native／SQL 调用不机械改成多个 HTTP 提交；超时、取消请求、租约到期均不等于物理任务已停止。
5. **凭据与状态隔离**：外部扩展不接收通用数据库 DSN、ORM／Session、长期高权限用户 Token，或可任意访问内部服务的容器对象。扩展状态按安装作用域隔离，不能只以插件 ID 作为全局存储命名空间。

## 4. OpenCode v2：插件装配机制

### 4.1 可以借鉴的机制

| 已核对的设计                                                               | 对本项目的借鉴                                                       |
| -------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| 内部工具、Agent、Provider 等通过插件接口装配；策略相关插件有禁止关闭的保护 | 核心自身也以插件组成，但保留最小宿主和受保护的权限／策略入口         |
| 一个包通过 exports 提供 server、TUI、GUI、RPC 等部分                       | 一个制品可包含执行部分、可选 UI、独立契约与配置，不要求同进程运行    |
| `Plugin.define` 提供 setup／清理；Effect 形式使用作用域管理资源            | 明确启动、就绪、排空、停用和清理责任，不能仅删除 registry 条目       |
| 领域注册／transform 与运行时 hooks 分开                                    | 用明确的能力注册与命令接口代替对全局配置或私有 service 的任意修改    |
| `Rpc.define` 描述输入、输出、错误和事件，并支持 schema 校验                | 契约可独立于实现使用；不能只依赖 Python 类身份或 TypeScript 静态类型 |
| CLI 管理安装、更新检查、更新与移除；配置支持精确版本                       | 安装管理、运行状态和版本身份都要成为正式能力，而非启动时随意加载目录 |

依据：[插件概览](https://opencode.ai/v2/docs/build/plugins)、[Server API](https://opencode.ai/v2/docs/build/plugins/server)、[RPC](https://opencode.ai/v2/docs/build/plugins/rpc)、[内置装配源码](https://github.com/anomalyco/opencode/blob/dev/packages/core/src/plugin/internal.ts)、[插件配置](https://opencode.ai/v2/docs/plugins)。

### 4.2 不应照搬的部分

- **同进程信任模型**：官方明确说明 Policies 不沙箱隔离插件代码。权限检查的公开 API 不是对任意插件进程行为的约束。
- **覆盖式注册**：本项目不应默认允许后来安装的扩展覆盖核心授权、提交入口或其他发布者的能力。采用带所有权的命名空间和显式冲突规则。
- **生产环境自动发现与热加载**：项目目录中的可执行代码不应自动成为服务端插件；安装需经过管理员授权与制品验证。先采用显式部署／重启，不优先复制热替换机制。
- **实验性 UI 接口**：不能把 GUI 的实验能力当作本项目稳定 UI SDK 的现成规格。
- **把通用 hook 当业务协议**：不能用任意 before／after 回调决定授权、审核、模型发布或原子提交；这些规则仍归领域 owner。

依据：[Policies](https://opencode.ai/v2/docs/policies)、[GUI](https://opencode.ai/v2/docs/build/plugins/gui)、[旧插件迁移说明](https://opencode.ai/v2/docs/build/plugins/migrate-v1)、[当前 SDK 包声明](https://github.com/anomalyco/opencode/blob/dev/packages/plugin/package.json)。

## 5. Supervisely：App 生态与 Developer Portal

### 5.1 制品、安装与运行分开

公开 SDK 区分 Ecosystem 条目的 `ModuleInfo`、团队范围的 `AppInfo` 和具体 task／session。可借鉴的是把“可发现的应用”“在哪里启用”“某次实际运行”分开，而不是照搬其数据库结构或增加一套本项目作业系统。

本项目的插件目录和启用记录应关联现有 Jobs、TrainingRun／Attempt、Inference 执行记录；长驻服务也须区分安装版本、服务实例和单次业务操作。

依据：[App API 源码](https://github.com/supervisely/supervisely/blob/d17cc620f018/supervisely/api/app_api.py)。

### 5.2 声明式入口与执行需求

| Supervisely 字段             | 实际表达的能力                   | 本项目可借鉴的边界                                  |
| ---------------------------- | -------------------------------- | --------------------------------------------------- |
| `context_menu.target`        | 在项目、数据集、文件等上下文启动 | 明确目标类型与所需权限，不为每个 App 硬编码按钮     |
| `integrated_into`            | 集成到标注工具、面板或独立页面   | 稳定的 UI 插槽及受限调用接口                        |
| `headless`                   | 是否提供应用前端                 | 无 UI 的批处理同样是一等扩展                        |
| `entrypoint`、`docker_image` | 运行命令与镜像                   | 预构建、固定身份的执行制品                          |
| `gpu`、`min_agent_version`   | 计算需求与 Agent 兼容性          | 调度需求是声明；是否准入由平台判定                  |
| `session_tags`               | 发现具有约定用途的运行 session   | 可参考服务发现体验，但不替代现有类型化能力 Registry |
| `instance_version`           | 所需平台兼容版本                 | 发布前验证宿主、SDK 和协议的兼容性                  |

注意：其 `version` 表示 App Engine 版本，不是应用自身版本。旧引擎使用 `main_script`，新引擎使用 `entrypoint`；不能混成一套本项目规范。

真实案例 [Apply NN to Images Project](https://github.com/supervisely-ecosystem/nn-image-labeling/blob/04094da1a574/project-dataset/config.json) 声明镜像、启动命令、workspace 任务显示位置，以及图片项目／数据集上下文菜单。它证明 App 不只是模型服务，还可以包含用户操作流程。

依据：[config.json](https://developer.supervisely.com/app-development/basics/app-json-config/config-json)。

### 5.3 Agent 与容器适合承载重计算

模型、训练、格式转换和批量质检有不同依赖与资源需求，放到独立运行环境比全部安装进主 API 环境更合适。Supervisely 的 Agent／容器结构提供了这方面的设计参考。

但“允许启动 App”不等于“允许访问所有数据”，Docker 或 `isolate` 字段也不等于已证明恶意多租户安全隔离。公开资料不足以替本项目证明细粒度出网、凭据隔离或生产沙箱资格；本项目需要自行约束插件身份、调用者、项目／资源范围、运行代次、凭据有效期和资源预算。

依据：[Agent 容器执行源码](https://github.com/supervisely/agent/blob/c78a8e2c993a/agent/worker/task_dockerized.py)。本报告没有验证其实际生产安装参数，不把代码默认值推广成所有部署的结论。

### 5.4 Developer Portal 是架构的一部分

值得借鉴的开发路径是：公开 API／脚本 → headless App → 带 UI 的 App → 标注工具集成，同时提供 SDK、模板、本地调试、示例和公共／私有分发。

本项目应复用既有 Python SDK、OpenAPI、React 与本地 UI 组件，不复制第二套前端框架。常见参数界面优先由 JSON Schema 驱动；复杂外部 UI 再使用隔离页面及受限通信。可信内置 UI 与第三方 UI 不应自动拥有相同的 DOM、凭据和内部状态访问权。

Supervisely 的公开 App 发布要求声明 `instance_version` 与 `docker_image`、检查 SDK 兼容性，并把依赖预装进镜像。可借鉴其发布门禁；本项目还应固定不可变制品身份，并让模板、schema、文档和兼容检查使用同一契约来源。

依据：[Developer Portal](https://developer.supervisely.com/)、[App Compatibility](https://developer.supervisely.com/app-development/basics/compatibility)、[标注工具集成](https://developer.supervisely.com/app-development/apps-with-gui/labeling-tool-app)。

## 6. 本项目的插件化目标形态

### 6.1 最小宿主、领域 owner 和扩展分别负责什么

- **最小宿主**：插件清单、依赖兼容、启动装配、能力授予、生命周期与运行入口；不吸收全部业务规则。
- **内置领域插件**：维护权威状态、公开命令／查询和内部适配器；已有受限 Native／SQL 能力继续保留原事务。
- **能力提供方**：模型、训练器、连接器、格式转换器、质检器、通知通道等，通过所属 owner 的窄协议接入。
- **工作流 App**：组合公开领域能力，使用现有作业与训练账本，不自行决定审核、发布或资源回收的核心语义。
- **UI 扩展**：通过受控上下文、命令、表单和结果面板提供交互，不直接获得数据库或后台凭据。

这些是职责，不是互斥包类型；一个制品可同时提供模型能力、工作流和 UI。统一清单与生命周期不要求用一套万能 RPC 替换既有 ML、训练 pull 或同事务数据协议。

### 6.2 清单与生命周期的最小要求

清单至少区分：插件 ID／发布者、插件版本、协议版本、宿主兼容范围、提供／依赖能力、执行与 UI 入口、配置 schema、请求权限、资源／网络需求、制品摘要及私有状态升级要求。

安装、授权启用、实际运行、排空、升级、停用和卸载是不同操作：

- 运行绑定确定的插件制品、配置、输入快照和执行代次，更新默认版本不改变在途运行。
- 停用先阻止新准入，处理已有运行及依赖，再移除入口；不能只隐藏菜单。
- 升级失败不能留下半套注册或混合版本；回退还须满足数据可读性和执行所有权条件。
- 扩展可维护隔离的自有状态，但不得借安装迁移修改核心 schema。内置模块迁移仍由受控装配统一编排。
- 核心不把任何插件的自报成功当作已提交事实；产物、权限、版本与当前执行身份都要核验。

| Inference 已有模型执行端口、HTTP 协议与能力协商 | 模型 Provider 的公开边界        | 安装制品、启用作用域、依赖兼容及完整生命周期                    |

| 训练执行器独立，已有共享冻结合同                | 输入、参数、模型身份及产物核验  | 框架分派仍绑定明确实现；注册与资格不能只靠自报支持              |
| API 与 Celery 仍静态装配                        | 已验证的路由、任务和 owner 绑定 | 统一内置插件装配及受控扩展入口                                  |
| 已有 owner、限权角色、幂等与恢复机制            | 插件宿主的数据与运行保障        | Assets、Learning、Insights 和运行装配的剩余边界须按现有台账收口 |

已完成的主线整合意味着在线学习和存储功能可作为当前业务基线，不意味着其全部 owner 边界已提取，更不意味着插件安装与升级已实现。

## 8. 旧后端重构计划如何衔接

### 8.1 为什么不是“先做完旧计划”

[旧计划](../plans/1792160873_backend-module-decoupling.md)第 1、7、8 节明确要求完整模块的语言无关契约、独立运行及所选替换实现的验证；第 9 节 E 阶段仍是逐模块独立运行和替换。它不只是“按规范整理代码”。

新目标增加了统一插件装配、安装管理、扩展隔离和开发者体验。即使把旧计划所有独立部署工作做完，这些能力也不会自动出现。把 E 阶段全部完成作为新目标的前置门，会推迟真正的插件安装闭环。

但旧计划已经明确“尚无远程消费者的进程内函数不提前网络化”“强事务不能由多个 RPC 冒充”“不建万能框架”。新方向并非推翻旧设计，而是调整主交付目标与执行次序。

### 8.2 继承、迁移和重新决策

下表是处置建议，不是取消目标的批准记录，也不是第二份进度台账。

| 旧计划内容                                         | 建议处置                                                               | 不能省略的要求                                                     |
| -------------------------------------------------- | ---------------------------------------------------------------------- | ------------------------------------------------------------------ |
| A：入口、数据、事务盘点                            | 继承为插件能力与依赖清单的事实来源                                     | 主线新增的存储、学习、运维调用必须纳入，不能继续使用过期基线       |
| B／C：公开契约、依赖方向、单一写入 owner、最小权限 | 作为硬约束保留；未闭合项迁入对应插件切片                               | 不能以新增 manifest 代替消除私表、私有导入和宽凭据依赖             |
| D 及各模块已验收实现、工件、消费者与恢复证据       | 复用，不为换名重新实现或重复验收未变范围                               | 证据保持原代码、环境和拓扑的适用界限                               |
| Assets、Learning、Insights 的未闭合边界            | 迁入新主线并按实际消费链推进                                           | 相应扩展上线前，其触及的数据、授权、事务与恢复边界必须闭合         |
| 静态 API／worker／迁移／凭据装配                   | 转化为内置插件统一装配任务                                             | 沿用现有实现和事务，不另造平行业务系统                             |
| E：所有模块独立构建、部署与替换目标                | 建议不再作为所有插件工作的统一前置门；按实际隔离、扩缩容与替换需求重排 | 属于原计划明确范围，须由维护者决定承接、延期或取消；未决定前仍有效 |
| 跨语言实现、Go 实验                                | 保留可移植契约；实际语言替换单独选择和验收                             | 不把实验当完整能力，不要求为了形式而永久维护双份实现               |
| “等待主线学习／存储功能合入”                       | 该等待理由已失效，转为当前代码的 owner 收口                            | 功能合入不是解耦完成，不能把原暂缓条目直接勾选完成                 |
| 旧库迁移、执行权退役、生产容量与部署故障           | 按目标环境适用性承接到明确的上线／运维门槛                             | 未处理前禁止宣称对应环境采用；不能以插件化名义绕过或丢弃           |

### 8.3 开始插件化之前，实际需要完成什么

不是先要求所有模块完成远程化，而是为**每个要交付的插件切片**设置前置门：

1. 被调用的核心命令／查询有明确 owner，扩展接口不携带 ORM、Session 或通用凭据。
2. 输入版本、原件／模型身份、产物归属与最终提交条件明确。
3. 撤权、取消、重复投递、丢响应和迟到结果不能越过现有围栏。
4. 所需迁移、角色、真实消费者和运维入口有可验证的装配方式。
5. 尚未触及的模块缺口继续留在唯一台账，不能因为首个插件完成而消失。

这允许已有 Inference 契约先承载真实模型插件，同时继续收口相关 Assets／Learning 边界；不要求先把整个平台换语言，也不接受先开放任意插件、以后再补权限。

### 8.4 旧计划正式退役的门槛

按[计划归档约定](../plans/README.md)，建议在以下条件全部满足后将旧计划标为 `superseded`，而不是 `completed`：

1. 维护者确认目标调整，尤其是全模块独立部署和语言替换要求的承接方式。
2. 新执行计划存在，逐项记录未完成内容的去向；延期／取消项写明理由，不能无声删项。
3. 正式架构文档更新，当前状态仍只有一个权威台账；研究报告不成为长期实施真值。
4. 旧计划补充替代说明与 Outcome 交接，保留已实现成果、证据和未取得的资格。
5. 再移动到 `docs/plans/archive/`，保持原文件名，同时更新所有 Markdown 引用。

旧计划尚未完成上述交接，仍保持原状态与位置。后续已形成并推进[LibreYOLO 推理插件实施规划](../plans/1793156248_libreyolo-inference-plugin.md)，以“现有 LibreYOLO 训练 → 原生权重回流 → 独立 LibreYOLO GPU 推理 → 人工发布与项目使用”为首个切片，并包含低门槛开发路径及首期 GPU 验收要求；实际完成情况和剩余门槛以该计划的 Outcome 为准。它不是覆盖全部旧目标的替代计划。

## 9. 建议的实施组织方式

采用“先明确不变量和扩展契约，再通过真实纵向切片完善宿主”的组织方式；不先做空的通用插件市场，也不等待所有独立部署工作结束。

建议优先选三个代表性闭环：

1. **现有模型服务插件化**：安装／验证制品 → 注册能力 → 项目启用 → 实际推理与候选提交 → 停用和在途任务处理。
2. **现有格式适配器插件化**：移除公开 Session／ORM → 读取授权输入 → 产生规范结果 → 核心验证并提交 → 重复与失败恢复。
3. **带 UI 的质检或分析 App**：声明上下文入口 → schema 参数表单 → 使用既有 Jobs → 结果展示；不为该 App 修改中心页面或引入第二套作业账本。

每条切片都应证明：

- 未安装／未授权／不兼容时明确拒绝，不退回内部私有路径。
- 安装制品而非仅工作区源码链接能够运行，版本和输入身份可追溯。
- 越权、过期执行和迟到结果不能落库；扩展失败不破坏其他领域状态。
- 停用会阻止新准入并正确处理已有运行，恢复或升级不会重复提交。
- 移除扩展后，核心数据和历史结果仍可读取；依赖阻塞有明确反馈。

开发者入口随后围绕这些真实案例提供 SDK、契约、模板、联调方法和兼容矩阵。私有／公开目录负责分发，不代替执行协议、安全边界和生命周期。

## 10. 未验证事项与研究限制

- 没有在本机验证 OpenCode 的第三方安装、热替换、GUI 或全部 RPC API；CLI 版本与帮助输出仅证明本机管理入口。
- 没有运行 Supervisely Agent、App、浏览器集成或生产权限场景；不依据公开示例宣称其完整安全或资源隔离能力。
- 对照研究阶段未实现本项目的插件清单、加载器、安装／升级、UI 扩展或新 SDK；后续 Inference 切片的实现与验收单独记录于承接计划，不据此宣称已有通用插件框架或前端 SDK。
- 没有批准缩减旧计划范围、归档旧计划、修改数据库或切换日常运行拓扑。
- 后续正式架构决定需进入现有开发文档，必要时形成 ADR；执行任务进入承接计划，不能只停留在本报告。
