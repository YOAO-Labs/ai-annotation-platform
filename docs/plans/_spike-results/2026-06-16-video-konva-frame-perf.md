## 1. 这个 spike 要回答什么

决策 A:视频像素怎么进 Konva。

- **A1**(推荐):`Konva.Image` 以视频帧为 source,**视频单独一层** `batchDraw`,播放时逐帧重绘视频层、标注层静止;暂停时贴 bitmap 缓存。真·单栈单坐标单 transform。
- **A2**(降级):透明 Konva Stage 盖在原生 `<video>` 上,只画标注,不重绘视频像素。perf 稳,但**没真正统一**(两个 transform 要同步,正是要消灭的漂移源)。

核心未知数:A1 在播放态逐帧把一帧像素灌进 `Konva.Image` 并 `batchDraw`,在高分辨率/高帧率下扛不扛得住。本 spike 量化这个开销,作为 A1 是否成立的**闸门**。

## 2. 测量方法学

### 2.1 为什么用合成 canvas 帧源,而不是真实 `<video>`

帧源是一个离屏 `<canvas>`,每帧重画一个会动的图案(移动渐变 + 平移噪声块),作为
`Konva.Image` 的 `image` source。**刻意不依赖任何视频资产。**

理由 —— 隔离出决策 A 真正关心的差量:

- A1 与 A2 的**共同成本**是「视频解码出一帧像素」:A1 里 `<video>`/`createImageBitmap`
  要解码,A2 里浏览器合成 `<video>` 元素也要解码。这部分两方案都有,**可以比掉**,
  不是 A1 vs A2 的决策变量。
- A1 相对 A2 的**额外成本**才是决策点:把这一帧像素「上传为 Konva.Image 纹理 +
  整层 `batchDraw` 合成」。这正是合成 canvas 帧源隔离出来的东西 —— 帧源每帧产出
  全新像素(渐变相位漂移 + 噪声平移,避免被 GPU 当静态纹理跳过),逼出
  「一帧像素 → Konva.Image → batchDraw」的最坏情况合成开销。

因此合成源测得的「单帧 batchDraw 耗时」≈ A1 在 A2 之上多付的成本。真实视频的解码
开销另算(且两方案共担),不污染本 spike 的对照结论。**局限**:合成源不含真实视频
的色彩/运动复杂度对 GPU 纹理上传的细微影响,但纹理上传量由分辨率决定(已作为矩阵
维度覆盖),量级可代表。

### 2.2 分层 vs 单层混画的对照设计

这是 A1 成败的**关键变量**(计划 §3.2:「不能只测单层」):

- **分层**:视频帧在独立 `<Layer>`(独立 canvas),标注 N 个 `Rect` 在另一个
  `<Layer>`。动画循环里**只** `videoLayer.batchDraw()`,标注层静止不重绘。这是 A1
  的推荐形态 —— 播放时数百个标注形状不参与重绘。
- **单层混画**:视频帧 + 标注 `Rect` 同一个 `<Layer>`,每帧整层 `batchDraw()`。
  作为对照基线,量化「不分层」时标注形状混入重绘循环的代价。

二者差量 = 分层带来的收益。若分层下达标而单层不达标,印证「A1 + 分层」的必要性。

### 2.3 采样口径

每帧动画循环里:重画合成帧源 → `img.image(canvas)`(让 Konva 重读纹理)→
**同步 `layer.draw()`**,用 `performance.now()` 夹住 `draw()` 这一段。

> **测量有效性修正(采集时发现并修复)**:最初用 `layer.batchDraw()` 计时,测得各
> 配置一律 ≈ 0.02ms 且与分辨率无关 —— 这是**无效**的:`batchDraw()` 把实际光栅化
> 合批到下一 rAF 且合并多次调用,同步计时只量到调度调用,量不到真实整帧合成开销。
> 改用同步 `layer.draw()` 后才量到真实成本(Konva.Image 的 `drawImage` 全帧纹理
> 上传 + 缩放 + 标注绘制),正是「播放时每帧重绘视频层」的单帧成本。生产里仍会用
> batchDraw(合批是好事),但要**度量**单帧成本必须用同步 draw。
>
> **背景标签页 rAF 暂停**:Chrome 完全暂停隐藏标签页的 rAF。采集时若标签页被切到
> 后台,该格只采到极少样本(达成帧率/掉帧率失真)。本批数据所有格均在前台、
> 采到 ~138(30fps×5s)/ ~274(60fps×5s)帧后冻结,样本充足。

- **单帧合成(draw)耗时**:`performance.now()` 前后差。统计最近 180 帧样本的
  **均值 / p95 / max**(ms)。这是决策判据的主指标。
- **达成帧率**:采样帧数 / 运行时长(fps)。反映在目标帧率下实际能跑多快。
- **掉帧率**:实际帧间隔 > 1.5× 目标间隔时记为掉帧,掉帧数 /(掉帧数 + 达成帧数)。

帧率节流到目标值(30/60),避免 rAF 自由跑到刷新率上限干扰对照。统计实时挂到
`window.__spikeStats`(便于自动化/截图取数);也支持「自动采样 X 秒后冻结」模式,
跑完定格结果便于截图。

### 2.4 测量矩阵维度

`{720p, 1080p, 4K} × {30, 60fps} × {分层, 单层} × {0 框, 20 框}`。

采集建议:每格用「自动采样 10s」跑,等数字稳定后读 `window.__spikeStats` 或截图。
同一台机器、同一浏览器、其它标签页关闭、接电源(笔记本)以减小抖动。建议记录采集
环境(机型 / CPU·GPU / 浏览器版本 / 显示器刷新率 / devicePixelRatio)。

## 4. 结论判据(出自计划 §3.2 / epic §2 决策 A)

- **A1 通过(主路径成立)**:**分层下** 1080p@30(标注主力场景)视频层单帧
  batchDraw **< ~8ms** 且无明显掉帧 → A1 + 分层成立,按 A1 推进 v0.16.1+。
- **4K@60 仅作上限参考**:不作硬性达标线。可结合实际使用模式放宽 ——
  「暂停态走 bitmap 缓存、不进重绘循环;播放态才逐帧重绘」(精修标注都在暂停态,
  逐帧重绘只发生在播放观看时,不伤精修体验)。
- **分层 vs 单层对照预期**:分层应显著优于单层(标注层静止,不参与每帧合成);
  20 框场景下差距应更明显。若分层相对单层无明显收益,需复核分层是否真生效
  (动画循环是否只重绘了 videoLayer)。
- **降级到 A2 的触发条件**:仅当**分层都救不回**(分层下 1080p@30 仍 ≥ 8ms 或明显
  掉帧,且暂停态缓存策略也无法掩盖播放态卡顿)才转 A2。届时把「双 transform 同步
  契约」写成 ADR 里有测试守护的一等不变量(非临时补丁)。

## 5. 结论

**A1(帧合成进 `Konva.Image` + 分层)成立,按 A1 推进 v0.16.1+,无需降级 A2。**

- **门槛格**(分层 1080p@30,标注主力场景):均值 0.13ms、p95 0.20ms、max 0.90ms、
  掉帧 0% —— **比 8ms 闸门快约 40×**,决定性通过。
- **上限参考**(4K@60 + 20 框):分层均值 0.13ms / p95 0.30ms、单层均值 0.23ms /
  p95 0.40ms,均远低于 8ms。即使 4K@60 这种最坏组合,Konva 单帧合成成本也不构成瓶颈。
  唯一观察到 >1% 掉帧的是 4K@60 0 框分层(4.8%),但其单帧合成仍仅 0.14ms —— 掉帧来自
  rAF 调度 / 显示器节奏,**不是合成成本**;且决策已留「暂停态走 bitmap 缓存、仅播放态
  逐帧重绘」的使用模式兜底,精修体验不受影响。
- **关键洞察**:单帧合成成本由**目标**舞台像素绑定(Konva.Image 绘进 ~960×540),与源
  分辨率几乎无关;4K 的重头是 `<video>` 解码,A1/A2 共担、已在本 spike 比掉。所以
  「视频帧进 Konva 逐帧重绘」这一 A1 相对 A2 的**增量**成本是亚毫秒级,A1 的「单栈」
  收益没有被 perf 成本抵消。
- **测量教训**:必须用同步 `layer.draw()` 度量单帧成本;`batchDraw()` 合批异步,同步
  计时测不到真实开销(见 §2.3)。此修正已落进 spike 组件。
