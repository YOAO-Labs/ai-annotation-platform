# Plan Draft · AI 能力深化后的文档分层与治理

> Status: research-draft; initial documentation layering is implemented. Remaining governance decisions are unscheduled and require the backlog promotion gate.

## 背景

平台的 AI 能力已经从“单次调用模型得到一个框”扩展为能力发现、模型路由、多阶段编排、异步任务、候选审阅、多目标视频追踪、GPU / 权重部署与失败恢复。继续只在单个用户页面或协议页面追加段落，会出现三类问题：

1. 用户流程、开发原理、接口字段和运维参数混在一起，读者难以判断从哪里开始。
2. 同一事实被复制到多页，代码变化后只改了一处，当前状态发生漂移。
3. PR 只检查“有没有文档”，没有检查“该变化应该落在哪一层、哪一层是真值”。

本计划的目标不是让所有文档更长，而是让每类知识只有一个主归属，其它页面通过摘要和链接建立路径。

## 目标

- 为用户、开发者、API 使用者和运维人员建立稳定入口。
- 在用户指南中建立独立的 AI 导航分组，让用户既能按产品界面查找，也能按 AI 任务查找。
- 给 AI 功能定义最小完整文档包，使能力、数据生命周期、审阅和部署同步演进。
- 明确手写文档、生成文档、ADR、计划和 Changelog 的边界。
- 把文档影响检查变成可执行的 PR 规则和 CI 提示。
- 保持正式文档描述系统当前状态，不把版本流水账写进用户可见页面。

## 非目标

- 不重写全部历史文档。
- 不为了导航整齐而立即搬动所有现有 AI 页面或改变稳定 URL。
- 不把 `docs/plans/` 变成长期知识库。
- 不在多层复制完整字段表、环境变量表或 OpenAPI schema。
- 不要求每个内部重构都增加用户文档。
- 不以文档数量或字数作为完成标准。

## 分层模型

| 层         | 回答的问题                                             | 主要目录                                                          | 真值边界                                                            |
| ---------- | ------------------------------------------------------ | ----------------------------------------------------------------- | ------------------------------------------------------------------- |
| 用户任务层 | 我怎样完成一个任务，结果处于什么状态，失败后怎么恢复？ | `docs-site/user-guide/`；AI 聚合入口为 `docs-site/user-guide/ai/` | 产品当前交互和用户可见语义；AI 分组负责导航，不复制各业务目录的正文 |
| 开发概念层 | 为什么这样设计，数据由谁拥有，状态如何流转？           | `docs-site/dev/concepts/`                                         | 架构模型、模块边界和不变量                                          |
| 开发操作层 | 我怎样扩展、调试或验证这项能力？                       | `docs-site/dev/how-to/`、`tutorials/`、`troubleshooting/`         | 可执行开发流程                                                      |
| 契约参考层 | 精确的字段、状态、事件和能力词表是什么？               | `docs-site/dev/reference/`、`docs-site/api/`                      | 协议与生成契约；字段表不在概念页复制                                |
| 运维层     | 如何部署、升级、观测、回滚和处理故障？                 | `docs-site/ops/`                                                  | 运行环境、资源和恢复流程                                            |
| 决策层     | 为什么选择这个长期方案？                               | `docs/adr/`                                                       | 已接受的架构决策与替代方案                                          |
| 实施层     | 这次准备做什么、分几步、如何验收？                     | `docs/plans/`                                                     | 临时实施记录；完成后必须链接正式文档                                |
| 变化层     | 这次发布对使用者有什么变化？                           | `CHANGELOG.md`                                                    | 版本差异，不承担当前手册职责                                        |

### 链接规则

- 原有工作台、项目、数据集和平台管理页面可以用一至三句话说明 AI 能力在当前场景中的作用，但必须链接到对应的用户任务详页。
- AI landing page 和侧边栏分组可以重复出现同一个导航链接，但不能复制详页正文；一个用户可见行为只指定一个 canonical page。
- 用户任务详页完整说明操作、结果去向和失败恢复；详细状态机再链接到开发概念或 API 指南，不能要求普通用户先读开发文档才能完成任务。
- 开发概念只列关键字段；完整 schema 链接到 reference / OpenAPI。
- 运维文档引用环境变量生成页，不复制全部默认值表。
- Changelog 链接正式文档；正式文档不反向写“某版本新增”。
- Plan 完成后增加 `Outcome`，列出正式知识落点；未落正式文档的知识不算沉淀完成。

## 用户指南的 AI 专题分组

### 决策

建立独立的 **“AI 辅助标注”** 侧边栏分组，并新增 `docs-site/user-guide/ai/index.md` 作为用户侧 AI landing page。该分组按用户任务聚合详细页面，解决 AI 功能散落在“图片标注 / 视频标注 / 项目管理 / 数据集 / 平台管理”下、入口页通常只写一行的问题。

信息架构分组不等于统一搬目录：

- 已经成熟的详页继续保留在最符合产品界面的目录，例如图片交互 AI 仍归 `workbench/`，批量预标仍归 `projects/`，外部预测仍归 `datasets/`。
- AI 侧边栏分组和 landing page 直接链接这些 canonical pages；同一页面可以同时出现在原业务分组和 AI 分组中。
- 只有跨越多个产品界面、没有自然业务归属的用户知识，才新建在 `user-guide/ai/` 下。
- 第一阶段不移动现有页面；如后续确需改路径，必须在同一变更中提供旧链接兼容、全仓链接替换和死链接验证。

### 目标导航结构

`/user-guide/ai/` 按“我现在要做什么”组织，不按模型名称或后端实现组织：

| 图片交互式 AI      | `user-guide/workbench/sam-tool.md`                                                                      | 标注员                 | 用点、框、示例或文本完成当前图片的辅助标注           |
| 批量与多阶段预标   | `user-guide/projects/ai-preannotate.md`                                                                 | 项目管理员             | 批量运行、编排阶段、查看进度并接管结果               |
| 视频 AI 追踪       | `user-guide/workbench/video-propagate.md`                                                               | 标注员                 | 选模型、给种子、纠偏并接受或丢弃候选                 |
| 外部预测与候选     | `user-guide/datasets/prediction-import-export.md`                                                       | 项目管理员             | 导入、替换、清理和导出外部模型预测                   |

| 模型能力与运行状态 | `user-guide/superadmin/model-market.md`                                                                 | 项目管理员、超级管理员 | 查模型能力；按权限查看注册与运行时状态               |

landing page 只承担路线选择，不再写一套缩略版手册。建议包含：

1. 按角色入口：标注员、项目管理员、超级管理员。
2. 按任务入口：当前题交互、批量预标、视频追踪、外部预测、模型配置、失败恢复。
3. 一张最小结果流说明：模型输出先成为候选，何时接受后变成正式标注；不同功能存在例外时直接链接详页。
4. 前置条件提示：项目工具单位、交互式 AI 开关、已启用 backend、角色权限。
5. “功能不可用时先查什么”的短路径，不复制完整 FAQ 或 runbook。

### 原业务页面如何保留简写

原业务页面仍需让用户在当前上下文发现 AI，但摘要统一采用“作用 + 边界 + 明确链接”的结构：

> 工作台支持用点、框和示例生成当前图片的 AI 候选；候选不会自动成为正式标注。操作步骤、模型选择和失败处理见 [图片交互式 AI]。

摘要不再展开参数表、状态列表或同一套步骤。若原页面已经是 canonical 详页，则保留完整正文，不为 AI 分组另建镜像页。

### 何时必须新建详页

仅“一句话提及”在功能简单且没有独立操作路径时可以接受。某项 AI 能力只要命中以下任意两项，就必须有独立用户任务页，而不能继续埋在概述段落：

- 有独立入口、前置配置或角色限制；
- 有三个及以上连续操作步骤；
- 存在运行中、待审、失败、取消等状态；
- 会创建、覆盖、清理或正式写入用户数据；
- 存在模型 / backend / 范围等选择分支；
- 失败后需要恢复、重试或人工接管；
- 同一能力在图片、视频、批量或工作台之间表现不同。

详页标题应使用用户任务语言；模型名、接口名和内部模块名只作为正文中的选择项或诊断信息，不能成为一级导航的主要组织方式。

## AI 功能的最小完整文档包

凡是新增或改变 AI 能力、模型、异步状态、候选流或能力路由，至少评估以下六个切面；“不适用”也应在 PR 文档影响检查中明确说明。

### 1. 用户任务

- 入口、前置条件和角色权限。
- 输入提示、模型选择和范围选择。
- 运行中、待审、已接受、已丢弃、失败和取消的用户语义。
- 结果写入时点、撤销边界和失败恢复。
- 常见误解与限制，不暴露无助于操作的内部实现细节。

### 2. 数据生命周期

- 输入数据、临时结果、候选和正式 annotation 的所有权。
- 异步任务状态机、幂等边界和并发控制。
- 前端缓存、刷新恢复和服务端真值。
- 删除、接受、丢弃、重跑对既有数据的影响。

### 3. 能力与路由

- capability vocab、模型变体、设备需求和 backend 声明。
- 项目启用、默认 backend 与按能力路由的优先级。
- 找不到能力、能力快照过期和 fallback 的明确行为。

### 4. 精确契约

- API request / response、错误码和权限范围。
- WebSocket 事件与 REST 状态的对应关系。
- ML Backend `/setup`、`/predict`、`/health` 的字段来源。
- 生成代码和 OpenAPI snapshot 的同步命令。

### 5. 部署与观测

- CPU / GPU、显存、权重、许可证、缓存和存储要求。
- Compose / production 环境变量是否真正传入目标进程。
- 队列、worker、超时、重试、指标、日志和 runbook。
- 数据库迁移、向前升级、备份和不可盲目降级的字段。

### 6. 安全与审计

- role 门与具体 project / task 资源范围必须分别说明。
- 创建者、项目 owner、审核员和超级管理员的动作边界。
- 接受、丢弃、取消、模型管理等关键动作的审计事件。
- 跨项目 IDOR、未接受候选泄露和 presigned URL 等风险。

## 文档影响决策表

| 代码变化                                | 必查文档                                               | 通常不需要                      |
| --------------------------------------- | ------------------------------------------------------ | ------------------------------- |
| 新增用户入口或改变操作结果              | 用户指南、FAQ、图片清单、Changelog                     | ADR，除非改变长期架构           |
| 改变 AI 数据写入时点或状态机            | 用户指南、开发概念、API / WS、runbook、Changelog       | 单纯截图页不能替代概念页        |
| 新增 / 修改 API 字段或错误码            | OpenAPI、API 指南、schema boundary                     | 在多个概念页复制完整 schema     |
| 新增 backend capability / model variant | 用户模型选择、ML 协议、能力词表、部署资源              | 只改模型市场页面                |
| 新增环境变量或 Compose 透传             | `.env.example`、生成 env reference、部署 / 升级文档    | 手改生成的 env 表               |
| 权限范围变化                            | 用户可见性说明、开发权限概念、API 指南、安全文档、测试 | 仅写 `require_roles` 即视为完成 |
| 纯内部重构且行为和契约不变              | 必要时开发 how-to                                      | 用户指南、Changelog             |

## 页面模板

### 用户任务页

1. 什么时候使用。
2. 前置条件。
3. 完成任务的主路径。
4. 运行状态与结果去向。
5. 失败恢复和限制。
6. 相关任务链接。

### 开发概念页

1. 问题与边界。
2. 端到端数据流。
3. 不变量和状态机。
4. 模块职责。
5. 权限、并发和失败语义。
6. 契约与 runbook 链接。

### API 指南

1. 场景与鉴权。
2. 最小请求 / 响应示例。
3. 状态、错误码、幂等和分页。
4. 资源范围与数据副作用。
5. OpenAPI schema 链接。

### Runbook

1. 症状。
2. 安全检查与数据保护。
3. 分层诊断顺序。
4. 修复 / 恢复命令。
5. 成功判据和升级条件。

## 实施阶段

### 阶段 A：盘点与归属

- 以 AI 预标、图片交互 AI、视频追踪、模型市场四条链路做样本盘点。
- 逐项标记“已有详页 / 只有摘要 / 完全缺失”，并用“何时必须新建详页”的阈值判断是否拆页。
- 标记重复字段表、历史版本叙述、孤立页面、缺失入口和没有目标链接的一行式介绍。
- 为每个核心事实指定一个 canonical page。
- 输出“保留 / 补写 / 拆分 / 合并 / 移动 / 生成 / 归档”清单，不立即批量重写。

### 阶段 B：入口与模板

- 新建 `user-guide/ai/index.md`，在用户指南侧边栏增加独立的“AI 辅助标注”分组；第一阶段聚合现有 canonical pages，不移动稳定 URL。
- 把原业务概述页中只有一行的 AI 介绍改为“作用 + 边界 + 详页链接”；已有详页不创建镜像副本。
- 在开发概念、API 和运维首页增加“按任务进入”的导航。
- 为上面四类页面增加轻量模板和示例。
- 可选 frontmatter：`audience`、`task`、`source_of_truth`；高变化页沿用现有的 `last_reviewed` 作为唯一人工复核日期，不另引入 `last_verified`。这些元数据不在渲染正文展示版本流水。
- 先以视频 AI 追踪验证“原业务入口摘要 → AI 分组 → 用户详页 → 开发概念 / 契约 / runbook”的完整链接链，再补齐其它 AI 能力。

### 阶段 C：PR 文档影响门

- 在 PR 模板增加 AI 文档包六切面检查，允许选择“不适用 + 原因”。
- 扩展 docs impact 脚本：按 API、capability vocab、env、migration、Workbench AI 入口等路径提示必查目录。
- 保持提示型 gate 起步；稳定后只把生成物漂移、死链接和明确缺失的必需参考设为阻断。
- 导航覆盖、站内 Markdown 死链、用户指南图片 manifest 与孤儿图片先作为独立检查项运行；导航例外必须记录页面和原因，不能静默跳过。
- 检查 items、counts、权限说明和测试是否使用同一资源范围，避免只改 UI 文案。

### 阶段 D：生成与去重

- OpenAPI 路由、环境变量、快捷键、设置项继续由生成器维护。
- capability vocab 增加可链接的生成参考页，减少协议页手抄枚举。
- 建立 canonical-link 检查：同一字段表或用户任务只允许一个主页面，其它页面保留摘要和链接；允许侧边栏重复链接，不允许正文镜像。
- 为 docs 检查输出导航未覆盖页、孤儿图片和 stale generated artifact 报告；生成目录与历史镜像不纳入普通页面覆盖统计。

### 阶段 E：持续验证

- 每个较大的 AI release slice 至少做一次“用户任务 → 概念 → 契约 → runbook”链接走查。
- 用真实无 GPU / GPU、普通用户 / 项目 owner 两类环境验证文档分支。
- 每季度抽查高变化页的 `last_reviewed`，过期只提示，不虚构自动正确性。

## 验收标准

- 新成员能从一个入口找到完成 AI 任务、理解数据去向、查看精确 API 和排查运行故障的路径。
- 用户指南侧边栏存在独立的“AI 辅助标注”分组；landing page 能按角色和任务导向所有已支持的 AI 用户流程。
- 原业务概述页中的 AI 摘要都链接到明确的用户详页；每个详页也能从 AI 分组和其自然业务上下文到达。
- AI 导航允许多处指向同一页，但同一任务不存在两份需要同步维护的详细正文。
- 任一 AI 状态、字段或环境变量只有一个明确主真值页面。
- PR 改变 AI 状态机、API、capability 或 env 时，docs impact 能提示正确目录。
- `pnpm docs:build`、OpenAPI 检查、env 生成、死链接和文档版本样式检查通过。
- 正式文档不出现用户可见的版本流水；历史决策留在 ADR / Plan / Changelog。
- Plan 完成时增加 `Outcome`，列出迁移页面、脚本、CI gate 和未尽事项。
