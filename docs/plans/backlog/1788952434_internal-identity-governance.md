## 工作包 A：接入公司的统一身份

### 触发条件

- 公司已经有可用于本系统的身份提供方，IT 能提供协议、测试租户/客户端及稳定用户标识；或者明确要求公司账号开通、调岗、离职联动。
- 产品负责人确认本地登录保留范围、账号绑定规则、哪些人员可自动入驻；IT 确认身份服务故障时的运行方式。

### 推荐方向

1. 优先接公司现有 OIDC 身份提供方；只有公司实际提供 SAML 时才选择相应适配，不在应用内自行实现 LDAP 密码校验。
2. 使用成熟协议库或身份平台的标准能力，保留受控的本地管理员恢复入口，避免身份提供方故障时无人能管理平台。
3. 外部身份以 issuer 和 subject 等稳定组合标识关联本地 User；不只按可变邮箱自动合并账号，也不因外部属性缺失提升角色。
4. 首次绑定现有账号需要已验证的绑定流程；未知成员默认进入受限状态，项目角色和工作分配仍通过应用现有管理流程授予。
5. 部门目录先同步成员与组，不把“属于某部门”自动等同于某项目管理权限。同步结果预览新增、变更、停用及冲突，不因一次目录请求失败批量停用成员。
6. 离职事件使本地账号和会话停止继续使用；业务任务交接使用当时已有的人员交接能力，不把删除标注数据作为目录同步动作。

```text
浏览器 → 平台登录入口 → 公司身份提供方
                        ↓ 验证回调与稳定身份
                    本地身份关联 → User → 现有项目权限
目录同步 → 变更预览 / 冲突 → 明确的成员状态变更
```

接口与数据方向：新增独立的身份登录/回调入口、外部身份关联记录和同步结果记录，保留既有本地登录契约；凭据不经普通系统设置 GET 回传。
所需外部材料由 IT 提供：issuer/metadata 地址用于发现协议端点；client ID 与凭据用于登记平台；回调地址用于限制认证返回；目录读取权限仅在实施部门同步时需要。
没有这些材料时，不预先创建第三方账号或部署新的身份服务。

验收：新用户登录、已有账号绑定、邮箱变更、重名、外部身份撤销、提供方不可用、重复回调和两个身份提供方的同名 subject 均得到正确处理；普通用户不能借同步成为超管。
回退：关闭新登录入口，保留身份映射和已存在用户；已同步的账号停用或权限变化不能靠关闭入口自动撤销，按变更记录处理。

设计参考：[Keycloak 官方管理文档](https://www.keycloak.org/docs/latest/server_admin/) 覆盖 OIDC/SAML、LDAP/AD 对接、用户会话与身份联合；这里只借用成熟机制，不将部署 Keycloak 设为前置条件。

## 工作包 B：跨项目角色与项目副管理员

### 触发条件

实际出现同一人在 A 项目标注、B 项目审核，或项目 owner 需要稳定委派副管理员的业务需求，且现有全局角色无法准确表达。

### 推荐方向

- 平台权限和项目内职责分开求值；保留现有五种内置角色的兼容行为，不直接引入用户可编程权限规则或任意权限拼装器。
- 使用现有 ProjectMember 作为项目职责归属，平台管理能力由平台角色控制；项目 owner、副管理员、标注、审核和只读边界在同一授权服务求值。
- 首先固化每项操作的权限矩阵和现有用户迁移映射，再修改请求鉴权、列表可见性、派发候选、审核、导出及前端动作显示。
- 历史记录按原有实际权限迁移，不能把旧 viewer 或普通成员升级为项目管理员；角色变更前显示未完成工作的影响。
- API Key 和后台任务也使用新的实际项目权限，不能仅改变前端角色标签。

接口与数据方向：增量扩展项目成员角色修改接口和 effective permissions 响应；ProjectMember 保持项目身份 owner，避免引入第二张重复项目角色表。
涉及 `deps.py`、批次/任务权限服务、项目成员和派发接口、用户角色变更、Web 权限 hooks 与矩阵、SDK 所依赖的 API 契约。

验收矩阵至少包括 A 项目标注/B 项目审核、A 副管理员/B 普通成员、owner 转交、角色降级后的未完成任务、直接 API/导出和后台作业。
迁移先做加法和兼容读取；旧应用无法表达新角色时，不承诺任意代码回滚仍保留相同行为。退回旧实现前先显式收敛新角色分配，不能删库恢复。

## 工作包 C：自动化凭据的用途、维护人与到期提醒

### 触发条件

至少有一条导入、预标或导出自动化成为固定生产流程，或人员离职已经影响过无人知晓的个人 API Key。

### 最小交付与扩展

1. 第一小包仅增强已有个人 API Key：记录用途与业务维护人，在管理范围内展示近期使用、到期时间，增加到期前 7 天和 1 天的站内提醒。无到期时间则明确显示长期有效。
2. 提醒复用现有通知服务，按 key、到期时间和提醒窗口去重；轮换或修改到期时间后按新状态计算，不把旧提醒当成凭据失效依据。
3. 人员停用前展示相关集成及维护人，指引换发和更新脚本；旧明文密钥不转交给接收人。
4. 只有固定自动化确实需要脱离个人任职关系时，再交付团队服务账号：明确业务 owner、项目范围、scope 和停用策略，禁止交互式人员登录。
5. 现有 API Key scope 覆盖并非所有端点；团队账号上线前必须核对实际自动化调用的完整 API 路径，不能把只勾选 read 的 key 宣传成全平台只读。

接口与数据方向：给已有 key 增加用途/维护人元数据和通知去重依据；管理员代管能力需新增服务端授权，不依靠前端按钮。
验收：到期提醒不重复、不含密钥；轮换后旧 key 失效；停用维护人时系统能找到受影响脚本；服务账号只访问被授权项目和操作。
回退：提醒和展示可关闭，仍保持既有 key 生命周期；已经撤销的 key 不能通过代码回退复活，脚本需使用新凭据。

## 工作包 D：超管高级运行策略

### 触发条件

内部运营已反复需要调整模型请求/探活超时，或逐帧预标数量与结果上限；能够用代表性的模型、媒体和作业验证调参结果。
第二批六项业务配置可独立交付，不等待本包；本包也可基于当前 SystemSettingsService 直接实现，不要求第二批 UI 改造先落地。

### 候选配置与完整合同

| 配置 / 当前代码默认                                                                    | 本包计划                                                                                                       | 必须一起处理的消费者                                                                                                                                          |
| -------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ML_PREDICT_TIMEOUT` / `ml_predict_timeout`：100 秒                                    | 以一次请求或作业的不可变策略快照控制后续 HTTP 操作；说明是 HTTP 超时，不是整项作业总时长；运行中操作不追溯修改 | `services/ml_client.py`、`api/v1/admin_ml_integrations.py`、`services/secondary_inference.py`、`services/gpu_arbitration/dispatch.py` 及调用它们的 API/worker |
| `ML_HEALTH_TIMEOUT` / `ml_health_timeout`：10 秒                                       | 一轮探测使用同一策略快照；新探测生效，不让旧探测覆盖新状态；在后台探活总时间预算内校验                         | `services/ml_client.py`、`services/capability_instances.py`、`services/ml_backend_env_sync.py`、`api/v1/admin_ml_integrations.py`、`workers/ml_health.py`     |
| `FRAME_PREANNOTATE_MAX_FRAMES` / `frame_preannotate_max_frames`：900                   | API 受理时固定预算，提交前显示计划处理帧范围；旧任务与重试不悄悄改变总帧数                                     | `workers/frame_preannotate.py` 的规划、拆段、抽帧与进度分母                                                                                                   |
| `FRAME_PREANNOTATE_MAX_BOXES_PER_FRAME` / `frame_preannotate_max_boxes_per_frame`：100 | 与帧上限一起传入所有子任务；显示因上限跳过的结果数量，不能伪装为模型只检出少量对象                             | `workers/frame_preannotate.py` 子任务与结果转换路径                                                                                                           |

配置默认取自 `apps/api/app/config.py`，不是对生产有效值的断言。第一轮可写范围以现有部署基线和代码预算验证为界；超过现有容量/时间预算时先验证并扩展整个预算，不只放宽表单数值。

### 为什么单独规划

- `gpu_arbitration/dispatch.py` 的 runtime 硬期限由推理 timeout 加宽限计算，还需要给恢复协调保留窗口。必须与 HTTP 请求使用同一快照，否则请求仍在执行而授权已经过期。
- 探活任务现有总预算、API 代理超时和任务 soft/hard limit 不会随 DB 设置自动变化；校验不通过时说明哪个预算受限，不能通过界面自动改部署。
- 当前多个 ML 方法会新建 HTTP client；问题主要是读取点分散和期限耦合，不是已经证实存在常驻 client 缓存失效。
- 启动同步使用当前数据库可达情况下的一致策略；既有纯部署启动路径保留环境回退合同，不能声称所有启动行为都能即时热更新。
- 新增白名单、schema、客户端参数、调度上下文及错误信息必须同批完成。逐帧预标在 API 受理时固定帧数/框数预算及版本，Celery 规划与所有子任务只消费该快照；提交前预览的版本若已变化，重新展示范围并确认。历史无快照任务首次执行前固定并持久化一次，不能每次重试重新读取全局值。运行中和已排队任务持有快照，重试保持原策略；用户明确重新创建任务后才使用新策略。

```text
超管高级设置 → 有效策略快照
                  ├→ API / worker → ML HTTP client
                  ├→ GPU dispatch → 硬期限与恢复窗口
                  └→ 逐帧编排 → 子任务参数 / 结果计数
```

沿用第二批提出的配置来源、单位、审计、恢复部署默认及跨进程传播说明；若本包先实现，独立补齐其所需的最小设置字段和消费者，不为等待通用页面而停工。
不在本包增加 GPU 模式开关、队列名、容器重启、模型存储连接或自动清理期限。

验收：两种 timeout 在实际请求中使用正确值；同一 GPU 操作的请求期限和授权窗口一致；运行中作业与重试不漂移；逐帧子任务使用同一帧/框限制且结果解释准确；无效预算在派发前拒绝。
回退：恢复部署默认只影响后续策略快照；已运行作业按旧快照完成或通过已有取消入口处理，不能将界面调参视为强制终止。

## 成本与最脆弱假设

统一身份和权限模型属于较大改造，外部系统联调成本明显；密钥用途/提醒可以小包先交付；高级运行策略必须覆盖跨进程与调度合同，不能按几个表单字段估算。
本计划假设仍主要面向内部团队。若开始服务互不信任的外部客户，需要重新规划租户隔离与管理边界，不能用现有 Organization 模型或用户组名称宣称已经具备完整多租户能力。
