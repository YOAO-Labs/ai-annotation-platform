# Ordinary PR CI in under ten minutes

Give authors a verdict on each ordinary push in **less than 600 seconds**, including queues. Let that verdict admit a PR to the merge queue, never straight into `dev`. Keep the full product suite on the candidate that actually merges. Do not delete a test to make a lane fit.

Status: design for review, not a change to Actions or branch protection. The reference is [PR #195 at `1c855e083`](https://github.com/YOAO-Labs/YOAO/tree/1c855e083cfc2fd7a1e742e28233ce5f7301c797). Rebase the plan on the CI that lands. ## Which PR qualifies

An ordinary change is allowlisted passive documentation, or a change confined to one reviewed product area with known consumers and a behavior test for that change. Accompanying prose does not turn a one-area patch into a cross-area patch. The planner decides **before** jobs run. A label, a small diff, a green retry, or a slow result cannot change the classification.

Start with documentation, a leaf web view, and an isolated backend feature with a known public entry point. For the #145 pilot, demonstrate that the selected component tests fail if the visible framework version disappears. A fixture containing a version string is not that proof. Keep full Vitest if a standalone job without the browser/build dependency fits on cold runners. Otherwise pass its reviewed owner files. For an API pilot, require one mapped behavior and its owner files, plus a real HTTP/database test when the change touches persistence. Pass explicit pytest file paths or node IDs **before collection** rather than discovering everything and using `-k`. Changed tests run themselves as well. An owner with no matching test stays broad until it has one.

Default to broad PR checks for auth and permissions, transaction boundaries, migrations, OpenAPI and shared SDKs, lockfiles, shared fixtures, workflow/selector changes, and changed public contracts. Both sides of a rename count. Missing base, unknown owner, unsupported diff, or multiple product owners cannot produce a fast green. [#99](https://github.com/YOAO-Labs/YOAO/pull/99/files) changes an authorization path, [#127](https://github.com/YOAO-Labs/YOAO/pull/127/files) a shared video fixture, and [#195](https://github.com/YOAO-Labs/YOAO/pull/195/files) the gate itself. All stay broad. [This three-file documentation commit](https://github.com/YOAO-Labs/YOAO/commit/dd0028f6b569862ea12c1984e0aca70a1915df57) needs docs checks, not PostgreSQL or Chromium. Executable docs and site configuration have their own owners.

## Latency budget

| When             | Required work                                                                                                                                                                                          | Budget or objective                                     |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------- |
| Local pre-commit | Staged formatting, conflict markers, cheap syntax and naming checks. Keep slow generation and full typechecks in CI or explicit pre-push commands.                                                     | 5–30 s; outside the PR clock                            |
| PR fast checks   | Changed-file checks, affected contract or type checks, validated test plan. Docs-only also builds and checks the affected documentation.                                                               | 1–3 min                                                 |
| PR unit tests    | Run the selected owner files; no databases or browsers for pure logic.                                                                                                                                 | 3–5 min                                                 |
| PR integration   | Exercise the changed seam. Use disposable PostgreSQL for transactions or one Chromium flow for behavior that only a browser can verify. No site-wide E2E for a table label.                            | ≤6:30 including cold setup and any build dependency     |
| Before merge     | Full API, web, SDK, owner contracts, migrations, worktree and E2E checks on the merge group SHA. Keep current full functional and specialty coverage here until evidence supports a separate decision. | 10–20 min is a future objective, not a measured promise |
| Nightly          | Reuse full suites. Run additional browser combinations, long video, stress, soak and recovery. Assign failures to owners with the first bad revision and receipts.                                     | 30–60 min is a future objective                         |

Run the PR checks **in parallel** after classification. Budget 90 s for all runner waits on the critical path, 20 s for planning, 390 s for the longest execution chain, and 20 s for the final verdict. That gives **8:40** and leaves 80 s before the hard limit. Dependency installs, checkout, migrations where required, report upload, and the build before a browser test count. Supersede stale PR runs only. Limit concurrency of full builds to avoid starving PRs. If hosted queues alone consume the margin, reserve isolated runner capacity for PRs or report the miss. Never turn timeout into success.

For backend pruning, rank cases by setup, test and teardown time on the critical shard. Check past failures and their causes, not just names. Drop a private call assertion or a repeated input only after a stronger test passes on the same boundary. Remove parameters that always skip separately from tests that saved runtime. Test real HTTP responses, permission denial, committed data and rollback. Expensive fixture setup is a reason to isolate or reuse the fixture, not to throw away the behavior it protects.

## Deliveries and gates

### A. Measure before changing requirements

- [ ] Start from the landed baseline. Limit edits to `ci.yml`, the existing planner/summary tooling, and developer testing docs. Keep the current gates.
- [ ] Record event, base/head/tested SHAs, attempt, classification/reason, expected jobs and actual nonempty reports. Record timestamps for queues, service setup, tests and the final check. Use the server-side PR opened/synchronize event as time zero. Historical Actions `created_at` is a proxy that omits pre-creation delay. Do not substitute author/committer time.
- [ ] Verify a real docs PR, a leaf web PR and an API change. Reconcile expected vs actual check identities and reconstruct end-to-end time from their GitHub receipts. Track unclassified changes and the share of independently reviewed ordinary PRs separately.

### B. Establish the merge gate before removing any PR job

- [ ] Start independently from the same baseline. Edit `ci.yml`, `backend-test.yml`, `e2e-run.yml` and `scripts/plan-e2e-suites.mjs` only as required. Today CI listens to `pull_request`, `push: dev` and `workflow_dispatch`. Neither workflow nor planner currently handles `merge_group`.
- [ ] Add `merge_group: checks_requested` to the workflow and support full scope in both the E2E and ML CPU planner paths. Test the synthetic merge commit for PRs and the actual group `head_sha` for queue builds. Publish one stable, unfiltered check (`CI verdict`) on both events. Initially require full work on both; merge groups always stay full. `if: always()` only schedules the verdict. Verify checkout, expected suites and actual execution receipts for the same event SHA, run and attempt. A missing or unresolved SHA, failed planner, missing report, unexpected skip, zero executed required tests or cancellation must fail, never return skipped or neutral.
- [ ] In a disposable protected branch, require the queue and the GitHub Actions check, block direct pushes/bypass, and protect changes to workflows and policy by independent review. Verify a passing PR with a deliberately failing group **cannot merge**. Then verify a good group can merge. A changed base or amended PR must produce a new group SHA and require a new verdict. Measure the real group build; keep correctness even if it exceeds 20 min.
- [ ] `dev` had `protected: false`, no effective branch rules and no repository rulesets at design time. A post-merge run or comment is not enforcement. If the queue or admin permission is unavailable, keep full CI on the up-to-date PR and require its trusted full verdict. Do **not** switch to fast-only PR checks. See [GitHub's queue contract](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue).

### C. Run owner lanes alongside the intact full gate

- [ ] After A and B, extend the existing inventory (`scripts/test-suites.json`) and planner. Give each production path one reviewed owner mapping to existing test commands and expected files. Reuse browser suite IDs rather than keeping two sets of trigger rules. Use the complete `git diff --name-status -z --no-renames` from the event base to the tested SHA so deletions and both sides of renames count. Use trusted base routing for changes to the planner itself. The current owner list is not a transitive dependency graph; do not build one.
- [ ] Wire the lanes in `ci.yml`. Include relevant checks from `docs-validate.yml`; always produce a verdict for docs-only PRs. Reuse named E2E suites/builds only when the whole path fits. No fork code gets deployment credentials or writes to a shared runner environment. Do not use a PR-written manifest as its own proof of completeness.
- [ ] Replay #145, #99, #127, #195, the docs commit, empty diffs, executable docs and a rename out of a shared path. Demonstrate a real broken UI assertion and a real backend regression both fail the intended lane. Compare the fast verdict with the unchanged full run on the same SHA. A missed product regression suspends that routing rule. An old unrelated failure does not count as a routing success or authorize ignoring it.
- [ ] Qualify the shadow lane against the 600-second budget with cold and warm runs and competing PRs. This proves the candidate lane only. Full CI is still required on every PR at this stage.

### D. Enable the hard limit and keep it honest

- [ ] After C, obtain maintainer approval. First prove the full `dev` candidate can pass; the [31 known fixture setup errors](https://github.com/YOAO-Labs/YOAO/issues/199) are not disposable tests. On `dev`, require an up-to-date PR and its full `CI verdict` with no bypass. Enable the mandatory queue using that same check. Prove a failed group blocks admission while the old full PR jobs still run. Only then change what the PR side requires.
- [ ] On protected `dev`, stop starting unrelated full workflows on ordinary pushes. Full CI remains mandatory for every merge group. Verify **30 consecutive ordinary, first-attempt pushes** across docs, web and API, including cold dependencies and overlapping PRs. Every required verdict must arrive in **<600 s**. Only this post-cutover measurement establishes the target.
- [ ] Publish passing and legitimately failing runs separately, p50/p95/max, count of breaches, and the number of broad fallbacks. A missing verdict, infrastructure timeout or unexpected skip is a failed qualification. List superseded heads separately. Do not hide the first attempt with a retry or reclassify slow samples. Publish the number of independently reviewed ordinary changes the pilot failed to admit. One allowlisted file does not qualify the whole repository.
- [ ] Roll back to full PR checks on a false green or broken queue. On a time breach, report it and fix the measured bottleneck. Track queue-to-merge separately so fast PR feedback does not hide slow delivery.
