## 1. 背景

当前阶段化预标注流程刻意保持简单：

- Stage 0 在整图上运行，产出父框。
- 所有下游阶段统一 `parent_stage = 0`（由 `projects.py:1283-1287` 强约束）。
- 多个下游阶段形成单层扇出，例如 `vehicle box → color | vehicle_type | plate OCR`。

这对"双阶段属性富集"够用，但无法表达更深的场景，例如：

```text
detect person → detect hat | detect shoe → classify color
```

是否要做成自由 workflow DAG，本身是一道独立的产品题。本版本给出更窄的答案：

- 内部允许**受限树形结构**，让深一层的流水线能被表达。
- 不引入自由 workflow 画布。
- `/ai-pre` 仍是平台侧的批量编排入口。
- 工作台 AI 面板继续做"当前任务执行 + 候选审核"，不演化成流水线编辑器。

## 2. Goals / Non-Goals

### Goals

1. 表达 depth-3 流水线：一个下游阶段可以消费上一个下游阶段产出的几何。
2. 支持子对象场景，例如 `person → hat/shoe → color`。
3. UI 上把每阶段的"输入来源 / 父类过滤 / 输出形态 / 写回目标"显式化。
4. 现有"两阶段"用户体验零退化（旧 payload 必须继续工作）。
5. 第一版 UI 仍是卡片为主，只在卡片上方加只读流程摘要，**不**做自由画布。
6. 后端校验与 worker 执行模型显式到位，防止"任意图"复杂度悄悄渗入。
7. v0.18.13 的 `pipeline_stages` payload 不动也能通过新校验、跑通新 worker。

### Non-Goals

- 不引入 React Flow / 拖拽式 workflow 编辑器。
- 不支持环、运行时动态分支、跨枝任意合流、用户自定义条件表达式。
- 不抽象成跨图像预标注的通用 workflow 产品。
- 不动工作台 AI 面板的语义。
- 不在没确定写回语义前引入"可独立审核的子物体框"。
- 不实现 Celery chord / 真正的并行图调度——除非串行执行被实测出是瓶颈。
- **不实现"crop 内检测新子物体 + 坐标回映"与"一等模型 I/O 输入契约"**——这两块是几何 depth-3（`person → hat → color`）真正跑起来的前提，但需要新的 ROI 原语与协议字段，整体推到 [0.18.15 计划](./2026-06-25-v0.18.15-model-io-contract-and-crop-remap-draft.md)（见 §6.6 可达边界）。

## 3. 产品决策：受限树形流水线

形式化定义（校验器和 worker 必须按同一份语义实现）：

```text
PipelineGraph G:
  stages: list[Stage]                              # stage.stage 在 0..N-1 连续
  ∃! root ∈ stages   满足 root.parent_stage = None 且 root.stage = 0
  ∀ s ∈ stages, s ≠ root:
    s.parent_stage ∈ {0, .., s.stage - 1}          # 必须指向已存在且更早的阶段
  depth(s) = if s = root then 1 else depth(parent(s)) + 1
  ∀ s : depth(s) ≤ 3
  无环（parent_stage < s.stage 自然保证）
  ∀ child : parent(child).write.target ∈ {"geometry", "intermediate"}   # 父必须产可消费几何
  单父（每阶段恰有一个 parent_stage）
  允许同级兄弟（多个 stage 可共享同一 parent_stage）
```

典型形态：

```text
Stage 1: detect person
  Stage 2a: detect hat from person ROI
    Stage 3a: classify hat color
  Stage 2b: detect shoe from person ROI
    Stage 3b: classify shoe color
```

UI 以分组卡片 + 顶部只读 ASCII 流程条呈现，所有编辑都在阶段卡内完成。

## 4. 场景语义

### 4.1 Person → Hat / Shoe → Color：写回方案决策

候选三种写回模式：

| 模式 | 含义 | 适配场景 |
|---|---|---|
| 写到父框属性 | hat/shoe 的颜色直接成为 person 框上的属性（`hat_color`、`shoe_color`） | 最终标注单元仍是 person |
| 写为子形状 | hat/shoe 是独立可审核的形状，各自有 class 与 attributes | 审核员需要单独修/接受 hat 或 shoe |
| 仅中间几何 | hat/shoe 框只存在于 pipeline 内部，不出现在审核界面 | 标注输出最简，但调试不直观 |

**v0.18.14 决策**：

- 默认写回目标是 **root 框上的扁平 attributes**（祖先就一个：root）。这是在 v0.18.13 `merge_classify_attributes()` 上最小的扩展。
- root 框上的属性键由 worker 拼成 `f"{label}_{key}"`，其中 `label` 是 `PipelineStage` 上新增的可选字段；缺省时回退 `f"s{stage}_{key}"`（例如 `s3_color`）。
- 新增 `write.target = "intermediate"`：阶段只产几何给下游消费，**不**作为最终候选预测落库。
- `write.target_stage` 作为未来扩展点写进 schema（值域规划：`"root" | "parent" | int`）。**本版本只接受 `"root"`**（缺省也按 `"root"` 处理），其他值一律 422。
- "写为子形状"模式刻意延后——它需要单独的审核工作流决策。

### 4.2 双阶段兼容

下列旧 payload 继续工作：

```text
detect vehicle → classify color | vehicle_type
detect object  → box-seg mask
```

它们就是 `parent_stage = 0` 且不设 `write.target_stage` 的 depth-2 树。新 schema 要求 `label`、`input`、`write.target_stage` 全部可选并带向后兼容默认（详见 §6.1）。`test_staged_pipeline_worker.py` 中既有 happy-path 测试不改 payload 就要继续通过。

### 5.1 UI 形态

`ProjectDetailPanel.tsx` 仍作编排容器，把阶段区从"扁平下游列表"升级成小型流水线构建器：

- 子阶段组：消费 root 输出的阶段。

### 5.3 容器改造（`ProjectDetailPanel.tsx`）

把当前的扁平结构：

```ts
// 现状：ProjectDetailPanel.tsx:~289-302
const downstreamIds: string[]   // 子阶段卡 id 的扁平列表
// payload：所有 parent_stage = 0
```

改成：

```ts
// 新结构
type StageNode = {
  id: string
  parentStageNumber: number | null   // 只有 root 是 null
  depth: number                      // 1..3
}
const stagesGraph: StageNode[]
```

组装 `pipeline_stages` 时，按拓扑序遍历 `stagesGraph`，确定地分配 `stage = 0..N-1`，从 `parentStageNumber` 算出 `parent_stage`。当所有子阶段的父都是 root 时，输出的 payload **逐字节**等同于 v0.18.13——这正是兼容性回归测试要锁的点。

### 5.4 防错提示

- `depth == 3` 时禁用"加子阶段"。
- 当前阶段 `write.target = "attributes"` 时禁用"加子阶段"，并 tooltip 说明"父阶段必须产几何"。
- 属性键冲突按"最终写到同一祖先"维度去重（v1 等价于 root），而非扁平兄弟（详见 §6.2）。
- 父阶段 `write.target = "intermediate"` 而其子链最终也没有 candidate 产出时，在子卡上挂 warning chip。
- 运行态统计面板（现按 `stage` 序号扁平展示）改成按 `pipeline.stages[].depth` 缩进的列表，数据源见 §6.4。

### 5.5 模型市场卡片展示修正（独立 PR，不依赖流水线改动）

**(a) 原子 / 内部编排恒显**

**(b) 语义字段骨架统一（空值占位，不再整行消失）**

## 6. 后端 / API 方案

### 6.1 Schema diff —— `PipelineStage`

新增字段（全部可选，默认 `None`，保住 v0.18.13 payload 验证不退化）：

| 字段 | 类型 | 默认 | 用途 |
|---|---|---|---|
| `label` | `str \| None` | `None` | 卡片显示名 + 写回属性键前缀 |
| `input` | `dict \| None` | `None` | `{"mode": "full_image" \| "crop" \| "geometry"}`，显式覆盖；缺省时由 worker 按 `parent.write.target` + 子任务类型推断 |
| `write.target` 增 `"intermediate"` | — | — | 阶段只产几何给下游用，不落库为候选 |
| `write.target_stage` | `Literal["root"] \| None` | `None`（视为 `"root"`） | 未来祖先选择的扩展点；v1 只接受 `"root"` |

**不动**的字段：`stage`、`parent_stage`、`parent_class_filter`、`roi`、`model_id`、`task_type`、`model_variants`、`params`、`class_filter`、`on_failure`。

### 6.2 校验 diff —— `_validate_pipeline_stages`（`projects.py:1264-1321`）

替换原单层块。伪码（落地时写进同一个 validator）：

```python
# 替换 projects.py:1283-1287
known_depth: dict[int, int] = {root.stage: 1}
known_target: dict[int, str] = {root.stage: (root.write or {}).get("target", "geometry")}

for s in sorted(stages, key=lambda x: x.stage):
    if s is root:
        continue
    if s.parent_stage is None:
        raise ValueError(f"stage {s.stage} 必须设置 parent_stage")
    if s.parent_stage not in known_depth:
        raise ValueError(
            f"stage {s.stage} 的 parent_stage={s.parent_stage} 未在前面定义，"
            "受限树形要求父阶段序号严格小于子阶段"
        )
    parent_depth = known_depth[s.parent_stage]
    if parent_depth >= 3:
        raise ValueError(
            f"stage {s.stage} 超过最大深度 3 (parent depth={parent_depth})"
        )
    parent_target = known_target[s.parent_stage]
    if parent_target not in {"geometry", "intermediate"}:
        raise ValueError(
            f"stage {s.stage} 的父阶段 {s.parent_stage} write.target={parent_target}，"
            "不产几何，无法作为父阶段"
        )

    known_depth[s.stage] = parent_depth + 1
    known_target[s.stage] = (s.write or {}).get("target", "attributes")

    # 不支持的 write.target_stage 值早 fail
    ts = (s.write or {}).get("target_stage")
    if ts not in (None, "root"):
        raise ValueError(
            f"stage {s.stage} 的 write.target_stage={ts!r} 暂不支持，本版仅接受 'root'"
        )
```

属性键冲突检查（`projects.py:1306-1320`）改成**按祖先写回目标**维度，不再按扁平兄弟。v1 写回目标恒为 root，落地伪码：

```python
# 伪码
final_keys: dict[str, int] = {}   # 最终键 -> 首个写它的 stage
for s in stages:
    if (s.write or {}).get("target") != "attributes":
        continue
    prefix = s.label or f"s{s.stage}"
    for k in (s.write or {}).get("keys", []) or []:
        final = f"{prefix}_{k}"
        if final in final_keys and on_key_conflict == "reject":
            raise ValueError(
                f"attribute key 冲突: stage {s.stage} 与 stage {final_keys[final]} "
                f"都写 {final} 到 root"
            )
        final_keys.setdefault(final, s.stage)
```

`last_wins` 保留原语义（按拓扑序后写覆盖前写）。

**新增校验（配合 §6.3 的 write.target 路由）**：子 `write.target ∈ {geometry, intermediate}` 会走 geometry-prompt 投递，故子模型必须支持 bbox prompt。校验器在能力目录里查子的 `model_id` 对应能力，`"bbox" not in supported_prompts or is_interactive` 即 422（错误片段 `"产几何但模型不支持 bbox prompt"`）。这条规则把 §6.6 表中 ❌ 的"crop 内检测新子物体"链路（普通检测器作产几何子）挡在校验期，避免运行期才暴雷——它正是 0.18.15 坐标回映落地后才解禁的能力。

### 6.3 Worker 执行 diff（`tasks.py:229-381`）

引入按 `stage` 索引的 `stage_outputs` map，按拓扑序遍历。伪码（替换 `_run_task_pipeline` 内部的 source/downstream 二分逻辑）：

```python

    stage_outputs: dict[int, list[Box]] = {}
    stage_stats: dict[int, dict] = {}
    enriched_keys: set[str] = set()
    topo = sorted(stages, key=lambda s: s.stage)   # parent_stage < stage ⇒ 拓扑成立

    for st in topo:
        if st.parent_stage is None:
            pred = await stage_clients[st.stage].predict(task_url, **stage_contexts[st.stage])
            stage_outputs[st.stage] = pred.boxes
            stage_stats[st.stage] = {"detected": len(pred.boxes)}
            continue

        parent_boxes = stage_outputs[st.parent_stage]      # 新：不再恒为 root 输出
        mode = _resolve_input_mode(st, parent_target=known_target[st.parent_stage])

        if mode == "crop":
            crops = crop_inputs_from_boxes(
                task_url, parent_boxes,
                parent_class_filter=st.parent_class_filter,
                pad=_resolve_pad(st),                     # 按 depth 的默认（§10）
                provenance_chain_root_id_field="provenance_root_box_id",
            )
            child_preds = await stage_clients[st.stage].predict(crops, ...)
            # 写回：v1 一律写到 root。merge_classify_attributes 加入
            # target_boxes（root 框列表）+ provenance chain 参数。
            new_keys = merge_classify_attributes(
                target_boxes=stage_outputs[0],
                crops=crops,
                child_preds=child_preds,
                label=st.label or f"s{st.stage}",
                write_keys=(st.write or {}).get("keys"),
            )
            enriched_keys.update(new_keys)
            # 该阶段自身输出是（可能已富集属性的）parent_boxes，
            # 这样孙子阶段还能看到几何。
            stage_outputs[st.stage] = parent_boxes

        elif mode == "geometry":
            prompts = geometry_prompts_from_boxes(parent_boxes, st.parent_class_filter)
            child_preds = await stage_clients[st.stage].predict(task_url, prompts=prompts)
            new_shapes = collect_geometry_shapes(child_preds)
            stage_outputs[st.stage] = new_shapes

        elif mode == "full_image":
            # 嵌套整图阶段（不用 parent 几何）；预留位
            ...

        stage_stats[st.stage] = {"targeted": ..., "ok": ..., "failed": ..., "skipped_geometry": ...}

    persist_boxes = stage_outputs[0]
    pipeline_extra = _build_pipeline_extra(topo, stage_stats, enriched_keys, known_depth)
    return _to_pred_results(persist_boxes), pipeline_extra, stage_stats
```

具体改动点：

1. **新增** `_resolve_input_mode(stage, parent_target)`：判据从"父产什么"改为"**子写什么**"（`stage.write.target`），把 crop 钉死在「只产属性」，从源头堵住坐标回映缺口（见 §6.6）：
   - `stage.input.mode` 显式给了 → 直接用（人工覆盖）。
   - 否则 `write.target == "attributes"` → `"crop"`：裁 ROI 喂纯分类，下游**只回属性、无坐标**——这是 crop 唯一安全的用法（off-the-shelf classify backend 零改造，`roi.py:1-9` 立项目标）。
   - 否则 `write.target ∈ {"geometry","intermediate"}` → `"geometry"`：geometry-prompt 投递（整图 + 父框归一化列表，下游回**原图坐标**几何）。此分支要求子模型支持 bbox prompt（`supported_prompts` 含 `bbox` 且非交互），否则校验期 422（§6.2）。
   v0.18.13 payload 隐式行为不变：双阶段 classify 子 `write.target=attributes` → crop；box-seg 子 `write.target=geometry` → geometry-prompt。**注意**：旧 `_stage_input_mode`（`tasks.py:186-205`）是按 `supported_prompts` 反推，本次改为按 `write.target` 正推，二者在现有双阶段 payload 上结论一致，但语义更稳——crop 不再可能被误用于产几何的子。
2. **新增** `_resolve_pad(stage)`：返回 `stage.roi.pad`，缺省时取 §10 给的按深度默认（`{1: 0.05, 2: 0.08, 3: 0.12}`）。
3. **`crop_inputs_from_boxes`（`roi.py:68-150`）** 签名保持兼容。它本来就接收任意父框列表，调用方改为传 `stage_outputs[parent_stage]` 而非恒为 root 即可。新增 `min_crop_side_px` 守卫（默认 32）：低于阈值计入 `skipped_geometry`，并按 `on_failure = "keep_parent"` 保留父框。
4. **`merge_classify_attributes`（`roi.py:243-299`）** 新增 `target_boxes` 与 `label` 入参。depth-3 链路下，worker 在 crop 输入元信息里携带 `provenance_root_box_id`，merge 时按 root box id 回查根框，即便直接父是 `intermediate` 也能定位。

### 6.5 最终属性键解析（写回 root）

- 给定 stage `S`（`label = L`，缺省时 `f"s{S.stage}"`）+ `write.keys = [k1, k2]`，写到 root 框上的最终键为 `{L}_{k1}`、`{L}_{k2}`。
- §6.2 的冲突检查作用在"加完前缀的最终键"集合上。
- `on_key_conflict = last_wins` 按拓扑序生效（更深的阶段覆盖更早对同一最终键的写）。

### 6.6 本版 depth-3 的可达边界（关键约束，决定 scope）

`roi.py` 现有两个原语都只够支撑 **depth-2 的几何过渡**：

- `crop_inputs_from_boxes`（`roi.py:68-151`）：只裁 `rectanglelabels`（轴对齐 bbox），裁完即丢弃 `(left, top, scale)` 仿射变换，**没有把 crop-local 几何回映到原图的能力**——它是为"下游只回属性"设计的。
- `geometry_prompts_from_boxes`（`roi.py:166-215`）：只读 bbox 父框，喂 box-prompt 模型（SAM 类 box-seg），下游回**原图坐标** polygon。它表达的是"给定框→出几何"，**不能**表达"在父 ROI 内**检测新子物体**"——普通检测器（YOLO 类）不吃 box prompt。

由此，本版 depth-3 的**可达 / 不可达**：

| 链路 | 本版 | 原因 |
|---|---|---|
| `detect → classify A → classify B`（attribute 链；A/B 都裁同一批向下透传的父 bbox，几何不变） | ✅ | crop 始终作用在透传的父 bbox 上，属性累加到 root（§6.3 中 `stage_outputs[st.stage]=parent_boxes`） |
| `detect → box-seg`（box→mask，geometry-prompt，原图坐标 polygon） | ✅（depth-2 叶子） | geometry-prompt 原语已支持 |
| `detect person → 检测 hat → color`（中间阶段在 crop 内**检测新子物体**，产原图几何） | ❌ **本版不支持** | 需"crop 内检测 + 坐标回映"，原语不存在 |
| `detect → box-seg → 在 polygon 上再裁/检测`（消费上一阶段**新产几何**做几何级下游） | ❌ **本版不支持** | crop/geometry-prompt 原语都只读 bbox，不读 polygon |

**诚实结论**：0.18.14 交付的是**受限树形的结构骨架**——schema、受限树形校验、拓扑执行、provenance meta、UI 脚手架、crop 钉死 attributes-only、模型市场卡片修正。它让 depth-3 在数据模型与 attribute 链路上成立，但**真正有价值的几何 depth-3（`person → hat → color`）所需的 ROI 原语（crop 内检测 + 坐标回映、polygon 裁剪）不在本版**，整体推到 [0.18.15 计划](./2026-06-25-v0.18.15-model-io-contract-and-crop-remap-draft.md)。

附录 A 的 `yolo-hat`（`write.target=intermediate` 的检测子，模型不支持 bbox prompt）即落在 ❌ 分支：本版校验会因"子产几何但模型不支持 bbox prompt"而 422。**附录 A 仅作 schema 形态示意，不是本版可跑样例**，0.18.15 落地坐标回映后才真正可跑。

## 9. 验收

**接受（必须通过）**：

- 既有双阶段 vehicle 流水线不改 payload：`detect vehicle → classify color | vehicle_type`。
- 既有 box-seg：`detect → box-seg`。
- 新 depth-3 happy（attribute 链，本版可跑）：`detect person → classify A → classify B`（B 的 `parent_stage` 指向 A），root 框上同时出现 A、B 两组属性，`PredictionMeta.extra.pipeline.max_depth == 3`。几何全程是透传的 person bbox。
- 多兄弟 attribute 富集：`detect vehicle → classify color | classify vehicle_type`，root 框同时有两个属性，`pipeline.enriched_attr_keys` 都包含。
- **几何 depth-3（`person → detect hat → color`）不在本版验收**——见 §6.6，所需 ROI 原语推 0.18.15。本版只验证它在校验期按预期 422（见下表）。

**拒绝（替换 `test_reject_depth_three` 的矩阵）**：

| 用例 | 期望错误片段 |
|---|---|
| 前向 `parent_stage`（如 stage 1 设 `parent_stage = 2`） | `"未在前面定义"` |
| depth-4 链路（`0→1→2→3`） | `"超过最大深度 3"` |
| 父阶段 `write.target = "attributes"` 被当作父引用 | `"不产几何，无法作为父阶段"` |
| `write.target_stage = "parent"`（或任何 ≠ `"root"` 的值） | `"暂不支持"` |
| 加完前缀后属性键碰撞（两个 stage 都写同一最终键到 root，且 `on_key_conflict = reject`） | `"attribute key 冲突"` |
| 子 `write.target ∈ {geometry, intermediate}` 但子模型不支持 bbox prompt（如附录 A 的 `yolo-hat`） | `"产几何但模型不支持 bbox prompt"`（§6.3 路由前置校验） |

**运行时行为**：

- 运行态统计面板按 `pipeline.stages[].depth` 缩进展示嵌套阶段。
- 工作台候选审核能看到最终属性而不暴露流水线结构。
- §10 的按深度 pad 默认在 `stage.roi.pad` 未填时生效；裁剪短边 < 32 px 时 `skipped_geometry` 计数。

## 10. 风险 / 开放问题

- **嵌套裁剪的画质衰减**。每深一层裁得更紧，下游模型见到的输入分辨率更低。缓解方案：按深度 pad 默认 `{1: 0.05, 2: 0.08, 3: 0.12}`，并在 `roi.crop_inputs_from_boxes` 加 `min_crop_side_px = 32` 守卫。低于阈值的裁剪计入 `skipped_geometry`，父框靠 `on_failure = "keep_parent"` 保留。
- **depth ≥ 3 的 root 追溯**。crop 输入必须逐层带 `provenance_root_box_id`（根框索引）。`merge_classify_attributes` 据此回查根框，哪怕直接父是 `intermediate` 也能定位。在 crop 输入字典里显式落字段，不要散在自由 key。
- **属性命名空间**。前缀 `label` 是避免 `s2_color / s3_color` 难辨的关键。前端表单在 `write.target = "attributes"` 且（`parent_stage != 0` 或兄弟共用 `write.keys`）时把 `label` 设为 required。
- **depth-3 的运行态 UX 信息密度**。可见每阶段 chips 控制在 4 个（detected / targeted / ok / failed），其余进 tooltip。
- **未来 DAG 的压力**。用户迟早会要 joins / 跨枝依赖 / 动态条件。这是单独的产品决策，不能往本版本里塞。`write.target_stage` 是已约定好的扩展位（未来开 `"parent" | int`），约定就是用来挡这种压力的。
- **可审核子形状**。"写为子形状"刻意不做。等到有具体审核流程要求审核员单独修 hat/shoe 时再启动；现在用 `write.target = "intermediate"` 占位防止过早落库。
