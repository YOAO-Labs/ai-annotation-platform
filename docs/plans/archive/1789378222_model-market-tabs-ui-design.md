# 模型市场多 TAB UI 优化方案

> 状态：设计提案，尚未实施。
> 日期：2026-09-14。
> 范围：`/model-market` 的能力目录、运行时观测、注册管理，以及注册管理的五个子视图。
> 目标：减少寻找内容和横向滚动的成本，让浏览能力、判断运行状态、维护注册对象各自有清晰的操作路径。

## 1. 推荐方向

采用现有产品的紧凑管理界面风格：中性表面、细分隔线、清晰的两级导航、与对象对应的工具栏、按需展开的详情。保留现有三主 TAB 和五注册子 TAB，使用已有 React、Tailwind 语义 token、shadcn/Radix、Lucide 和 Query 数据层。

最小方案是只调整间距、缩短表头、收起 UUID。它能改善局部密度，但仍留下筛选无效、子页返回重置和重复统计问题。推荐同时处理布局与导航状态；每阶段独立可用，样式回退不涉及数据库。

本方案假设主要工作发生在桌面管理场景。若手机成为主要操作入口，则需要单独优化长表单和维护流程；本次仍要求手机可阅读、可筛选、可进入详情，关键操作不依赖横向拖动整张表。

## 2. 实际界面证据

已在用户提供的运行地址查看全部三个主 TAB、全部五个注册子 TAB、目录卡片/列表切换及运行时成员展开。使用超级管理员角色；检查了 1440×1000 深色页面，补看目录浅色、1280×800 浅色实例页和 390×844 实例页。

| 观察                                                                                         | 影响                           | 处理方向                                                     |
| -------------------------------------------------------------------------------------------- | ------------------------------ | ------------------------------------------------------------ |
| 实例表有 10 列，1440px 窗口仍无法同时看到左侧名称和右侧操作                                  | 查到对象后还要横向找操作       | 合并身份信息，控制主列，固定操作列                           |
| 手机实例页的注册子 TAB 在约 y=755px，首屏几乎没有业务记录；约 1337px 的表格装在 332px 容器内 | 信息到达过晚，无法快速比较状态 | 去掉重复大统计卡，窄屏使用对象摘要行                         |
| 标题、全局三统计卡、主 TAB、注册摘要卡、子 TAB、子页按钮依次堆叠                             | 层级过多，表格开始于约 y=550px | 主标题 → 主导航 → 子导航 → 紧凑摘要/工具栏 → 数据            |
| 两级 TAB 都是相近的胶囊容器                                                                  | 主功能与对象分类缺少视觉区分   | 主 TAB 使用下划线，子 TAB 保留紧凑分段样式                   |
| GPU、项目绑定、问题中心仍显示“搜索服务池或实例”和健康筛选，但不消费这些条件                  | 用户无法判断筛选是否生效       | 工具栏归属具体子页，只显示真实生效条件                       |
| GPU/项目/问题页也显示“注册实例”，服务池另有“新建服务池”按钮行                                | 当前页面主操作不明确           | 服务池突出新建池，实例突出注册实例，其余页面按职责显示动作   |
| 顶部“模型条目”为 16，目录标题为 34；非目录页该统计卡显示占位符                               | 同名统计范围不明确，且占用空间 | 目录统计跟随实际展示集合，移除父页面重复计数                 |
| 目录模型卡默认展开输入、输出、属性和完整变体                                                 | 34 个条目形成很长页面          | 首层保留选择模型所需信息，详细合同与变体按需展开             |
| 运行时已有两列池卡，每卡又含四个小信息块，页头还叠加四块摘要                                 | 层层卡片，缺失指标反复出现     | 保留两列池卡，内部改为紧凑字段带                             |
| GPU 名称/诊断中重复完整 UUID；问题筛选使用 ID，影响对象只是数量                              | 难辨认，也难从问题进入对象     | 可读名称优先，短 ID 辅助识别，完整 ID 可复制，影响对象可跳转 |
| 切到其他主 TAB 再返回注册管理会回到服务池                                                    | 打断维护上下文                 | 子页与定位对象写入 URL，支持刷新和前进后退                   |

观测时模型市场主要读取接口返回 200，未捕获页面 JavaScript 异常；这不代表后台所有服务正常。运行时确实存在部分数据来源不可用、路由指标缺失等业务状态，优化需要如实呈现。

本次没有验证项目管理员的真实浏览器会话、人工制造空数据/接口失败、提交注册或执行预热/卸载。这些列入实施后的验收；权限约束已通过实现和文档核对。临时截图在审查后清理，不作为正式文档媒体保留。

## 3. 公共页面结构

注册页结构示意：

```text
模型市场
浏览模型能力、查看运行状态和管理后端服务。

能力目录        运行时观测        注册管理
                                ────────

服务池 6   实例 6   GPU 资源 2   项目绑定 4   问题中心 3

可路由实例 4/6 · 待处理问题 3 · 数据部分可用
搜索当前对象……   当前对象筛选                   当前主操作   刷新

名称与身份       关键关联       状态       关键资源       操作
对象记录……
```

上图数字来自本次观测，仅说明位置，不进入实现默认值。每个计数必须有明确来源；请求尚未完成显示加载状态，未知不写成 0。

- 页面保留一个 H1，去掉 Panel 中与选中 TAB 重复的装饰性大标题与大图标。
- 移除父页面三张全局统计卡。使用项目数留在项目绑定，模型数留在目录，运行统计留在运行时；注册摘要保留已有服务池、可路由实例、问题和受影响项目口径。
- 主 TAB 采用本地 `TabsList variant="line"`，子 TAB 采用默认分段样式；复用现有组件，不另造 TAB 系统。
- 首层只承载当前操作所需的总览；相同口径的 mode、来源更新时间统一展示一次，单行例外再单独标注。
- 页面内部仅保留一套有明确范围的刷新动作；维持原有数据请求行为，目录重探能力的副作用需要保留在按钮说明中。
- 色彩沿用语义：健康/完成、警告、失败、AI 能力；普通计数与 ID 保持中性。问题 TAB 徽标按真实最高严重度展示，不能把所有非零数量都画成红色。
- 保留当前字体与紧凑字号：主内容 `text-sm`，次级信息 `text-xs`，短 ID 和标签 `text-2xs`。数字右对齐并使用等宽数字；不靠缩小主要文字塞入列。
- 使用现有 `bg-background / bg-card / bg-muted / border-border` 和状态 token。CSS 采用语义 Tailwind，不更改全站主题或加入新字体。
- 交互反馈以现有 hover、active、focus-visible 为准；高频 TAB 切换和刷新不加入装饰动画。页面级覆盖使用明确的颜色/透明度 transition，不增加 `transition-all`。
- 与通用 UI 技能的字体换新、通用按压缩放建议相比，本方案优先遵循仓库“保留既有设计系统和紧凑操作”的规则，不扩大全站改动。

本地组件已经封装 Radix。其受控状态、手动激活和键盘导航可直接复用；主 TAB 使用手动激活，方向键移动焦点，Enter/Space 确认切换，避免只移动焦点就触发后台加载。参见 [Radix Tabs 官方文档](https://www.radix-ui.com/primitives/docs/components/tabs)。

## 4. 各主 TAB 的目标布局

### 4.1 能力目录：先判断模型是否适合，再查看详细参数

默认仍按协议能力分组，保留卡片/列表两种模式。未设置筛选时，即使没有接入后端，也保留完整协议能力目录。

工具栏顺序：

1. 搜索、分组、卡片/列表切换、刷新。
2. 任务和模态快捷筛选、更多筛选。
3. 当前结果计数、已应用条件标签。

计数约定：明确区分“能力类别数”和“模型条目数”；结果计数使用当前实际渲染集合，过滤前后显示“匹配 N / 总计 M”。不通过父页面按项目累加 capabilities 生成第二套模型总数，不把接入数量描述成实时在线数量。

模型卡首层保留：

- 模型名称与来源后端；
- 任务/模态，以及可批量、交互/有状态等影响选型的能力；
- 简短输入 → 输出摘要；
- 已知的驻留情况或“运行状态未知”，适用时显示缓存提示；
- 详情展开入口，以及现有规则允许时的预热动作。

协议分组中，任务标签已在分组标题呈现时，不在每张卡内重复；切换到不分组时恢复。框架、模型族、完整属性、资源细项、版本/尺寸等变体放进卡内展开区域。展开按钮为独立按钮，不能把整个卡片包成含多个交互控件的大按钮。

列表模式中，每个协议行保持紧凑，显示能力、输入/输出、接入数量、模型名称摘要和“查看全部 N 个模型”。这个入口需要实际展开剩余模型，替换现有不可点击的“+N 个模型”文字。未接入能力先显示一行说明和接入入口，推荐后端在展开区域列出。

输入类型、输出属性、变体与图像/视频预热目标仍消费现有字段；不删能力信息，不改变运行参数。

### 4.2 运行时观测：横向比较状态，再下钻实例

保留当前“服务池卡 → 成员 → 详情 Sheet”的布局机制和两列桌面网格，避免同时引入新的卡片/表格模式开关。

- 顶部四个大摘要块改成一条可换行的紧凑摘要带：路由模式、可路由实例、需关注服务池、数据来源可用性。
- 数据来源详细时间、错误和 freshness 保持现有展开区。首次数据失败保留明确重试，局部失败保留可信内容。
- 池卡去掉四个内层小卡，改为两行字段：健康与路由分开显示；可路由/总实例、并发、驻留、CPU 回退分别有标签。
- 正常池保持稳定顺序；不因每次轮询的数值变化而重新排序。异常池维持现有优先级规则，不自动展开造成页面跳动。
- 同一池无流量指标时只显示一条“暂无路由指标”，详细缺失字段仍在下钻处显示未知；不能为减少空白把它们显示为 0。
- 正常池卡目标约 160–190px，高度允许随必要错误信息增长；展开成员时仍跨两列。1440×1000 首屏目标能比较 6 个未展开池。
- 成员首层展示名称、健康、路由、容量、驻留四条独立信息；详情与维护动作沿用已有组件。
- 未注册容器继续放在独立折叠区，不混入服务池和路由统计。

### 4.3 注册管理：按维护对象组织内容和操作

子 TAB 下放对应工具栏；公共刷新可以保留，搜索与筛选必须属于当前集合。

| 子 TAB   | 主内容结构                                                             | 当前工具栏和操作                                               | 下沉内容                                                                       |
| -------- | ---------------------------------------------------------------------- | -------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| 服务池   | 服务池身份 / 成员 / 容量 / 关联项目与资源 / 健康及路由 / 操作          | 搜索池或成员、健康筛选、新建服务池；行内展开成员，更多菜单维护 | 完整池 ID、策略解释、正常重复时间、原始 reason                                 |
| 实例     | 实例身份 / 所属服务池 / 健康及路由 / 并发与 GPU 摘要 / 最近检查 / 操作 | 搜索名称/ID/URL、健康筛选、可移除的池定位条件、注册实例        | URL 放名称副行，来源为轻标签；权重、完整 GPU claim、原始快照进入现有详情 Sheet |
| GPU 资源 | 资源身份 / 静态声明与预算 / 运行时占用 / 队列与租约 / 模式 / 诊断      | 按节点、名称、ID 搜索；全局就绪性紧凑显示，展开关联实例        | 完整 UUID、Rollout 细节、详细诊断                                              |
| 项目绑定 | 项目 / 关联服务池 / 可用实例 / 风险 / 项目设置                         | 当前对象搜索，按项目/按服务池切换                              | 完整项目 ID；推断出的“主服务池”不作为已配置事实突出展示                        |
| 问题中心 | 严重度 / 问题说明 / 影响对象 / 建议及定位入口                          | code 搜索，严重度快捷筛选，服务池/实例/GPU/code 附着式筛选     | 原始 code、去重键和诊断全文；影响对象可展开名称并导航                          |

补充约定：

- 服务池的“注册实例”作为次级菜单入口保留，主按钮只突出“新建服务池”。GPU、项目、问题视图不放无关创建按钮。
- 实例主操作“详情”始终可见；编辑、健康检查、停流/恢复和高风险操作维持既有权限及菜单分组，不通过扩大整行点击区域意外触发维护。
- ID 默认使用名称 + 短 ID；完整值提供 tooltip、可键盘访问的复制按钮，并在详情中完整显示。GPU 未提供设备序号时，不凭空命名“GPU 0/1”。
- GPU“静态已声明 / 可分配预算”和“运行时 committed”保持两条独立读数；静态超售百分比不冒充物理显存实时利用率。预算未知时不画空的进度条冒充 0%。
- 项目关联来自当前拓扑与已启用后端的展示推导；页面标注“依据已启用实例关联”。取消当前按可路由数量推断的“主服务池”主列，真实配置仍到项目设置查看。
- 问题主记录仍按稳定去重键唯一展示；列表行只显示简短诊断和关联数量，点击跳到问题中心带上对象条件。源数据没有可匹配的问题记录时，显示非交互摘要，不制造禁用的伪跳转。
- 问题筛选选项优先显示对象名称，重名时附短 ID，实际筛选值仍是稳定 ID。

## 5. 导航、筛选与状态约定

利用现有 `useUrlFilterState`，增加页面局部 codec；不引入全局状态库、通用表单引擎或新服务。

- 保留 `tab=catalog|runtime|registry` 与旧 `tab=failed` 跳转。
- 注册子 TAB 增加 `registry_view=pools|instances|gpu|projects|issues`；缺失默认 pools。切主 TAB 保留该值，返回注册页恢复上次子视图。
- 池→实例使用 `registry_view=instances&instance_pool=<id>`；替代当前 `registry:focus-tab` 事件。问题影响对象通过目标子页的定位键进入具体对象。
- 详情定位键使用 `instance_id`、`gpu_id`、`pool_id`；问题筛选键与对象详情键分开，不相互覆盖。
- 已删除或当前角色无权访问的对象显示“对象不存在或当前不可访问”，不扩大筛选到全部对象。
- 显式 TAB 与对象跳转新增浏览器历史；文本编辑替换当前历史。返回按钮恢复原子页与条件。
- 主 TAB、注册子 TAB 的未知枚举回退到允许的默认页并规范化 URL。项目管理员无权访问 runtime/gpu/projects/issues 时，回退到其可见页，不发相应超管请求。
- 非活动页参数保留但不参与当前查询/筛选；codec 只修改自身键。

筛选与显示状态键：

| 所属视图 | URL 键                                                                                                              | 默认与清除范围                                                        |
| -------- | ------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------- |
| 目录     | `catalog_q`、`catalog_group`、`catalog_view`、`catalog_task`、`catalog_modality`、`catalog_family`、`catalog_infra` | 分组 task、视图 cards；多选使用重复键；清除条件保留搜索/分组/显示方式 |
| 服务池   | `pool_q`、`pool_health`                                                                                             | 搜索空、健康 all；清除条件保留搜索                                    |
| 实例     | `instance_q`、`instance_health`、`instance_pool`                                                                    | 搜索空、健康 all、无池限定；清除条件移除健康和池限定                  |
| GPU      | `gpu_q`                                                                                                             | 搜索空；只匹配本页资源名称、节点、ID                                  |
| 项目绑定 | `project_q`、`binding_view`、`binding_pool`                                                                         | 默认按项目；切分组保留搜索并更新其明确提示，池限定可单独移除          |
| 问题     | `issue_q`、`issue_severity`、`issue_pool`、`issue_instance`、`issue_gpu`、`issue_code`                              | 默认全部问题；code 文本搜索独立于精确 code 筛选；清除条件保留文本搜索 |

过滤枚举非法时给可见提示和移除入口，不能静默丢掉非法过滤值扩大结果。服务池、实例、GPU、项目、问题各自搜索真实的展示集合；搜索标签随当前对象变化，不能保留无效的跨页工具栏。

状态流向保持单向：

```text
URL / 当前角色
       |
       v
页面局部 codec + 已有 useUrlFilterState
       |
       +--> ModelMarketPage --> 当前主 Panel --> 对应子视图
       |                               ^
       |                               |
       +--> 对象定位          既有 Query + 纯 view-model
                                       |
                                  行 / 卡 / 详情
                                       |
                         用户导航更新 URL；维护沿用既有 mutation
```

## 6. 响应式与异常状态

- ≥1280px：保留现有侧栏，注册主表无需横向滚动即可看到身份、主要状态、详情/操作；实例关键列控制在 6 列，必要时次要信息换行。
- 768–1279px：合并关联/资源摘要列，操作列固定；允许详情内的专业宽表局部滚动，页面本身不横向溢出。
- <768px：子 TAB 单行可横向滚动，当前项自动进入可视区域；工具栏换行；表格改为同一数据映射生成的对象摘要行，名称/状态/详情在可视范围内，不另造一套业务推导。
- 390×844：注册子 TAB 目标进入前 300px，第一条实例目标进入前 460px；两个项目管理员 TAB 按实际数量分配宽度，不保留第三个空槽。
- 空态明确区分“未接入”“没有匹配结果”“无可路由实例”“数据加载失败”。只在请求完成后显示最终空态。
- 初次加载使用与最终布局一致的骨架；后台刷新保留内容、标注刷新或陈旧状态，避免内容整块闪空。
- 详情关闭后焦点返回原触发按钮；TAB、筛选、菜单、折叠和复制均可用键盘操作。失效条件、风险和禁用原因不能只依赖颜色或鼠标 hover。
- 自动刷新不改变用户展开状态或强制滚动位置。单个来源失败不清掉其余可信数据。
- 深浅主题均使用 `data-theme`；不引入 `.dark` 选择器。

## 7. 必须保留的业务合同

依据 [ADR-0051](../../adr/archive/0051-model-market-observability-information-architecture.md)，以下已是冻结决策：

1. 健康、路由、容量、驻留是四条独立状态轴，不能压成一个“在线”绿点。
2. unknown、stale、partial 不互相替代；缺失数据不回落成 0/健康/空闲。
3. 诊断去重键保持 `code + subject_type + subject_id`。
4. 卸载继续要求 draining、inflight=0、账本新鲜、router enforce；不能用界面简化绕开门禁。
5. 项目管理员裁剪是服务端责任，前端查询门控继续保留；目录不能因无法调用超管接口而整体失败。
6. 图像和视频的预热、驻留池继续独立处理。
7. 不新增实时趋势、Prometheus 计数接线、GPU 调度行为或 API 字段。现有数据不足时改善解释，不创造指标。
