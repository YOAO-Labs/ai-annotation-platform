# v0.18.1 — M1 · 顺序 2 阶段预标注 MVP（路径 B 第一块）

> 状态：**待实施 plan**（不开干）。创建于 2026-06-23。
>
> 定位：路径 B（[平台层多阶段预标注编排 ROADMAP](../../ROADMAP/2026-06-23-staged-preannotation-pipeline-roadmap.md)）的**第一个落地里程碑**。把「检测 backend → 拿框 → 平台裁 ROI → 分类 backend → 属性合并写回」整条**跨 backend** 通路在平台 worker 里串通并验证。本期只做**单 detect → 单 classify 顺序链**（无并行扇出、无类别路由、无界面产品化），把数据通路打穿；ROI/降级（M2）、界面（M3）留后续。**M0 设计冻结折进本 plan §2**。

## 0. M0 设计冻结（拍板项，后续里程碑共享）

ROADMAP §7 已决议，本期固化为实现前提，不再翻案：

1. **同步顺序执行**：单 Celery task 内 `for stage in stages` 顺序跑（含未来并行兄弟也先顺序），不拆 `chord`。
2. **属性取值域对齐复用协议③**：backend `/setup` 自报 `output_attribute_schema`，一键导入项目 `attribute_schema`（v0.18.0 已落地，B 不重做）。
3. **ROI 平台裁**：平台按父框 bbox 裁 crop 传下游，backend 无感（本期固定 `crop`+固定 pad，可配留 M2）。
4. **采纳维持逐框**：属性 merge 进父框 `attributes`，前端零改动。
5. **界面线性阶段卡，不上节点图**（本期只做最小「加第二阶段」，完整 UI 留 M3）。
6. **并行兄弟键冲突 → 声明 + 检测**（本期无并行，仅预留 `write.keys` 字段，校验留 M2/M3）。
7. **数据模型 MVP 不改表**：阶段元信息暂存 `PredictionMeta.extra` JSONB（`prediction.py:95`），正式列留 M3 评估。

## 1. 目标 / 非目标

**目标**
1. 放开 `MAX_ML_BACKENDS_PER_PROJECT`（允许一项目绑 ≥2 backend：detect + classify）。
2. `PreannotateRequest` 增可选 `pipeline_stages`（ROADMAP §3.1 形态）；缺省时**完全等价于现有单阶段路径**（向后兼容）。
3. `_run_batch` 阶段化：阶段 0 检测产框 → 平台裁 ROI → 阶段 1 分类 → 属性 union 进父框预测的 `attributes`，落库。
4. 平台内置 `dynamic_crop`：按阶段 0 每个 bbox（+固定 pad）裁图，作为独立 input 喂阶段 1 backend。
5. 阶段元信息（`stage_index` / `parent_prediction_id`）写入 `PredictionMeta.extra`，不改表。
6. UI 最小可用：`ProjectDetailPanel` 支持「加第二阶段」（复用 `PreannotateConfigForm` 第二实例），跑通即可。

**非目标**
- 不做 `parent_class_filter` 类别路由（留 M2）。
- 不做并行扇出 / 多 classify（留 M2/M3 界面）。
- 不做 `roi.mode` 多模式 / 可配 pad（本期固定 `crop` + 固定 pad，留 M2）。
- 不做阶段级失败策略细化、按阶段进度上报（留 M2）。
- 不做 `write=new_shape`、正式表字段、`chord` 并行、完整阶段卡 UI（留 M3）。
- 不动工作台 `AIInspectorPanel`（候选属性审阅泛化是 v0.18.2/3 的事；v0.18.0 已给最小只读预览）。

## 2. 详细设计

### 2.1 放开多 backend 上限

- `MAX_ML_BACKENDS_PER_PROJECT` 当前默认 1，409 拦截在 `apps/api/app/api/v1/ml_backends.py:66`。
- 改：默认调到能容纳 detect+classify（保守值如 `3`，env 可覆盖），保留上限防显存爆炸。仅改默认值与 `.env.example`，拦截逻辑不动。
- 文档：`.env.example` 改后跑 `pnpm docs:gen-env-vars` 重生 `env-vars.md`（CLAUDE.md §5）。

### 2.2 请求体扩展（`apps/api/app/schemas/preannotate.py::PreannotateRequest`）

新增可选字段（与现有平铺字段并存，互斥使用）：

```python
class PipelineStage(BaseModel):
    stage: int
    ml_backend_id: uuid.UUID
    model_id: str | None = None
    task_type: str | None = None
    model_variants: dict[str, str] | None = None
    params: dict | None = None
    class_filter: list[int] | None = None
    parent_stage: int | None = None          # None=源阶段（吃整图）
    roi: dict | None = None                   # 本期仅认 {"mode":"crop"}，pad 固定
    write: dict | None = None                 # {"target":"attributes","keys":[...]}；本期只认 attributes

class PreannotateRequest(BaseModel):
    ...                                       # 现有字段不动
    pipeline_stages: list[PipelineStage] | None = None
```

**归一化**：endpoint 在 dispatch 前把请求规整成统一的 `stages` 列表——
- `pipeline_stages` 非空 → 直接用。
- `pipeline_stages` 为空 → 用现有平铺字段合成 `[单 stage]`（`stage=0, parent_stage=None`），下游 worker 只认 `stages`，**单/多阶段共一条代码路径**。
- 本期校验：`stages` 长度 ≤2；非源阶段必须 `parent_stage` 指向已存在的更小 index；`write.target` 仅允许 `attributes`。

### 2.3 Worker 阶段化（`tasks.py:118` `_run_batch`，ROADMAP §3.2）

`_run_batch` 现签名是一组平铺单模型参数。改为接收归一化后的 `stages`（其余 batch 级参数 `predict_mode`/`batch_id`/`user_id` 不变）。核心循环：

```python
stage_outputs: dict[int, dict[task_id, list[pred]]] = {}
for stage in stages:
    for task in tasks:
        if stage.parent_stage is None:
            inputs = [{"id": task.id, "file_path": presigned_url(task)}]
        else:
            parents = stage_outputs[stage.parent_stage].get(task.id, [])
            if not parents:                       # 降级：上游无框 → 本 task 跳过本阶段
                continue
            inputs = build_roi_inputs(task, parents, stage.roi)   # 平台裁 crop
        ctx = _build_predict_context(model_id=stage.model_id, task_type=stage.task_type,
                                     model_variants=stage.model_variants, params=stage.params, ...)
        results = await client(stage.ml_backend_id).predict(inputs, ctx)
        stage_outputs[stage.stage] = save_stage_results(
            results, stage_index=stage.stage, parents=parents, write=stage.write)
```

- **源阶段（stage 0）**：行为与今天单模型预标完全一致（产框，落 `Prediction` 行）。
- **下游阶段（stage 1）**：每个 crop 对应一个父框，分类结果的 `attributes` **merge 进父框那一行预测的 `attributes`**（不新增 `Prediction` 行），并在父框的 `PredictionMeta.extra` 补 `{"enriched_by_stage": 1}`；下游自身不另起几何。
- 现有进度发布、`failed_predictions` 软记录、`predict_mode` 复用；本期下游失败 = 该框属性留空、保留上游框（粗粒度，细化留 M2）。

### 2.4 平台内置 ROI 裁剪 `build_roi_inputs`（ROADMAP §3.4）

- 新增 worker 侧工具：取 task 原图（经现有 presigned/读取通路）→ 对每个父框 bbox 按固定 pad（如 0.05）外扩 → Pillow/OpenCV 裁 crop → 落临时对象（复用现有 MinIO/S3 通路存临时 key，或内存 base64 走 image input）。
- 每个 crop 作为独立 input，**携带回指父框 id** 的映射，供 2.3 结果 merge。
- 下游 backend 无感：只收到一张小图跑它本就支持的分类，结果塞 `attributes` 返回（协议 §3 已有，非新增）。
- 临时 crop 生命周期：batch 跑完即清（或用短 TTL presigned）。MVP 取最简实现，复杂度留 M2 评估。

### 2.5 阶段元信息落库（不改表）

`PredictionMeta.extra`（`prediction.py:95` JSONB）写：
- 源阶段框：`{"stage_index": 0}`。
- 被 enrich 的父框：补 `{"enriched_by_stage": [1], "stage_attr_keys": ["color"]}`，便于追溯「哪个属性来自哪个阶段」。
- 不引入新列、不迁移（正式列 `stage_index`/`parent_prediction_id` 留 M3 按价值评估）。

### 2.6 前端最小改动（`ProjectDetailPanel`）

- `ProjectDetailPanel.tsx` 现持一份 `PreannotateConfigForm`。本期加「+ 加第二阶段」按钮，按下后**容器再实例化一份** `PreannotateConfigForm`（第二个 `usePreannotateConfig` 实例），收集成 `pipeline_stages[1]`。
- **红线（ROADMAP §5）**：阶段编排逻辑放在 `ProjectDetailPanel`（容器持有 N 个共享表单实例），**绝不改 `PreannotateConfigForm` / `usePreannotateConfig` 本身**——否则工作台 `AIInspectorPanel` 被动继承 pipeline UI。
- 第二阶段卡最小字段：backend/model/variant（复用表单）。`roi`/`write.keys` 本期给固定默认（crop + 单一属性键由协议③导入的字段推断），不暴露完整配置 UI（留 M3）。
- 仅一阶段时请求体不带 `pipeline_stages`，走老路径，零行为变化。

## 3. 实施步骤（每步带 verify）

1. 放开 `MAX_ML_BACKENDS_PER_PROJECT` 默认 + `.env.example` + 重生 env-vars → verify：同一项目能绑 detect 与 classify 两个 backend，不再 409。
2. `PreannotateRequest.pipeline_stages` + 归一化 + 校验 → verify：带 1 个 stage 的请求行为同今天；带 2 个 stage 的请求通过校验、超 2 或非法 parent 报 422。
3. `_run_batch` 阶段化（统一走 `stages`） → verify：单 stage 跑批结果与改造前逐字一致（回归）。
4. `build_roi_inputs` 平台裁 crop → verify：单测对一张多车图按 bbox 裁出 N 张 crop，pad 生效，crop↔父框映射正确。
5. 下游 merge 写回 + `PredictionMeta.extra` → verify：detect→classify 跑完，父框预测 `attributes` 含 classify 输出键，`extra.enriched_by_stage` 记录在案。
6. `ProjectDetailPanel`「加第二阶段」UI → verify：界面配 detect+classify 两阶段→运行→工作台候选框带 `attributes`→采纳→属性入库可编辑（沿用 v0.18.0 已通的 select 链路）。
7. 版本收尾（CLAUDE.md §10）：bump `CHANGELOG.md` / `config.py` / `pyproject.toml` / `package.json`，`uv lock`，pre-commit 重生 openapi 快照；`curl localhost:8000/health` 验证 0.18.1。

## 4. 验收标准

- 一项目绑 detect + classify 两 backend，配 detect→classify 两阶段批量预标后：每个目标框带 `class_name`（detect 类）+ `attributes`（classify 产出键）；上游无框的 task 不产物（降级正常）。
- 单阶段请求行为与 v0.18.0 完全一致（向后兼容回归通过）。
- 采纳后属性入库、工作台 select 可编辑（复用 v0.18.0 链路）。
- 阶段元信息可在 `PredictionMeta.extra` 查到「哪个属性来自哪个阶段」。

## 5. 风险 / 开放问题

- **crop 域偏移**（ROADMAP §3.6 末）：全图训练的 classifier 吃紧 crop 可能掉点；固定 pad 缓解，可配 pad 留 M2。属模型质量非协议问题。
- **临时 crop 管理**：MVP 用最简存储；若 I/O 成瓶颈，M2/M3 再优化（内存传递 vs 临时 key）。
- **`_run_batch` 回归面**：改其入参形态触及所有现有单模型预标路径，第 3 步回归是硬关卡，务必逐字比对改造前后单阶段结果。
- **多 backend 显存**：detect + classify 并存的显存预算，沿用 v0.18.0 监控即可。
