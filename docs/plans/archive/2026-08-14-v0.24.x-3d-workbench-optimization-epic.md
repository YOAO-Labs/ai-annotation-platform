### 2.2 调研输入只改变优先级，不直接扩大范围

- [Supervisely 与 CVAT 标注工作台深度调研](../../research/22-supervisely-cvat-workbench.md) 基于官方文档、图片、GIF、视频和固定源码快照，明确把双击对象聚焦、per-object zoom、相机稳定和布局预设排在第一条低风险工程切片。v0.24.2 因此先做高频精修，不把时间轴和质检一起塞入。
- [Supervisely 3D Point Cloud and Episodes](https://docs.supervisely.com/labeling/labeling-toolbox/3d-point-cloud-episodes-2) 已把时间轴、多帧点云、相机上下文、AI cuboid 调整和大点数交互放在同一工作台。当前差距集中在 4D 导航与相机内编辑，不在基础渲染器。
- [LeRobotDataset v3](https://huggingface.co/docs/lerobot/lerobot-dataset-v3) 用 Parquet、MP4 和关系型 episode 元数据组织多模态时序，并支持流式读取。若以后接入具身数据，原始分片应保持不可变，平台只保存索引和标注。
- [RoboInter](https://github.com/InternRobotics/RoboInter) 提供 23 万以上 episode 和十余类中间表示；[RoboInter1.5](https://arxiv.org/abs/2607.18709) 又把这些表示扩展到具身世界建模。它说明未来标注对象会包含轨迹、接触、技能与语言，但不构成立即把这些类型塞进 3D 工作台的理由。
- [DROID](https://droid-dataset.github.io/) 同时保留多相机、相机标定、动作、状态和语言，且后续仍在补校准数据。多传感器时序的首要条件是时间和标定可信。
- [EmbodiedScan](https://arxiv.org/abs/2312.16170) 把 RGB-D、3D 框、语言与占据表示放在同一数据集。平台当前先补齐 3D 框的编辑、导出和质检，再评估 occupancy 或语言接地。

## 4. 原始数据流与真值边界（历史记录）

> 本节记录 2026-08-14 时的跨版本方案，只用于解释 v0.24.0 和未实施草案的原始依赖。v0.24.2 不新增下图中的导出或 frame-summary 链路，其数据流以独立计划为准。

```text
放大相机图
    │ 固定相机深度反投影
    ▼
draftPsr ───────────────► 点云主视图 / 三视图 / 全部相机投影
    │ pointerup 一次提交
    ▼
Annotation(box_3d) ─────► history + PATCH
    │
    ├────────► KITTI: 选定相机标定 + 真实 2D bbox
    ├────────► COCO: 每个相机即时派生 2D bbox
    └────────► nuScenes: scene / pose / timestamp / track 链

Scene + DatasetItem.frame_index + SceneFramePose + Annotation
    │ 单次聚合
    ▼
GET /scenes/{scene_id}/frame-summary
    │
    ▼
ThreeDSceneTimeline ─────► 选择 task，复用工作台现有导航与锁语义
```

贯穿三个版本的约束如下：

1. `Annotation.geometry.type=box_3d` 是唯一几何真值。相机操作只更新它。
2. `SensorCalibration` 是投影与反投影的唯一标定合同。前后端都按 row-major `extrinsic`、可选 `rect`、`intrinsic` 执行。
3. `SceneFramePose` 是 nuScenes 时间与 ego pose 的唯一来源。缺失时 nuScenes 导出失败，不能回退为零时间或单位位姿。
4. 时间轴是只读摘要和导航入口，不自动修复轨迹，不替用户接受预测，也不改 task 状态。
5. v0.24.0 至 v0.24.2 不增加数据库表、迁移、依赖、环境变量或长期 feature flag。

## 5. v0.24.0：在相机图内移动 3D 框

### 5.1 交互合同

只有放大相机视图、选择工具、单选 `box_3d`、任务可编辑且标注未锁定时显示中心手柄。种框模式、点 Mask 模式、多选、只读、无标定或框中心在相机后方时不显示。

拖拽开始时记录原始 PSR、原图像素坐标和框中心的相机深度。移动过程中把当前像素按这个固定深度反投影回 lidar/world 坐标，只替换 `center`，`size` 与 `rotation` 保持不变。`handleEditPsr(next, false)` 更新 `draftPsr`，所以点云主视图、三视图和其他相机投影共享同一份草稿。松手调用 `handleEditPsr(next, true)`，只产生一条 PATCH 和一条 history；`Escape`、pointer cancel 或拖出后取消，不提交。

这里不默认锁地面。桌面、货架、机械臂末端和悬空物体都不满足地面约束。用户需要贴地时继续使用已有 `fitBottom`。固定深度让一次拖拽只改两个自由度，深度调整仍在主视图、三视图或数值面板完成。

### 5.2 几何实现

在 `geometry/projection.ts` 增加纯函数：

```ts
unprojectPixelAtDepth(
  pixel: readonly [number, number],
  depth: number,
  calibration: SensorCalibration,
): [number, number, number] | null
```

计算顺序固定为 `inverse(extrinsic) * inverse(rect?) * inverse(intrinsic) * [u * depth, v * depth, depth]`。矩阵仍按现有 row-major 合同读取；若使用 Three.js 求逆，必须通过 `Matrix3.set` / `Matrix4.set` 逐项装载，不能把 row-major 数组直接传给列主序 `elements`。

函数只接受有限正深度和可逆矩阵。无效输入返回 `null` 比抛异常更适合 pointer move 热路径，调用方保持原草稿并显示一次非阻塞提示。投影与反投影的 round-trip 误差以原图像素计不超过 1 px。

### 5.3 文件范围

- 修改 `apps/web/src/pages/Workbench/stages/three-d/geometry/projection.ts`，加入固定深度反投影。
- 修改 `apps/web/src/pages/Workbench/stages/three-d/geometry/projection.test.ts`，加入 identity、外参、rect、不可逆矩阵和 round-trip 用例。
- 修改 `apps/web/src/pages/Workbench/stages/three-d/CameraProjectionView.tsx`，绘制中心手柄并处理 pointer capture。
- 修改 `apps/web/src/pages/Workbench/stages/three-d/ThreeDWorkbench.tsx`，把选中框、可编辑状态和 `handleEditPsr` 传给放大相机视图。
- 扩展 `apps/web/e2e/tests/workbench-pointcloud-edit.spec.ts`，验证一次提交、撤销和跨视图同步。

不新增 hook 或 mutation abstraction。现有 `draftPsr`、`handleEditPsr`、`updateAnnotationWithHistory` 已覆盖拖拽草稿、提交和撤销。

### 5.4 验收门

- 一次拖拽只有 pointerup 的一条 PATCH，请求体仍只有 `geometry.type=box_3d`。
- 拖拽期间其他相机投影和三视图实时移动，尺寸与旋转逐位保持。
- 无标定、只读、锁定、多选和种框模式没有编辑手柄，也不能通过事件旁路提交。
- 投影 round-trip 误差不超过 1 px。
- 用 30 个车辆、桌面物体和货架物体样本做固定任务计时，中心位置微调的中位耗时较当前主视图操作下降至少 20%。该数据记录在计划 Outcome，不新增产品遥测。

## 6. 原 v0.24.1：可信导出与多相机派生 2D（未实施，已延期）

> 本节是历史草案，不是当前代码能力，也不再绑定 v0.24.1。若恢复该方向，必须新建带日期的独立计划，重新验证占位输出、文件范围和测试 oracle 后再实施。

### 6.1 后端共享投影

新增 `apps/api/app/services/pointcloud_projection.py`，只放两个前后端无法共享语言实现的纯函数：

- `transform_box_to_camera_psr`，用选定相机的 `extrinsic` 与 `rect` 把中心和朝向变换到 camera frame。
- `project_box_to_image_bbox`，生成八角点，按近裁剪面裁剪 12 条边，投影后计算 bbox，并在有宽高时裁到图像范围。

KITTI 和 scene 质检共用这两个函数，所以单独文件有两个生产调用方。测试 oracle 使用与前端 `projection.test.ts` 相同的标定 fixture，允许的像素误差不超过 1 px。

### 6.2 KITTI 规则

`POST /projects/{project_id}/export` 与批次导出增加可选 query 参数 `lidar_camera_role`。只有目标包含 LiDAR KITTI 时消费：

- 请求明确给出角色时，只能匹配 `TaskDatasetItemLink.role`，比如 `camera_front`。
- 未给出且所有导出帧只有一个完整标定角色时自动选择。
- 未给出且存在多个角色时，任务失败并提示选择相机；不能取字典中的第一个相机。
- 任一帧缺少该角色、合法标定、图片宽高或可见投影时，导出失败并列出首个问题帧。

`label_2` 的中心、`rotation_y`、`alpha` 与 bbox 都从选定相机标定计算，不再只做固定 ISO 到 KITTI 轴映射。`axis_frame` 不改变 KITTI 标准相机坐标。

新增 `GET /projects/{project_id}/lidar-camera-roles?batch_id=`，返回：

```json
{
  "roles": [
    {
      "role": "camera_front",
      "frame_count": 1200,
      "calibrated_frame_count": 1200,
      "sized_frame_count": 1200,
      "complete": true
    }
  ],
  "default_role": "camera_front"
}
```

Export Modal 仅在 LiDAR 项目选中 KITTI 时请求该端点并显示原生 `select`。只有一个完整角色时自动选中，多个角色不预猜。

### 6.3 COCO 派生 2D 规则

LiDAR 项目允许选择现有目标名 `coco`。它遍历每帧所有有标定且有尺寸的相机，为每个 frame-camera 组合写一个 COCO image，为可见 `box_3d` 写派生 bbox。输出只存在于 ZIP：

- `images[].file_name` 使用 `{camera_role}/{frame_key}/{source_name}`，避免多相机重名。
- `annotations[].attributes` 保留已有属性，并加入 `__source_box_3d_id`、`__track_id` 和 `__camera_role`。
- 完全在相机后方或裁剪后面积为零的框跳过，并在 `info.skipped_annotations` 计数。
- 未标定相机写入 `info.skipped_cameras`，不会生成看似有效的空 bbox。
- 数据库不创建 bbox annotation，也不改 `total_annotations`。

该序列化器沿用现有 COCO category、attribute 和 JSON 字段约定，但不把 LiDAR task 假装成 image task。实现放在 `exporting/lidar.py`，避免给 `ExportService.export_coco` 增加只服务于 3D 的分支。

### 6.4 nuScenes 规则

扩展 `LidarFrameExportCtx`，携带 `scene_id`、`frame_index`、`timestamp_us`、ego translation / rotation 和相机尺寸。`packaging.py` 按 chunk 批量加载 `SceneFramePose`，不按帧查询。

输出增加真实 `scene` 与 `sensor` 表，并修正以下字段：

- `sample.scene_token` 按 `scene_id` 分组，`timestamp` 取 `SceneFramePose.timestamp_us`。
- `sample.prev` / `next` 按同一 scene 的 `frame_index` 排序。
- `ego_pose.translation` / `rotation` 取持久化位姿。
- `sample_data.timestamp`、`prev` / `next` 与对应 sample 一致。
- `instance.first_annotation_token`、`last_annotation_token`、`nbr_annotations` 按 `track_id` 生成。
- `sample_annotation.prev` / `next` 按同一 instance 的帧序生成。

任一导出帧缺少 scene、frame index、时间戳或 ego pose 时，nuScenes 目标失败，错误进入 AsyncJob；同一任务里的 AAP JSON 与 pointmask 不受影响。README 明确这是 AAP 的 nuScenes-style 训练子集，不声称包含 map、log 等平台没有的数据。

### 6.6 验收门

- 搜索 `_kitti_bbox_placeholder`、`identity placeholder`、`"timestamp": 0` 和固定 `aap-scene` 均无生产代码命中。
- KITTI 使用明确相机后，3D 中心、yaw 与 2D bbox 对 oracle 的误差不超过 1 px / `1e-5`。
- 多相机 KITTI 未选择角色时失败，不产生 ZIP；单完整相机保持兼容。
- COCO 派生框与前端相机投影对同一 fixture 的差异不超过 1 px，数据库行数不变。
- nuScenes 两个 scene、每个至少三帧的 fixture 可还原 sample、pose、timestamp、track prev / next，不串 scene。
- AsyncJob cache key 已包含 `lidar_camera_role`，不同相机选择不能命中同一导出缓存。

## 9. 0.24.x 后的需求触发项

### 9.1 3D AI 候选

只有同时满足以下条件才立项：已有一个可调用的 LiDAR 或 RGB-D backend；能返回 `box_3d` 或 `point_mask_3d`；有至少 500 帧经人工确认的验证集；项目方明确需要候选接受、驳回和 lineage。

届时扩展现有 ML backend protocol 的输入模态和结果类型，继续复用 Prediction、review、lineage 与动态 capability，不新建模型注册中心，也不把某个 SAM3D 名称写死在平台协议中。

### 9.2 Embodied Episode Profile

只有出现已承诺的 LeRobot v3 或等价 episode 项目，并且同时需要相机、state/action、语言以及至少两类时序标注时才立项。

推荐映射保持简单：`Scene = episode`；Parquet / MP4 分片保持不可变；数据库保存 episode 边界、feature schema 和标注索引，不把高频 action 每步复制成关系表。首批新类型最多是 `episode_segment` 与 `pose_3d`，skill、subtask、contact 等先作为属性或事件评估，不一次性建完整 ontology。

## 11. 文档与 Outcome

每个版本实施时在同一提交更新对应 `docs-site` 页面与 `CHANGELOG.md` 的 `Unreleased`。各独立计划自行追加 Outcome；本 Epic 只在所有保留方向完成、重新排期或明确废弃后追加总 Outcome，不再用它承载版本实施明细。

本计划最脆弱的假设是：近期付费项目仍以 3D 几何真值为主要交付物，具身数据中的 action、language 和 skill 还不需要成为平台一级实体。若首个 0.24.x 项目实际只需要 RGB 多相机与动作序列，应停止扩展 `ThreeDWorkbench`，改为给 `video-mm` / `mm` 设计 Episode Profile。
