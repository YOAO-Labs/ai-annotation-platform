## 2026-07-10 回归实测 + 新发现（修订依据）

在双 RTX 3090(24GB) 上对 sam3.1_multiplex 做了直连回归 + 平台链路 E2E，结论直接重塑本 epic 的阶段边界：

**A. sam3-backend 直连（`curl localhost:8002/predict`，真 sam3.1_multiplex）——健康：**
- 前向跑通、输出键 `out_obj_ids`(N,)int64 / `out_binary_masks`(N,H,W)bool / `out_probs`(N,)float32 与解析假设吻合。
- 修掉一枚真 bug：`video_predictor.py` 的 `_pick_target_obj` 无种子/空 mask 兜底误读 `output_probs`（真键 `out_probs`），
  致 probs 兜底静默失效、退化取首个目标而非最高分（已修 + 单测 + 真模型验证）。
- **显存画像**：视频前向峰值随窗口帧数近似线性——基线权重 ~5.4GB，3 帧 9.4GB / 16 帧 18.9GB / **41 帧即 OOM@24GB**，
  约 0.85–1.3 GB/帧。主因是 tracker 把整窗每帧的 1008² backbone 特征 + 每目标 memory 常驻 GPU 做时序 memory-attention，
  再被 multiplex（≤16 目标槽）放大，**非权重本身**。→ 见阶段 B 显存约束。

**B. 平台链路 propagate（前端/API → runner → adapter）——发现路由洞：**
- 一个 `model_key="sam3_video"` 的 job，celery-worker-gpu 日志显示 3 个 `/predict` **全打到 `172.17.0.1:8001`
  （grounded-sam2）**，不是 sam3-backend(8002)。grounded-sam2 收到 sam3_video context 后按 **seed-bbox** 追踪、**忽略
  text**，返回貌似合理的 bbox → 静默假成功。
- 根因：`../../apps/api/app/services/video_tracker_runner.py` 用
  `get_project_backend(project_id)` 选后端，而 [`ml_backend.py:248 get_project_backend`](../../apps/api/app/services/ml_backend.py)
  只返回「项目显式绑定的 `ml_backend_id`」或「交互式 fallback」，**完全不看 `model_key`**。本项目绑定 grounded-sam2 →
  所有 tracker（含 sam3_video）都发去它。
- 前端一致：[`useWorkbenchShellModel.tsx:3096`](../../apps/web/src/pages/Workbench/state/useWorkbenchShellModel.tsx)
  `supportedTrackers = mlCapabilities.capability?.supported_trackers`——取的是**单个绑定/交互 backend** 的能力，
  grounded-sam2 不声明 sam3_video → 对话框正确灰置「未绑定后端」。**前端门禁是对的**，只是它如实暴露了「平台没有把
  sam3_video 绑给任何 backend」这个缺口。
- 结论：**sam3_video 的平台链路从未真正跑过 sam3-backend**。这不是回归，是 v0.21.19 里被推迟的 gating 依赖（per-tracker
  backend 选择）从未落地。**据此新增阶段 R，且它是阶段 B 真正 E2E 的前置。**

**C. 分窗窗口默认值已收窄（已落，非本 epic 阻塞）：**
- runner 分窗大小此前所有 tracker 共用 `VIDEO_TRACKER_WINDOW_SIZE_FRAMES=300`——对 sam3_video 意味着单窗可达 300 帧、
  远超 24GB（~35 帧即触顶）。已加 sam3 专用更小分窗 `VIDEO_TRACKER_SAM3_WINDOW_SIZE_FRAMES=16`（runner 按
  `model_key=="sam3_video"` 取较小值，sam2 的 300 不动），backend 侧 `SAM3_VIDEO_MAX_WINDOW_FRAMES` 默认 300→16 兜底。
  **注意**：此项的 E2E 验证仍卡在阶段 R——路由没通，就没法在真 sam3 上验证分窗；直连 8002 已验其显存必要性。

## 动机：三条能力线 + 一条路由线，撞同一批平台假设

| 能力线 | backend 现状 | 卡点 |
|---|---|---|
| **A · sam2_video 多目标** | vendor `SAM2VideoPredictor` 原生支持任意 `obj_id`、propagate 返回 `[num_obj,…]`；平台 wrapper 硬编码 `_OBJ_ID=1` 只取 obj[0]（`grounded-sam2-backend/video_predictor.py:62,254`） | 平台单 track 落库 |
| **B · sam3.1 multiplex 多目标** | `sam3.1_multiplex.pt` 是 Object Multiplex 多目标视频模型（128 目标 ~7x），backend **已建且直连可跑**（v0.21.19 PR3） | ① 平台单 track 落库 ② **路由没通（阶段 R）** |
| **C · detect-then-track**（相邻 epic） | 检测式追踪天然多目标 | 平台单 track 落库 |
| **R · tracker backend 路由**（新） | sam3-backend 声明 `supported_trackers:["sam3_video"]`、grounded-sam2 声明 `["sam2_video"]`——能力信息齐 | 平台按「单一绑定 backend」选，不按能力选 |

多目标三条线卡在同一个「单 annotation 单 track」硬假设；路由线卡在「一项目一 backend」的选择模型。二者独立、但**都必须先修，sam3_video 才既能到、又能多目标落库**。

## 核心洞察：数据模型已就绪，真瓶颈是 路由 + 落库分组 + 透传（带证据）

**好消息——大半改造面不存在：**

| 层 | 结论 | 证据 |
|---|---|---|
| **DB annotation/几何** | 多 track = 多 annotation 行，`video_track_bbox` 结构复用，**annotation 表不改** | 一个 Annotation = 一个 geometry = 一条 track（`_jsonb_types.py VideoTrackGeometry`，`track_id` 已是一等标识） |
| **协议契约** | `/predict` 返回带 `instance_id` 的 bbox 序列**已声明** | `capability_registry.py:288-296` |
| **前端画布/时间轴** | 已能渲染任意多 track、时间轴按多 track 聚合，**几乎零改** | `VideoKonvaStage.tsx filter(isVideoTrack)`；`videoTrackTimeline.ts buildGlobalTimelineDensity` |
| **前端几何回填** | job 完成靠 `invalidateQueries(["annotations",taskId])` 整体重拉，多 track 天然可见 | `useVideoTrackerJobs.ts:145-147,231-233` |
| **backend 多目标能力** | sam2 vendor 原生多 obj、sam3.1 天生 multiplex；直连已验 | 见「2026-07-10 回归实测 A」 |

**真瓶颈——路由 1 处 + 落库分组 1 处 + 透传 1 处（+ 模式 b 才需的入口/迁移）：**

1. **【新·核心】tracker backend 路由**（阶段 R）：`get_project_backend` → 按 `model_key ∈ supported_trackers` 选后端。
2. **后端 runner 分组落库**（阶段 0）：`apply_tracker_results` 按 `instance_id` 分组、新 instance 建新 annotation；
   跨窗续追从单 `last_bbox` → per-instance 字典。
3. **adapter 透传 instance_id**（阶段 0）：`TrackerFrameResult` 加 `instance_id`（现直接丢弃），分组逻辑放 runner。
4. **前端发起入口 + job 表外键**（仅模式 b）：`annotationId` 移出 URL、payload `seeds[]`、job↔多 track 归属——归阶段 M。

**现成参照（显著降风险）**：平台**已有一条跑通的多目标写路径**——检测式追踪 ingestion：backend 一次返回多条带
`track_id` 的 `video_track_bbox`，worker `for pred in results` 落成**独立 annotation**（`prediction.py to_internal_shape`、
`workers/tasks.py:314,878`），`_new_track_id`（`annotation_propagation.py:45-47`）是检测/交互/3D 共用的 track_id 工厂。
**runner 多目标化 = 把这套「多 track→N annotation」心智搬进 `apply_tracker_results`**，不是从零设计。

## 产品模式决策（沿用 2026-07-07）

- **模式 a · 自动发现**：用户框一个 / 给 text，backend 自动发现同类多目标各自成 track。sam3 text-driven /
  detect-then-track 的自然形态，**前端零 UI 改造**（重拉即见多 track）。
- **模式 b · 主动多 seed**：一次框多个目标主动发起。要动 URL 架构 + 多选交互 + job 归属，**归阶段 M（可选）**。

**✅ 已定：模式 a 优先，模式 b 单列后续。** 模式 a 吃到核心红利且前端零改，模式 b 增量、性价比低；模式 a 的多目标底座是
模式 b 的前置。**本 epic 阶段 R/0/A/B/U 全走模式 a，job 表 `annotation_id` 外键不迁移。**

- **R3 · 前端能力协商改并集**：sam3_video 可用性改看「项目**所有已启用** backend 的 `supported_trackers` 并集」而非单个

- **风险**：`is_interactive` 与 `supported_trackers` 是两套能力轴，别混；一项目多 tracker-capable backend 时选择需确定性
  （多个都声明同一 tracker → 取绑定优先 / 首个 connected，需定规则）。

  继承 label、跨窗连续）；`test_video_tracker_worker.py` 顺带补齐阶段 R 遗留的路由回归（backend 声明 `supported_trackers`）。
- **契约（2026-07-10 定 · 跨窗身份按模型两条腿，见决策 #7）**：阶段 0 的**落库层与跨窗身份机制解耦**——它只消费
  一个**全局稳定的 `instance_id`** 并按它分组落库，*怎么算出这个 id* 由阶段 B 各条腿负责：**B-mx（multiplex/text）**
  = 平台在窗边界帧 IoU 关联出的全局 id；**B-pvs（PVS 点/框）** = backend 的 **caller 指定 obj_id**（memory 传播，
  身份 by construction 稳定）。两条腿都让阶段 0 的 `_partition_results_by_instance` 拿到全局稳定 id → **阶段 0 无需改**；
  `primary` 仍标源种子对应实例。协议 / 各腿实现归阶段 B（见 [`ml-backend-protocol.md`](../../docs-site/dev/reference/ml-backend-protocol.md) §video_tracker「多目标落库」当前仅描述已实现的单实例 + 字段）。

  需分卡。
- **job/进度归属展示**：一个 job 产出多 track 时 badge 挂哪条 / 是否聚合（`useVideoTrackerJobs.ts byAnnotation`），需小设计。
- **UI/UX 改动别踩暗色/token 红线**：阶段 U 全部走语义类 + `--sc-*`（见 CLAUDE.md §6），方向/状态色配对 `dark:`。

  （`init_state`/`add_new_points_or_box(obj_id=…)`/`propagate_in_video`）拿干净 caller-obj_id 多对象——`handle_request(add_prompt)`
  是语义 prompt 风格（框像检测返多对象、每调用疑似 reset、点路径 spike 时报错），不适合逐对象精确种子。B-pvs backend 按直接 API 接。

- **三模型显存（B-pvs 引入）**：图像 sam3.pt + 视频 multiplex + **PVS(sam3.pt 权重)** 三者单卡（24GB）需 idle 卸载调度；
  PVS 与图像可能共享 sam3.pt 权重（待确认，若共享则增量小）。B-pvs 落地先确认 VRAM 画像。
