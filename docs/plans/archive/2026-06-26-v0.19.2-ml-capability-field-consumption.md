# v0.19.2 · ML 能力字段消费（resource_profile / output_attribute_types）

状态：定稿（finalized）。版本 **v0.19.2**，排在 v0.19.0 全局 backend 注册表之后。

## 范围决策（2026-06-29 定）

| WS | 决定 | 理由 |
|---|---|---|
| **WS1** `output_attribute_types` 落点校验（纯前端） | **进**（先行） | 非阻断、最低风险。`class` 档跳过 config-time 警告（taxonomy 几乎恒在，警告即噪音）。 |
| **WS2** dispatch-time 硬校验（422） | **进**，仅留两条硬挡 | 422 只留给「跑完必然空结果」的结构性误配。 |
| ~~WS2 第 3 条~~ `write.keys` × schema 对账 | **降级为 config-time 警告 → 并入 WS1** | schema 可能滞后/不全，硬挡会误伤合法配置；「可能错」归警告，「必然错」才归 422。 |
| **WS0** 管道补口 | **进**，随 WS2 顺手 | 5 行纯透传，全局编排选择器前置；但 WS2 取数走 `health_meta`，故不阻塞于此。 |
| **WS3** `batchable` 源阶段分块 | **不进 v0.19.2** | backend 顺序循环不堆 GPU batch，3a 收益仅 per-call overhead 摊销（毛估 5–15% wall-clock）；动核心失败/进度/取消语义风险最高；应与 3b 真 GPU 批量合并算总账。 |

## 背景

四个 ML backend 的 `/setup` 现已统一自报两个字段：

- `output_attribute_types`：半开放受控词表 `class / text / language / orientation`（`score` 已移除——置信度是 prediction 一等字段，不入「输出属性」语义）。分类/检测/文本分割声明 `["class"]`；交互分割 / 视频追踪 / box→mask 细化**留空**（透传或无类别产出）。
- `resource_profile`：`{device, batchable}`。批量模型 `batchable=true`；交互 / 有状态视频追踪 `batchable=false`；不填 `vram_gb`。

平台已持久化二者（`ml_capabilities.py:118,132` → `health_meta.capabilities`），但**消费很零散**：

| 字段 | 已被消费 | 空白 |
|---|---|---|
| `output_attribute_types` | 画布 `useCapabilityValidation.ts:103` 仅查 `"text"`；编排 `StageCard` 用 `schema \|\| types` 存在性粗判「产不产属性」；`ModelCard` 展示 | `class/language/orientation` 三种都没做落点校验 |
| `resource_profile` | 仅 `ModelCard.tsx:35` 展示 | `batchable` 完全没进调度/编排闸门；`device` 未用 |

管道缺口：`/instances` 端点 `_shape_models()`（`capability_instances.py:61`）**不透传** `resource_profile` 与 `supported_inputs`；项目级 `/capabilities` 端点二者都含，`StageCard` 走的是 `/capabilities`，故编排侧能拿到 `resource_profile`，走 `/instances` 的消费方（ModelMarket instances、未来全局编排选择器）拿不到。

## 目标

让这两个字段真正服务两个目的：**正确利用**（用对、跑更快）与**及时纠错**（配置期 / 派发期把静默空结果变成显式信号）。沿用本仓现成的两层模式：config-time 前端非阻断 warn + dispatch-time 后端 422 硬挡。

## 第 3 项前置确认：`/predict` 协议（已完成）

> 用户先要求确认的事项，结论先行落档，决定 WS3 的拆分。

**Wire 协议本身就是批量原生的，无需任何协议改动**：`ml_client.predict(tasks: list[dict], context)` → POST `{"tasks":[...]}`；四个 backend 全部 `for t in req.tasks` 接收 N 条，返回 `BatchPredictResponse{results:[...]}`（`yolo-backend/main.py:639-693`，gsam2/sam3/onnxtools 同构）。

worker 实际喂法分三种，只有源阶段没吃到批量：

| 调用处 | 现状 | 批量？ |
|---|---|---|
| 源阶段 `tasks.py:290` + 外层 `_run_batch:801 for task in tasks` | `predict([{单图}])` 逐图循环 | ❌ N 图 = N 次调用，每次 `tasks=[1]` |
| crop 分类下游 `tasks.py:405` | `predict(crop_inputs)`（单图所有父框的 crop 列表） | ✅ 已批 |
| box-seg 几何下游 `tasks.py:350` | `predict([{单图, prompts:[...]}])` | ✅ 已批 |

**第二关键事实——服务端顺序循环，非真 GPU 堆叠**：yolo `_run_predict:647 for t in req.tasks` 逐条 `predict_one(...)`（其余三家同 `for t in tasks`）。即使一次发 N 条，backend 也一条条跑，不堆 batch 张量。

故 WS3 拆两层：

- **3a（便宜，纯平台）**：源阶段按 `batchable=true` 分块发 `tasks:[...]`。收益 = 省 HTTP 往返 / 连接建立 / 每调用 context 校验 / Celery↔backend 延迟，N 次 → N/B 次。无需改 backend。
- **3b（贵，逐 backend，本计划不含）**：真 GPU 批量（每家 `predict_one` 堆叠张量），吃显存、按 backend 逐个立项。

## WS1 · `output_attribute_types` 落点覆盖校验（纯前端，及时纠错，优先）

把现在的 text-only 特例升级为统一规则：遍历 model 声明的每种 `output_attribute_type`，校验项目是否有承接位，缺失则发同款非阻断警告「採納后该属性丢失」。

| type | 项目需具备的承接位 | 是否发警告 |
|---|---|---|
| `class` | 类别 taxonomy（几乎恒在） | **跳过**（taxonomy 恒在，警告即噪音） |
| `text` | 文本属性字段（**已实现**，并入统一表） | 是 |
| `language` | 语言属性字段 | 是 |
| `orientation` | OBB / 旋转工具或属性 | 是 |

落点：
- 画布 `apps/web/src/pages/Workbench/state/useCapabilityValidation.ts:102-117` —— 把 `includes("text")` 那段改为遍历映射表。
- 编排 `apps/web/src/pages/AIPreAnnotate/utils/pipelineGraph.ts:stageWarning` —— 复用同一映射表。
- 编排再收紧一格：`StageCard.tsx` 当 `write.target="attributes"` 但所选 model 的 `types` 不含 `"class"` → 该 model 不该当分类下游（比现用 `is_interactive` 过滤更直接；box-seg/interactive 因 `types` 留空会被这条挡住）。

**并入（原 WS2 第 3 条降级而来）—— `write.keys` × `output_attribute_schema` 对账，config-time 警告**：StageCard `write.target="attributes"` 时，若用户选的属性键不在所选 model 自报 `output_attribute_schema` 的字段集合内 → 出非阻断警告「该键 model 可能不产出」。**只警告、不进 422**：schema 可能滞后或未报全，硬挡会误伤合法配置（「可能错」归警告，「必然错」才归 422）。schema 缺失时整条跳过（向后兼容）。

风险：低（纯前端、非阻断）。需确认 `score` 移除无残留消费方——已确认（仅 text 检查 + 存在性判断，见背景表）。

验收：模型声明 `types` 含某属性（`class` 除外）但项目无落点时，画布与编排各出一条非阻断警告；分类下游选到 `types` 不含 `class` 的 model 时 StageCard 给警示；`write.keys` 含 model schema 未声明的键时出对账警告。

## WS2 · dispatch-time 硬校验（后端 422，及时纠错）

把「静默空结果」变「明确报错」。在预标注路由（`apps/api/app/api/v1/projects.py`）对 `apps/api/app/schemas/preannotate.py::PipelineStage` 加两条执行能力硬挡（与 `supported_inputs` 几何可达性 422 的 route `projects.py:1417-1434` 同一处叠加）：

1. stage 所选 model `resource_profile.batchable=false` → 拒绝进批量预标流水线（今天 `is_interactive`+`composition!=composite` 已间接挡掉 interactive-seg/tracker，此条是更诚实的单一判据，防未来「`is_interactive=false` 但有状态」模型漏放）。
2. stage `write.target="attributes"` 但 model `types` 不含 `"class"` → 拒绝（避免跑完一批拿到全空属性）。

> 这两条都是「跑完必然空结果」的**结构性确定误配**，适合 422 硬挡。原计划的第 3 条（`write.keys` × schema 对账）属「可能错」，已降级为 config-time 警告并入 WS1，不在此处硬挡。

**取数硬约束**：校验侧必须从 `health_meta.capabilities` 读 `resource_profile` / `types`，**不能走 `/instances`**（后者已裁掉 `resource_profile`）。这也意味着 WS2 不阻塞于 WS0。

风险：中。须回归既有合法流水线不被误拒。

验收：构造上述两类误配，提交流水线 → 422 带可读 detail；既有合法多阶段配置仍通过。

## WS3 · `batchable` 驱动源阶段分块（**不进 v0.19.2，存档待立项**）

> 决策（2026-06-29）：**不进 v0.19.2**。依据见上「第 2 关键事实」——backend 服务端顺序循环、不堆 GPU batch，故 3a 推理总时长一秒不省，收益**只有 per-call overhead 摊销**（毛估 5–15% wall-clock，N 越大越划算）；而它是本计划唯一触及核心失败/进度/取消语义、改坏会静默吞结果的高危改动。收益/风险比最差，且与 WS1/WS2 零依赖。真要做应与 3b（真 GPU 批量）合并立 ADR 算总账，避免先改一遍执行路径、3b 再改第二遍。以下方案存档备查。

仅做 3a。把 `_run_batch`（`apps/api/app/workers/tasks.py:801`）的源阶段「逐图循环」改为：当源 model `batchable=true` 时按固定块大小（如 8）聚合多 task 成一次 `predict(tasks=[...])`。

适用边界（重要）：**只对单阶段批量任务**或**多阶段流水线的源阶段**干净适用；下游 crop/几何阶段依赖单图检测结果，天然逐图，不在本 WS。

必须一并处理的副作用（现状均为逐图粒度）：
- 失败粒度 `tasks.py:807-847`：现每图独立 try/except 落库；分块后需把块内单条失败拆回逐 task 的 failed 记录（不能整块失败）。
- 进度 `tasks.py:851`：现 5% 步长按图推进；改为按块完成推进。
- 取消 `tasks.py:802`：现每图检查；改为每块边界检查（取消延迟 ≤ 一块）。
- 块大小：配置项（env），默认保守（如 8），留 1 退化为现状。

不含：3b 真 GPU 批量（backend 改动，单独 ADR + 逐 backend 计划）。

风险：中高（触及核心批量执行路径 + 失败/进度/取消语义）。建议先以单阶段检测任务做基线压测，量化 N 次→N/B 次省下的 wall-clock，再决定是否推进。

验收：单阶段 detection 批量任务在 `batchable=true` 下走分块路径，块内单图失败仍产生独立 failed 记录，进度/取消行为与逐图版语义等价（粒度放宽到块）；`batchable=false` 或块大小=1 时逐字退化为现状。

## WS0 · 管道补口（进，随 WS2 顺手）

`_shape_models()`（`apps/api/app/services/capability_instances.py:61`）放行 `supported_inputs`（以及 `resource_profile`），使走 `/instances` 的消费方也能拿到。

依据见下方「附录 · 全字段消费 sweep」：`supported_inputs` 是**唯一的字段流缺口**——它本身已是带真 422 的权威投递契约（`projects.py:1417`），只是 `/instances` 这条线被裁掉，导致 ModelMarket instances 与未来全局编排选择器拿不到。故从「可选铺路」提为**推荐**。若 WS2 取数走 `/capabilities`/`health_meta`，则 WS2 本身不阻塞于此，但全局编排仍需要它。

## 排期与依赖

本计划 v0.19.2 落地范围 = **WS1 + WS2 + WS0**，WS3 出范围。

- WS1 独立、最便宜、风险最低 → 先行（含从 WS2 降级而来的 `write.keys` 对账警告）。
- WS2 紧随 WS1；取数走 `health_meta.capabilities`，故不阻塞于 WS0。
- WS0 随 WS2 顺手做（5 行透传，全局编排选择器前置）。
- WS3 出范围，存档待与 3b 合并立 ADR。

## 暂缓 / 不在范围

- `resource_profile.device` 路由（GPU/CPU 队列、并发度）：归 v0.19.0 registry + 调度。
- 3b 真 GPU 批量：单独 ADR + 逐 backend 计划。
- `output_attribute_schema` 驱动的属性**自动映射**：另议（现仅用于「从 backend 导入属性」；本计划只在 WS1 做 `write.keys` 对账**警告**，不做自动映射）。
