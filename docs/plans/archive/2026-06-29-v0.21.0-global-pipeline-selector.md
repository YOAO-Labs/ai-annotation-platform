# v0.21.0 · 全局跨项目编排选择器

状态：草案(draft)。minor 版本——v0.19.2 WS0 的**正主消费方**。把现在逐项目、临时的编排搭建
升级为全局、可命名、可复用的跨项目流水线选择器。是这一系列 plan 的 capstone。

## 背景

- v0.19.2 WS0 让 `/instances` 透传 `supported_inputs` + `resource_profile`,计划里写明这是
  **「全局编排选择器的前置」**——前置已就位,选择器未建。
- 现状编排(`StageCard` / `ProjectDetailPanel`,`apps/web/src/pages/AIPreAnnotate/`)走**项目级**
  `/capabilities`,每个项目从零搭流水线,无法跨项目复用「检测→车辆属性」这类常用编排。
- v0.18.27 落地方案 A(`Project.preannotate_pipeline` 单列 JSONB,一项目一条,
  `apps/api/app/db/models/project.py:53-55`)。ROADMAP §75 明确升级触发条件是「≥2 例多命名
  或跨项目复用需求出现」,并警告「不要因『灵活性』提前建表」。

### 触发用例(承接 ROADMAP §75 触发线)

命名沿用 M-N 供后续跟踪:

- **M-1** 「detect → 车辆属性」(乘用车项目)
- **M-2** 「detect → OCR」(车牌/工牌项目)
- **M-3** 「detect → 属性 + tracking」(视频侧,下游 v0.21.1 消费)

三条已由业务侧提出,命中触发线,非「灵活性推测建表」。

## 目标

基于全局 `/instances` 建一个编排选择器:从全局池选 backend/model 搭流水线,
存为**命名可复用**的编排(三级 scope),跨项目套用。把 WS0 数据用起来。

## 沿用的既有决策(不新开 ADR)

### ADR-0023 项目模板 vs 克隆策略

本版编排模板全部沿用其骨架:

- **三级 scope**:`private` / `organization` / `public`(显式 enum 列,**不用 nullable 判语义**)。
- **copy-on-write**:套用即 `deepcopy`,模板改不追杀已实例(`docs/adr/archive/0023-project-template-vs-clone.md:29`,
  显式否决 by-reference,§Alternatives)。
- **权限判据**:`assert_template_visible` / `can_edit_template` / `assert_can_create_scope`
  (`apps/api/app/services/project_template.py:43-80`)直接抄成 pipeline 版。
- **写权限**:`public` 仅 super_admin;`organization` 组织成员;`private` 由创建者/超管。
- **usage_count 运营信号**:沿用。

### ADR-0044 全局注册表 + 项目启用

本版编排「未启用 backend」降级沿用其二层模式:

- **派发期硬拦**:404 backend 未启用(`apps/api/app/api/v1/projects.py:1557-1560`)。
- **保存期软提示**:能力软 warning(`_compute_pipeline_capability_warnings`,`projects.py:1490-1541`)。
- **套用期同姿态**:套用瞬间校验,缺则 422 + 提示去启用(不新决策)。

## 收尾优化 · 编排 UI 对齐(增补,2026-07-02)

WS0–WS3 已落地,但**全局编排页与项目编排面板的搭建能力对不齐**:全局页画布禁用了加子/改父、右列无 Inspector、只能保存 `public`、无库管理入口。走 rule-of-three 前的**方案 B(渐进补齐)**+ 一层轻量 refactor(不下沉整套 `<PipelineComposer>`)。

### 差距清单(SSOT,后续 PR 按此闭环)

- **DAG**:全局页 `PipelineGraphCanvas` 传 `onAddChild={() => undefined}` / `canReparentConn={() => false}` → 只支持"源 + 直挂 root 兄弟"扁平结构;项目页支持 `MAX_DEPTH=3` 受限树。
- **Stage 参数 Inspector**:全局页无右列检查器,`globalStagePayload` 硬编码 `roi.pad=0.05` / `input.mode` 按 `bbox_prompt` 自动切 / `write.target` 按 `isGeometryModel` 自动切,`class_filter` / `write.keys` / `label` / `model_variants` / `params` 全丢。
- **校验**:全局页无 `hasKeyConflict` 检测(下游 write.keys 不可配也检测不了);保存时不跑 `stageWarning` 汇总。
- **Scope**:全局页写死 `public` disabled;项目页只有 `private` / `public`——两边都缺 `organization`(后端 `pipeline_template.py` 已支持三级)。
- **命名库管理**:全局页只保存不管理,没"我的编排列表 → 编辑 / 删除 / 展示 usage_count / 套用到某项目"。
- **默认名**:全局"公共默认编排" vs 项目"项目默认编排",预填名冲突,应统一为 placeholder。

### 落地做法(4 步,不动 API/DB)

**为什么走方案 B**:`usePreannotateConfig` 深度依赖 `projectId`(拉 `useProject` / `aliasFrequency` / `mlBackendsApi.setup+capabilities` / `useUpdateProject`),让 `StageCard` 全套 project-agnostic 化=方案 A 级别改动,与"渐进补齐"矛盾。方案 B 只共用**状态机层**(纯计算),Inspector 分两版:项目侧继续用 `StageCard`(全能力),全局侧用新增精简版 `<GlobalStageInspector>` 只暴露编排本身参数。

1. **抽 `usePipelineComposer(context)` hook**(纯搬 state,不动 UI)
   - 位置:`apps/web/src/pages/AIPreAnnotate/hooks/usePipelineComposer.ts`
   - 搬 `ProjectDetailPanel` 里的 `stagesGraph` / `selectedSid` / `stagePayloadsRef` / `stageCapsRef` / `stageTick` / `addStage` / `removeStage` / `onReparent` / `canReparentConn` / `downstreamPayloads` / `payloadBySid` / `conflictInfo` / `allDownstreamReady` / `onStageChange` / `onStageCaps`。

## 收尾优化 · 再修正(2026-07-02):三格候选与项目侧同源

上面「收尾优化 · 编排 UI 对齐」实现里,`GlobalStageInspector` 三格类别/属性键**误做成"逗号分隔自由文本 + 裸填 index"**,理由写成"全局池无项目类别表"。**这条理由读错了代码**:重看 `StageCard` / `usePreannotateConfig` / `PreannotateConfigForm` 后确认——项目侧 StageCard 里,三格的候选**真源都是 model / backend 自报**,项目类别 / 项目 attribute schema 只是**最后回落**候选,payload 层与项目类别**从不耦合**(存的是 model 原生 index 或纯字符串,`ChipMultiSelect allowFreeText` 允许任意值)。也就是说编排本来就是与项目类别解耦的,是这一系列 plan 的地基之一。

- 源阶段 `class_filter: number[]`:项目侧从 `geometricModel.classes`(model 自报原生类别表)勾选 index。**全局池 `CapabilityInstanceModel.classes` 已经带这份数据**,全局侧完全可以同 UX 勾选,不必让用户裸填数字。
- 下游 `parent_class_filter: string[]`:项目侧候选 = 上游 model 输出类名 > 项目类别回落 > `allowFreeText`。全局侧只缺"项目类别回落"这条(与解耦初衷一致,应保留缺失),其余两条都能对齐。

## 收尾优化 · 再修正 2(2026-07-02):补 model_variants,params 延后

深调 payload 全字段后发现,「三格 chip」只补了类别/属性键,**仍漏两个字段**——用户复核时点出:

| payload 字段 | 项目侧 | 全局侧(修前) | 数据源在全局池? | 处理 |
|---|---|---|---|---|
| `model_variants`(version/size/lang/series 轴) | VariantSelector | ❌ 完全没有 | ✅ `/instances` **已下发** `supported_variants`+`variant_combinations`+`default_variants`(`ml_capabilities.py:88-89,118-128` 注释「全局编排选择器需要」保留了它) | **本次补** |
| `params`(conf/iou 等推理阈值) | SchemaForm(`/setup.params`) | ❌ 完全没有 | ❌ `/instances` 按设计裁掉(schema 注释「不暴露 url / params 等运维信息」);只项目作用域 `/projects/{id}/ml-backends/{bid}/setup` 有 | **延后到套用时**——copy-on-write 本就落到项目,项目侧 StageCard 拉 `/setup` 配阈值;要全局配需改后端(把 params schema 透进 instances 或加全局 setup 端点),本版不做 |

### 变体修正做法

- `GlobalStageInspector` 挂 `VariantSelector`(源+下游共用一段):数据取 `selectedOption.model.supported_variants`(结构与 VariantSelector 要的 `MLBackendSupportedVariantGroup` 一致,直接传)、`variant_combinations`、`default_variants`。`VariantSelector` 路径 A 只吃 `supportedVariants`、不依赖 params schema,故无项目依赖。
- `variantValue` state 承载用户选择;payload 组装时每轴取值 `variantValue[k] ?? default_variants[k]`,只保留本 model 声明的轴(与项目侧 `StageCard` 过滤语义一致),空=不下发 `model_variants`(后端按启动默认解析)。
- 加载编辑回填:reverse-init 从 `value.model_variants` 灌 `variantValue`;不设「换 model 重置为 default」的 effect,避免与 load 回填互相 clobber(defaults 在 payload 组装期兜底即可)。

### 验收(补)

- 全局页选中带变体轴的 model(如 yolo size 轴)→ Inspector 出「模型变体」选择器;未手改时 payload `model_variants` 取 model `default_variants`;改选后取用户值。
- `params` 全局侧不出现;文档/hint 说明「阈值等推理参数在套用到项目后由项目侧配」。

## 收尾优化 · 再修正 3(2026-07-02):roi/input/write 改为内生派生

用户复核截图指出:`roi.mode` / `input.mode` / `write.target` 在项目侧 StageCard **是内生的**——选完下游 model 后由其 task 定死,**从不给手选下拉**。之前 GlobalStageInspector 把这三个做成手选 `<select>` 是错的:用户能选出 model 不支持的组合(如给分类模型手选 `write.target=geometry`)。

项目侧派生逻辑(`StageCard.tsx` payload 构造,逐条复刻):

| 下游 model | 判据 | roi.mode | input.mode | write.target |
|---|---|---|---|---|
| 检测 | `task=detection && !is_interactive` | crop | crop | geometry |
| 分割 | `task=segmentation && prompts⊇bbox && !is_interactive` | geometry | (省略) | geometry |
| 识别 | `task=ocr && composition≠composite && !is_interactive` | crop | (省略) | attributes |
| 分类 | 其余 | crop | (省略) | attributes |

### 修正做法

- 删掉 `roiMode` / `inputMode` / `writeTarget` 三个 state 与对应 `<select>`;新增 `deriveDownstreamShape(model)` 纯函数(判据同上表),返回 `{role, roiMode, inputMode?, writeTarget, isAttributes}`。
- payload 里 roi/input/write 全部取 `shape`(input 仅检测下游显式下发、其余省略交后端烘焙,与 StageCard 一致);`write.keys` / `label` 仅 `isAttributes`(分类/识别)时出字段。
- UI 加一行只读「阶段类型」展示 `role · ROI x · 投递 y · 写回 z`,让用户看清将发生什么但不能改。
- 反向初始化(load-edit)不再回填 roi.mode/input.mode/write.target(选中 model 后自动派生一致)。

至此**全局侧手配字段 = 项目侧手配字段**:模型 / 变体 / 类别(源白名单 + 下游父框)/ write.keys / label / ROI pad;内生字段两侧同派生;仅 `params` 延后到套用时(数据源不在全局池)。
