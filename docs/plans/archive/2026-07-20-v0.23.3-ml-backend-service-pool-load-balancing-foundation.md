## 1. 结论

v0.23.3 新增一等 **ML Backend 服务池**，把“项目选择一个逻辑能力”和“平台选择一个物理实例”拆成两个明确步骤：

```text
项目 / pipeline stage 请求 service_pool_id
                  │
                  ▼
      MLBackendRouter 原子选择实例
      ├── pool / member 配置与能力兼容
      ├── active / draining / disabled
      ├── health / circuit / max_concurrency
      └── Redis route lease + 加权调度
                  │
                  ▼
       selected registry instance_id
                  │
                  ▼
   既有 MLBackendClient + GPU arbitration
                  │
                  ▼
 Prediction / FailedPrediction / AsyncJob / audit
 同时记录 requested_pool_id + selected_instance_id
```

本版本必须交付**真实请求路由**，不是前端把若干 URL 分组，也不是把 GPU 仲裁改名：

1. `ml_backend_registry` 继续代表一个物理实例，ID、URL、鉴权、health、GPU claim 和 GPU lifecycle identity 不变。
2. 新增服务池、唯一成员关系和项目池绑定；项目、pipeline 和用户偏好以 pool id 为配置真值。
3. 每次推理先由跨进程一致的 router 选择实例并获得 route lease，再进入现有实例 transport 与 GPU 仲裁。
4. 默认只实现一种生产策略：**平滑加权轮询（smooth weighted round robin）+ per-instance 并发上限**。
5. route lease、traffic draining 和被动熔断独立于 GPU request lease、GPU eviction drain 和模型 residency。
6. 不做透明跨实例重试，避免预测重复、状态会话破坏和非幂等副作用；失败只影响后续选择。
7. 同步交付 topology、runtime snapshot、drain / resume 和路由指标合同，作为 v0.23.4 的硬前置。

v0.23.3 是后端架构与第一方调用链切换版本。模型市场「注册管理 / 运行时观测」的完整池化 UI 留给 v0.23.4；本版本只做保证项目选择、创建向导和现有页面不失效所需的最小前端兼容。

## 2. 当前基线审计

### 2.1 当前对象层级

| 当前对象                               | 当前语义                                           | 负载均衡缺口                        |
| -------------------------------------- | -------------------------------------------------- | ----------------------------------- |
| `MLBackendRegistry`                    | 一行 = 一个唯一 URL、能力快照、并发配置、GPU claim | 没有逻辑服务池或成员关系            |
| `ProjectMLBackend`                     | 项目直接启用 registry 实例                         | 项目无法绑定一个多实例能力          |
| `Project.ml_backend_id`                | 项目主实例                                         | 主配置与物理实例耦合                |
| `preannotate_pipeline[].ml_backend_id` | 每阶段精确实例                                     | stage 不能在等价副本间选择          |
| 用户 AI 偏好中的 backend id            | 变体、模型、交互后端按实例分桶                     | 副本扩容会复制偏好或漂移            |
| `Prediction.ml_backend_id`             | 实际生成结果的物理实例                             | 缺少 requested pool 溯源            |
| `FailedPrediction.ml_backend_id`       | 失败发生的物理实例                                 | 无法区分池请求和实例失败            |
| `AsyncJob.payload.ml_backend_id`       | 请求时指定的实例                                   | 没有 pool / selected instance 双 ID |

### 2.2 当前请求选择

- `get_project_backend()` 优先 `Project.ml_backend_id`，否则取第一个 connected interactive 实例。
- tracker 能力匹配后返回显式绑定实例或 `supporting[0]`。
- 同步 API 直接按 backend id 构造 `MLBackendClient`。
- batch worker 在 job 启动时 `db.get(registry_id)`，源阶段整批复用同一实例；pipeline 下游阶段也按 `ml_backend_id` 逐一加载实例。
- 创建项目、项目启用、AIPreAnnotate、保存 pipeline、用户偏好和重试都传递 registry id。

这些路径没有原子实例选择、权重、公平性、跨进程 inflight、traffic drain 或 circuit breaker。

### 2.3 GPU 仲裁不是负载均衡

ADR-0049 和 v0.22.4 明确不做同一 backend 多副本、负载均衡和 scale-out。GPU arbitration 的职责是：在**实例已经确定之后**，按 `backend_registry_id + gpu_resource_id` 管理显存预算、request lease、卡级队列、驻留和驱逐。

因此：

- route lease 不能复用只在 GPU enforce 下完整生效的 GPU request lease。
- CPU 实例、GPU off / observe 模式和无 GPU claim 的实例也必须参与路由并发控制。
- traffic draining 只阻止新请求选中实例；GPU residency draining 是显存驱逐生命周期，二者不得共享状态字段或 ACK。
- 最终 selected registry id 必须原样进入 GPU dispatch，不能把 pool id 当 GPU backend identity。

### 2.4 当前观测缺口

- `/admin/ml-integrations/observe` 逐 URL 探测 health / setup，没有 pool、weight、routable、selection 或 route inflight。
- `ml_backend_request_duration_seconds` 只有 backend id / outcome，无法还原池级分布。
- `extra_params.max_concurrency` 在 off / observe 下主要是进程内 semaphore，不是跨 API / Celery 的全局路由容量。
- GPU `/gpu-resources` 的 backend / card queue 只表达 GPU 准入，不是路由队列。

## 3. 目标、非目标与不变量

### 3.1 目标

- 建立 service pool → registry instance 的一对多模型，一个实例只能属于一个服务池。
- 迁移项目启用、主 backend、pipeline stage 和用户偏好到 pool id。
- 建立跨进程原子选择与 route lease，统一约束 API、Celery 和视频 / pipeline 调用。
- 支持成员权重、per-instance max concurrency、active / draining / disabled 和新鲜 health 门控。
- 支持 transport 失败的被动熔断，使后续请求绕开暂时不可用实例。
- 保留实例级 GPU 仲裁、能力快照、鉴权、生命周期和历史 prediction 溯源。
- 所有新请求记录 requested pool 和 selected instance 双 ID。
- 提供 pool CRUD、成员管理、项目池启用、drain / resume、topology 和 runtime snapshot API。
- 建立 off / observe / enforce 灰度模式和 fail-closed enforce 语义。
- 保持旧实例 ID 请求的有限兼容，使 SDK / 旧 Web 在迁移窗口内可解析到对应 pool。
- 同步 OpenAPI、正式文档、环境变量文档、CHANGELOG 和版本源。

### 3.2 明确不做

- 不做 autoscaling、自动注册副本、服务发现、跨节点编排或 Kubernetes controller。
- 不做区域 / 可用区感知、数据本地性、成本路由、延迟预测或自适应权重。
- 不同时提供多种调度算法；首版只实现 smooth weighted round robin。
- 不做全局路由等待队列；全部可用实例达到并发上限时直接返回结构化 503。
- 不做自动跨实例 retry、hedged request 或 speculative execution。
- 不迁移正在运行的 tracker / session；有状态执行单元在选定实例上保持 pin。
- 不把不同 capability、模型目录或参数 schema 的实例强行放进同一池。
- 不把 warmup、reload、unload、health check 等实例生命周期动作自动负载均衡。
- 不删除现有 registry CRUD、实例 health / unload API 或旧请求字段；清理另行排期。
- 不重构模型市场完整管理 / 观测 UI；该工作属于 v0.23.4。
- 不修改 Backend `/health`、`/setup`、`/predict` wire protocol 来承载平台内部路由状态。

### 3.3 冻结不变量

1. pool id 是逻辑请求身份；registry id 是物理执行身份，二者永不互换。
2. 一个 registry instance 同时最多属于一个 service pool。
3. 一个 service pool 的全部 active 成员必须通过 routing capability fingerprint 校验。
4. 项目只能请求已启用的 pool；router 不能越过项目绑定选择实例。
5. 只有 `traffic_state=active` 的成员可接收新 route lease。
6. draining 成员保留既有 lease，不接收新 lease；inflight 归零后才能 disable、移出或普通 unload。
7. route lease acquire / heartbeat / finish / cancel 使用 Redis 原子合同；进程退出最终由 TTL 回收。
8. Redis 在 enforce 下不可用时 fail closed；不能静默直连 `legacy_instance_id`。
9. GPU dispatch 始终使用 selected registry id，现有 generation / fence / membership 不池化。
10. 单阶段 Prediction / FailedPrediction 的 `ml_backend_id` 表示 selected instance，新增字段表示 requested pool；多阶段聚合必须另存每阶段 / 调用的双 ID，不能把 root instance 冒充全部 shape 的生产者。
11. 没有真实指标时返回 unknown / null，不把缺失值解释成 0 或健康。
12. 被动熔断只作用于后续请求，不重放已经失败的非幂等预测。
13. 非空且 enabled 的 pool 必须有 `legacy_instance_id`，且它必须是本池成员；它只服务 off / observe 兼容，不参与 enforce 优先级。空 pool 只能 disabled。
14. pool / member / weight / traffic state 任何变更都单调增加 `routing_generation`，旧 generation 不得 acquire。

## 4. 架构决策与 ADR

P0 新增 `docs/adr/0050-ml-backend-service-pools-and-request-routing.md`，至少冻结：

- 为什么在 ADR-0044 的全局实例注册表之上增加服务池，而不是改变 registry 行语义。
- 为什么 pool / instance 使用双 ID，prediction 为什么保留实例溯源。
- 为什么一个实例首版只能属于一个 pool。
- 为什么首版选择 smooth weighted round robin，而不是随机、least latency 或多策略插件。
- 为什么 routing ledger 与 GPU arbitration ledger 分离。
- 为什么不做透明 retry。
- 为什么项目绑定迁移到 pool，生命周期控制仍定位 instance。
- migration 的 forward-only 条件和旧 ID 兼容窗口。
- v0.23.4 如何只消费 topology / runtime contract，不复制 router 判定。

ADR 被接受之前可以完成 inventory、fixture 和实验脚本，但不得合并生产 schema 或请求切换。

## 5. 目标数据模型

### 5.1 `ml_backend_service_pools`

| 字段                      | 约束与语义                                                                                                                         |
| ------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| `id`                      | UUID PK，逻辑请求稳定身份                                                                                                          |
| `name`                    | 显示名；不作为 join key                                                                                                            |
| `enabled`                 | 全局接流开关；显式创建的空 pool 默认 false，singleton backfill / 自动创建按既有状态设置                                            |
| `routing_policy`          | 首版只允许 `smooth_weighted_round_robin`                                                                                           |
| `legacy_instance_id`      | nullable FK → registry；非空 enabled pool 必须指向本池成员，仅供 off / observe 实际 dispatch 与受控 downgrade，不影响 enforce 权重 |
| `routing_generation`      | 正整数、单调递增；pool / member / weight / traffic state 变更时同事务推进                                                          |
| `capability_fingerprint`  | 路由相关能力规范化摘要；无可信快照时为 null 且池不可路由                                                                           |
| `capability_snapshot`     | 池级 canonical capability，只保存路由相关字段                                                                                      |
| `created_at / updated_at` | 审计与 topology 新鲜度                                                                                                             |

不在池表保存 URL、auth token、GPU claim、model residency 或实例 health。

### 5.2 `ml_backend_pool_members`

| 字段                      | 约束与语义                                          |
| ------------------------- | --------------------------------------------------- |
| `id`                      | UUID PK                                             |
| `pool_id`                 | FK → service pool；`(pool_id, registry_id)` unique  |
| `registry_id`             | FK → registry；单列 unique，保证实例只属于一个 pool |
| `traffic_state`           | `active / draining / disabled`，DB CHECK            |
| `weight`                  | 1..100，默认 1；仅影响分配比例，不突破实例并发上限  |
| `created_at / updated_at` | 配置变更时间                                        |

删除 registry 前必须先完成 drain、inflight=0、GPU retirement 和成员移除；若它是 `legacy_instance_id`，还必须先显式选择另一个 quiescent 成员接替，或把空 pool 原子置 disabled 并清空该指针。FK 使用 RESTRICT，不能靠 cascade 绕过控制线。

### 5.3 项目绑定

将 `project_ml_backend` 迁移为 `project_ml_backend_pool`：

- `registry_id` 改为 `pool_id`，唯一约束变为 `(project_id, pool_id)`。
- `enabled` 和项目级 `default_variants` 保留，但覆盖语义改为 pool 级。
- `Project.ml_backend_id` 迁移并重命名为 `ml_backend_pool_id`，成为项目主服务池。
- 项目启用和主池必须一致；禁用主池时显式清空或要求先换主池，不能留悬空引用。
- disabled、空成员或无 capability fingerprint 的 pool 可以被超管预配置，但不能被项目启用。

### 5.4 请求与结果溯源

- `Prediction.ml_backend_id`：单阶段保存 selected registry instance；多阶段聚合行保存 root stage selected instance，并明确列语义不是全部 shape producer。
- `Prediction.ml_backend_pool_id`：新增；单阶段保存 requested pool，多阶段保存 root stage pool。
- `PredictionMeta.extra.pipeline.selections[]`：保存 stage / invocation 的 pool id、selected instance id、operation 与 shape / result 关联；同一 Prediction 聚合多个实例结果时以此为完整 lineage。
- `FailedPrediction` 保存失败所在 stage / pool + selected instance；若选择前失败，instance id 可为 null，不能一律写 root instance。
- `AsyncJob.payload / result`：新任务写 `ml_backend_pool_id`、每阶段 pool id，以及 selection 汇总；实例级失败记录 selected instance。
- audit：触发事件写 pool id；实际调用 / 失败 / drain 事件写 pool + instance。
- 结构化日志统一字段 `service_pool_id`、`backend_registry_id`、`route_lease_id`、`routing_outcome`。

### 5.5 JSONB 和用户偏好

必须盘点并迁移：

- `projects.preannotate_pipeline[].ml_backend_id` → `ml_backend_pool_id`。
- `projects.default_variants` 的 backend key → pool key。
- `users.preferences.ai.params_by_backend`。
- `users.preferences.ai.model_by_backend`。
- `users.preferences.ai.interactive_backend_by_project`。
- `users.preferences.ai.secondary_by_model` 内所有 backend 引用。
- AsyncJob 历史 payload 中可确定映射的 `ml_backend_id` 补 `ml_backend_pool_id`，原字段保留为历史实例证据。

所有 JSONB 迁移必须以 machine-readable registry → singleton pool 映射表驱动，不用名称或 URL 重算。

## 6. Alembic 迁移与兼容

### 6.1 一对一安全 backfill

迁移建议使用下一 revision（当前最新为 `0131`），分阶段执行：

1. 新建 pool / member 表和约束。
2. 为每条现有 registry 建一个 singleton pool，pool 名称取 registry 名称、`legacy_instance_id` 指向该 registry；生成并持久保存 exact registry → pool 映射。
3. 每个实例成为对应 pool 的 active、weight=1 成员。
4. 迁移 `project_ml_backend` 到 pool 关联，保留原关联行的 id、enabled、default_variants 和时间。
5. 增加并回填 `Project.ml_backend_pool_id`。
6. 增加 prediction / failed prediction 的 pool FK，并在父表 / 分区上验证。
7. 迁移 pipeline 与用户偏好 JSONB。
8. 为历史 AsyncJob 补可确定的 pool id，不改审计日志历史事实。
9. 建索引、FK、CHECK 后执行 orphan / cardinality / JSON shape 守卫。

backfill 完成后，每个原请求仍落到唯一原实例，行为必须与 v0.23.2 完全一致。只有管理员显式把新实例加入既有 pool 并切换 rollout mode 后，才产生多实例分配。

### 6.2 兼容边界

- 新 API 和第一方 Web / worker 使用 `ml_backend_pool_id`。
- 旧请求中的 `ml_backend_id` 先尝试解析为 legacy registry id，再解析其唯一 pool；响应增加弃用提示，但本版本不删除字段。
- lifecycle API 的 `{registry_id}` 永远继续表示实例，不套用上述别名。
- 旧 `/admin/ml-integrations/all` 保持实例列表，供 v0.23.3 现有模型市场页面继续工作。
- 项目设置和创建向导做最小切换，展示 pool 名称 / 成员数，提交 pool id；完整池管理留给 v0.23.4。
- SDK 若暴露推理 / 项目配置写路径，同步增加 pool 参数；旧 instance 参数走相同 resolver。

### 6.3 downgrade

在所有 pool 都是 migration 生成的 singleton、且没有新 pool / 多成员 / pool-only 配置时，可以按保存映射逆迁移。

一旦创建多成员 pool、变更 / 删除 legacy instance 或写入 pool-only pipeline / preference，downgrade 不再无损，迁移必须 fail closed 并提示 forward-only。不能把多成员配置静默压回任意实例。

## 7. Capability 等价合同

服务池表示可互换的逻辑能力，成员加入前必须执行新鲜 `/setup` 探测并计算 canonical fingerprint。

### 7.1 fingerprint 包含

- capability protocol version。
- model ids、task、modality、infra。
- model / weights version 或等价 build revision；首版不支持版本混跑 / canary。
- supported prompts / inputs / outputs / trackers。
- parameter JSON schema 中影响请求合法性的字段。
- variant axes、枚举和默认值。
- stateful / batchable / warmup 等路由相关能力。

### 7.2 fingerprint 排除

- URL、实例名称、auth、health 时间。
- GPU UUID、显存占用、temperature、compute 实时状态。
- model residency、cache、builder / borrower。
- 纯展示描述和不影响请求兼容的实例元数据。

### 7.3 变化处理

- 创建 pool 时以 seed instance 生成 pool snapshot / fingerprint。
- 加成员必须 exact match；不匹配返回 409 `ml_backend_pool_capability_mismatch` 和结构化 diff。
- active 成员后续 health 刷新发现 fingerprint 漂移时，原子改为 disabled，记录诊断和审计；不能继续路由后再由请求暴露错误。
- pool capability 变更必须在全部成员 disabled / quiescent 后显式执行，不自动取多数派。

fingerprint canonicalization、排序、缺省值和 SHA 算法必须有 golden fixture，前后端不重复实现。

## 8. 路由领域与依赖边界

新增 `app/services/ml_routing/`：

```text
ml_routing/
├── contracts.py       # pool / selection / lease / error 合同
├── capability.py      # canonical snapshot 与 fingerprint
├── policy.py          # eligibility 与 smooth weighted round robin 输入
├── ledger.py          # Redis keys、Lua acquire / heartbeat / finish / cancel
├── circuit.py         # 被动失败分类与 ejection 状态
├── router.py          # DB topology + ledger 编排，返回 RouteSelection
├── diagnostics.py     # topology / runtime 诊断
└── metrics.py         # pool / instance 路由指标
```

边界：

- `MLBackendRouter` 返回 selected `MLBackendRegistry` 与 route lease，不发 HTTP 请求。
- 既有 `MLBackendClient` 仍只负责一个实例的 transport、auth、local semaphore 和 GPU dispatch。
- router 可以依赖 registry model、routing ledger 和 capability；不得导入 API router 或 worker。
- `MLBackendClient` 不反向导入高层 router，避免新的循环依赖。
- 调用方使用 context manager / `try/finally` 保证 finish / cancel，并显式上报 outcome；同一 lease 只能提交一个终态。
- GPU arbitration 不导入 ml_routing；route selection 完成后单向调用实例 client。

禁止把全部实现塞回现有 `ml_backend.py` 或 `ml_client.py`，也不新增泛化 BaseRouter / repository 框架。

router 的候选构建顺序固定为：先验证项目已启用 pool 与 pool enabled，再从 DB 读取同一 `routing_generation` 下的 active member；registry 必须 connected、health 未过期、capability fingerprint exact match。Redis acquire 再原子排除 circuit open 与达到 max concurrency 的成员。任何一步不确定都返回结构化 reason，不回落到名称、URL 或 `legacy_instance_id` 猜测。

## 9. Redis routing ledger

### 9.1 原子合同

acquire Lua 在一个原子步骤完成：

1. 校验 pool / candidate generation。
2. 清理过期 route lease。
3. 校验调用方传入的 active / fresh / capability-compatible candidates，并排除 circuit open 和达到 max concurrency 的实例。
4. 对剩余候选执行 smooth weighted round robin。
5. 写入 exact lease id / pool / instance / owner / operation / expiry。
6. 更新 current weight、selection counter 和运行时 bucket。
7. 返回 selected instance 或结构化 rejection reason。

heartbeat 只能延长 exact 未过期 lease，不能改变 pool / instance / owner。正常终态使用 `finish(lease_id, outcome, duration)` 原子记录 metrics、更新 passive circuit 并释放；caller cancel 使用不计 transport failure 的 `cancel`。两者都必须 exact、幂等，重复终态返回同一稳定结果，不能重复累计指标。

### 9.2 推荐 key namespace

```text
ml-router:v1:pool:{pool_id}:state
ml-router:v1:pool:{pool_id}:member:{instance_id}:leases
ml-router:v1:lease:{lease_id}
ml-router:v1:pool:{pool_id}:member:{instance_id}:circuit
ml-router:v1:pool:{pool_id}:metrics:{bucket}
```

key、KEYS / ARGV 顺序、TTL、返回码和 Lua SHA-256 在 P1 冻结 golden；不能与 `gpu-arbiter:*` namespace 交叉。

`metrics:{bucket}` 使用固定分钟桶和有限 histogram 边界，至少保存 selection、success、error、rejection 和 duration buckets；bucket 过期自动回收，不保存 request / lease 级高基数明细。runtime snapshot 聚合最近窗口并返回 request count、error rate 和近似 P95，同时明确窗口起止和精度。

### 9.3 并发语义

- `extra_params.max_concurrency` 继续是实例配置，router 在所有 rollout mode 的 enforce 路径以 route lease 做跨进程上限。
- local semaphore 和 GPU backend lease 暂时保留为 defense-in-depth，不在本版本删除。
- route inflight 包含已选中后等待 local / GPU 准入的请求，表达实例承担的全部未完成需求。
- 首版没有 router queue；所有候选达到上限时返回 503 `ml_backend_pool_saturated` 和 `Retry-After`。
- route lease TTL 必须大于正常 transport timeout，并由长任务 heartbeat；固定 TTL 不因普通轮询无限续命。

### 9.4 故障语义

- Redis acquire 不可用：observe 只记录诊断并继续 legacy dispatch；enforce 返回 503 `ml_backend_router_unavailable`。
- 无 active / healthy 成员：503 `ml_backend_pool_unavailable`。
- 全部达到并发上限：503 `ml_backend_pool_saturated`。
- capability mismatch：成员不进入候选，不在运行时临时降级请求 schema。
- caller cancel 走 cancel，成功 / 可分类失败走 finish；无法分类的异常在 finally 保守 cancel，进程 crash 由 TTL 清理。

## 10. 调度、熔断与 draining

### 10.1 Smooth weighted round robin

首版只支持一个 policy：

- 每轮 eligible 成员 `current_weight += configured_weight`。
- 选择 current weight 最大者；并列按稳定 instance UUID 排序。
- 选中者 `current_weight -= eligible_total_weight`。
- 达到 max concurrency 的成员先排除，不参与当轮权重推进。
- membership / weight generation 改变时，旧 current weight 按新集合安全重置。

该策略提供确定、可测试的权重比例；不宣称根据 latency 或实时 inflight 最优。后续若需要 least-request，单独新增 ADR / feature，不在本版本预留插件框架。

### 10.2 被动熔断

- 只把连接拒绝、connect/read timeout、无 HTTP 响应和受控 gateway unavailable 计为 transport failure。
- 业务 4xx、模型校验失败、GPU capacity 503、主动 cancel 不触发实例 ejection。
- 连续失败达到配置阈值后在 Redis 写 `open_until`，后续 selection 排除该实例。
- 新鲜 health success 或 cooldown 后进入一次 half-open probe；成功关闭，失败重新 open。
- 不自动重试当前失败请求，避免重复 prediction 和 stateful session 损坏。

### 10.3 Traffic draining

状态机：

```text
active --drain--> draining --inflight=0--> disabled
   ^                    |
   └------ resume ------┘
```

- drain mutation 先持久化 membership state，再使新 acquire 不可选。
- runtime snapshot 显示 exact inflight 和最老 lease deadline。
- draining 时可以 resume；disabled 后 resume 需重新验证 health / capability。
- 移除成员、删除实例和普通 unload 要求 disabled + route inflight=0。
- traffic drain 完成不证明 GPU residency 已释放；卸载仍走现有 GPU / backend lifecycle proof。
- `traffic_state` 是 configured state；runtime 另返回由 rollout mode 决定的 `effective_routing_state`。
- off / observe 下可以预配置成员状态，但实际 legacy dispatch 不受它门控，drain 响应必须标 `effective=false`，也不能用 shadow inflight 证明安全卸载。
- 只有 enforce 下的 draining + 正式 route inflight=0 才形成 traffic quiescence proof；v0.23.4 不得在其它 mode 显示“已停流”。

## 11. 路由选择作用域

| 调用类型                         | 选择 / lease 作用域        | 说明                                         |
| -------------------------------- | -------------------------- | -------------------------------------------- |
| 同步 interactive / predict       | 单 HTTP 业务请求           | 请求完成走 finish，主动取消走 cancel         |
| batch 单阶段                     | 每个 task / execution unit | 不把整批永久压在一个实例                     |
| pipeline                         | 每个 stage invocation      | stage 保存 pool id；不同调用可选不同等价实例 |
| video tracker / stateful session | 整个 job / session pin     | heartbeat 保活，不能中途换实例               |
| retry failed prediction          | 新的显式请求               | 可以选择不同实例，但写新 selection 证据      |
| health / setup                   | 精确实例                   | 不经过 pool router                           |
| warmup / reload / unload         | 精确实例                   | 管理员明确选择目标，禁止静默挑副本           |

同一 stateful job 的 affinity 只在 job 内部显式保存 selected instance，不实现通用 cookie / user sticky session。

## 14. Rollout 模式

新增：

```env
ML_BACKEND_ROUTER_MODE=off
ML_BACKEND_ROUTER_HEALTH_MAX_AGE_SECONDS=90
ML_BACKEND_ROUTER_LEASE_TTL_SECONDS=120
ML_BACKEND_ROUTER_HEARTBEAT_INTERVAL_SECONDS=15
ML_BACKEND_ROUTER_PASSIVE_FAILURE_THRESHOLD=3
ML_BACKEND_ROUTER_EJECT_SECONDS=30
```

最终名称和范围在 P0 按 typed settings 冻结；同步 `.env.example`，运行 `pnpm docs:gen-env-vars` 并检查 `DEV.md`。

模式语义：

| mode      | 实际实例                                                          | routing ledger                                       | 失败处理                              |
| --------- | ----------------------------------------------------------------- | ---------------------------------------------------- | ------------------------------------- |
| `off`     | 请求携带的 legacy instance；新 pool 请求使用 `legacy_instance_id` | 不 acquire                                           | 保持 v0.23.2 行为                     |
| `observe` | 请求携带的 legacy instance；新 pool 请求使用 `legacy_instance_id` | shadow namespace 计算 would-select、记录诊断，不门控 | ledger 失败不阻断实际请求             |
| `enforce` | router selected instance                                          | 正式 acquire / heartbeat / finish / cancel           | Redis / topology 不确定时 fail closed |

进入 enforce 前必须满足：

- migration / backfill 零 orphan。
- 全部第一方调用方已传 pool id。
- observe 窗口中 actual / would-select capability 一致，无未知实例映射。
- route lease cleanup、进程 crash TTL、Redis 故障和 worker cancel 演练通过。
- 至少一个真实双实例 pool 完成比例、饱和、drain、ejection 和 GPU 交互验收。

本版本不引入复杂 durable rollout state；环境 mode 是单一部署级开关。API / worker / beat 必须读取相同配置，部署时整体重建 / 重启，不能混跑不同 mode。

## 15. 观测与指标

新增指标时保留现有 metric，不原地改变 label contract：

- `ml_backend_router_selections_total{pool_id,instance_id,outcome}`。
- `ml_backend_router_rejections_total{pool_id,reason}`。
- `ml_backend_router_ejections_total{pool_id,instance_id,reason}`。
- `ml_backend_routed_request_duration_seconds{pool_id,instance_id,outcome}`。
- route inflight / lease deadline 从 Redis snapshot 聚合，避免多进程 Gauge 各写各的。

runtime snapshot 至少返回：

- router desired / effective mode 与 runtime readiness。
- pool enabled / policy / total / routable。
- member configured traffic state、effective routing state、weight、health、routable reason。
- inflight / max、selection window、rejection、last selected。
- circuit state / open until。
- route snapshot、health、GPU、residency 各自 observed_at / stale / error。
- diagnostics 使用 `code + subject_type + subject_id` 稳定去重键。

Prometheus label 只用稳定 UUID / 受控 outcome，不放 URL、错误文本、lease id 或用户输入，避免基数爆炸。

## 19. 停止条件与回滚

出现任一情况立即停止：

- pool / instance ID 在任一调用链中无法区分。
- 项目仍以实例为 canonical binding，却开始在池内任选实例。
- capability fingerprint 无法证明成员请求兼容。
- router acquire 不能跨进程原子执行或可能突破 max concurrency。
- enforce 遇 Redis 不确定时会静默直连。
- route lease 无法覆盖 cancel / timeout / worker crash。
- tracker / stateful session 会在执行中换实例。
- Prediction / FailedPrediction / AsyncJob / GPU dispatch 丢失 selected instance。
- traffic drain 与 GPU drain 共用状态或错误执行 lifecycle。
- migration 无法完整迁移 pipeline / preference，或 downgrade 会静默丢多成员配置。
- observe 有未知映射、would-select capability mismatch 或高比例 router rejection。

回滚按层执行：

- P1 schema 在 singleton 条件下可逆；多成员配置后 forward-only。
- P2 ledger 是独立 namespace，可停止调用但不删除 GPU 数据。
- P3 / P4 先退到 router `off`，legacy alias 恢复原实例行为；不回滚已写双 ID 历史。
- P5 enforce 故障先切 observe / off，保留 topology 和诊断证据。
- 禁止通过删除 pool 表、清 Redis 全库或把 pool id 当 registry id 进行紧急回滚。

### B.4 Redis key / Lua I/O 冻结

namespace：`ml-router:v1`（与 `gpu-arbiter:v1` 零交叉）。

```text
ml-router:v1:pool:{pool_id}:state                          # SWRR current_weight / generation / counters
ml-router:v1:pool:{pool_id}:member:{instance_id}:leases    # sorted set: lease_id -> expiry
ml-router:v1:lease:{lease_id}                              # hash: pool / instance / owner / operation / expiry / generation
ml-router:v1:pool:{pool_id}:member:{instance_id}:circuit   # hash: open_until / consecutive_failures / state
ml-router:v1:pool:{pool_id}:metrics:{bucket}               # hash: selection/success/error/rejection + duration buckets
```

**acquire Lua**（KEYS = `[pool:state, pool:member:{i}:leases..., lease:* 占位]`，ARGV 顺序冻结）：

1. `pool_id`, `candidate_generation`, `caller_active_candidates_json`（含 instance_id / weight / max_concurrency / fingerprint_ok / health_fresh）, `owner`, `operation`, `lease_ttl_ms`, `now_ms`, `lease_id`。
2. 校验 `pool:state.generation == candidate_generation`，否则返回 `{ok=0, reason="generation_mismatch"}`。
3. 清理 `pool:member:{i}:leases` 中过期 entry（`ZREMRANGEBYSCORE`）。
4. 对每个 active candidate：若 circuit `open_until > now` 或 `ZCARD(leases) >= max_concurrency`，标记 excluded。
5. 剩余非空候选执行 SWRR：`state.current_weight[i] += weight[i]`，选 max（并列按 instance UUID 字典序），`state.current_weight[winner] -= total_eligible_weight`。
6. 写 `lease:{lease_id}` hash + `ZADD pool:member:{winner}:leases now+ttl lease_id` + `state.selection_counter[winner] += 1` + `metrics:{bucket}.selection += 1`。
7. 返回 `{ok=1, instance_id=winner, lease_id, expiry}` 或 `{ok=0, reason}`（`pool_unavailable` / `pool_saturated` / `all_circuits_open`）。

**heartbeat Lua**：`EXPIRE` / `ZADD` 更新 `lease:{lease_id}` + `pool:member:{i}:leases` 的 score，仅当 lease 未过期且 pool/instance/owner exact match，否则 noop。**不**改 pool / instance / owner。

**finish Lua**（ARGV: `lease_id, pool_id, instance_id, owner, outcome, duration_ms, now_ms, bucket`）：

1. 校验 lease 存在且 exact match；已 finish 返回同一稳定结果（幂等）。
2. `ZREM pool:member:{i}:leases lease_id`、`DEL lease:{lease_id}`。
3. outcome=`success` → `metrics:{bucket}.success += 1` + circuit `consecutive_failures = 0`、`state = closed`。
4. outcome∈`{transport_timeout, connect_refused, no_response, gateway_unavailable}` → `metrics:{bucket}.error += 1` + circuit `consecutive_failures += 1`，达阈值则 `open_until = now + eject_ms`、`state = open`。
5. 其他 outcome（业务 4xx / cancel / gpu_capacity_503）→ 仅 `metrics:{bucket}.{outcome} += 1`，**不**触发 circuit。

**cancel Lua**：与 finish 同结构但**不**计 transport failure、**不**更新 circuit；仅释放 lease + `metrics:{bucket}.cancel += 1`。

TTL：`lease` 默认 `ML_BACKEND_ROUTER_LEASE_TTL_SECONDS`（120s），必须 > 正常 transport timeout；长任务由 heartbeat（`ML_BACKEND_ROUTER_HEARTBEAT_INTERVAL_SECONDS`=15s）续命。`metrics:{bucket}` 桶过期自动回收（窗口外）。key 顺序 / ARGV 顺序 / 返回码 / Lua SHA-256 在 P2 冻结 golden 测试。

### B.5 Capability fingerprint 冻结

canonical snapshot 字段（**排序固定，前后端不重复实现**）：

1. `protocol_version`（capability 协议版本）
2. `model_ids`（sorted list）
3. `task` / `modality` / `infra`
4. `model_version` / `weights_version`（或等价 build revision；首版不支持版本混跑）
5. `supported_prompts` / `supported_inputs` / `supported_outputs` / `supported_trackers`（sorted）
6. `parameter_schema`（仅影响请求合法性的字段）
7. `variant_axes`（sorted）+ 枚举 + 默认值
8. `stateful` / `batchable` / `warmup`（路由相关布尔）

排除：URL、实例名、auth、health 时间、GPU UUID、显存、residency、cache、纯展示描述。

canonicalization：JSON with `sort_keys=True` + list sorted + missing defaults filled；SHA-256 hex（64 chars）。golden fixture 覆盖 field order / list order / missing defaults 不影响 fingerprint；task / model / input / output / param / variant 不兼容产生精确 diff（`409 ml_backend_pool_capability_mismatch`）。

### B.6 Rollout 配置冻结

ML_BACKEND_ROUTER_LEASE_TTL_SECONDS=120             # 必须 > transport timeout
ML_BACKEND_ROUTER_HEARTBEAT_INTERVAL_SECONDS=15     # 长任务 lease 续命
