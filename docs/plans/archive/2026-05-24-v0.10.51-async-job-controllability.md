# v0.10.51 · 后台任务可控性（Phase 2）

- 日期：2026-05-24
- 范围：Phase 2 —— `batch_predict` 协作取消 + `retry_failed_prediction` 纳入 async_jobs
- 前置：[v0.10.50 接缝打通](2026-05-24-v0.10.50-async-jobs-notification-seam.md) —— 本版复用其终态通知 helper（`services/async_job_notify.py`）
- 关联：[async-jobs-unification 决策](../../../ROADMAP/archive/2026-05-23-async-jobs-unification.md)

---

## 1. 背景与问题

承接 v0.10.50（接缝打通）后，后台任务仍有两处可控性/可见性缺口：

- **`batch_predict` 不可取消**：当前 `CANCELLABLE_KINDS = {"predictions_import", "audit_archive"}`，批量预标一旦发起只能等其跑完；CPU/调用密集的大批量任务卡住时无法中止。
- **`retry_failed_prediction` 不入 `async_jobs`**：失败预测重试走独立流程（`FailedPrediction` 表），历史页/通知里看不到，与统一任务体系脱节。

## 2. 目标 / 非目标

**目标**
- P2-1：`batch_predict` 支持协作取消（Celery `revoke` + 任务循环内 cancel 检查），取消后产生 `job.cancelled` 通知（复用 v0.10.50 helper）。
- P2-2：`retry_failed_prediction` 纳入 `async_jobs` 追踪，终态走统一通知。

**非目标**
- 强杀 worker 进程式取消（避免半写入）。
- 邮件 digest / @mention 等 Phase 3 项。

---

## 3. 设计决策

1. **协作式取消，不强杀。** 参考 `video_tracker_runner` 同款模式：`/async-jobs/{id}/cancel` 写取消请求标记 + Celery `revoke(celery_task_id, terminate=False)`；worker 在每条预测的循环边界检查，命中则 `mark_cancelled` 并跳出，**不**中途 kill 进程，避免预测结果半写入。
2. **取消标记落点**：复用现有状态机——cancel 端点对 `pending` job 直接 `mark_cancelled`；对 `running` job 写标记（`payload.cancel_requested=true` 或专用列，实现时二选一并在 PR 说明），worker 循环 `db.refresh(job)` / 重查后识别。
3. **取消后 result 要可解释**：写入已完成 / 未处理计数到 `job.result`（如 `{cancelled_at_index, done_count, skipped_count}`），前端历史页能展示"已取消，完成 N/总 M"。
4. **retry 用 `track_job` 包裹**：`kind="prediction_retry"`，短任务无中间进度，适合上下文管理器；终态由 v0.10.50 的 `notify_job_terminal` 统一发通知。

---

## 4. 实施步骤

### Step 1 — batch_predict 协作取消
- `apps/api/app/api/v1/async_jobs.py`：`CANCELLABLE_KINDS` 增加 `batch_predict`；cancel 端点对 `batch_predict` 的 `running` job 触发 `revoke(celery_task_id, terminate=False)` 并写取消标记；`pending` 直接 `mark_cancelled`。
- `apps/api/app/workers/tasks.py`：批量循环开头重查 job 状态 / 取消标记，命中 → `mark_cancelled` + `notify_job_terminal` + 跳出，写 result 的已完成/未处理计数。
- **验证**：发起大批量 predict → 调 cancel → worker 在下一条边界停止，job 终态 cancelled，result 含完成数；产生 `job.cancelled` 通知；已写入的预测不被回滚也不留半条记录。

### Step 2 — retry_failed_prediction 纳入 async_jobs
- `apps/api/app/workers/predictions_retry.py`：用 `track_job(kind="prediction_retry", user_id=..., project_id=..., payload={failed_prediction_id, ...})` 包裹重试，终态走 v0.10.50 helper（需把 `prediction_retry` 加入 `TERMINAL_NOTIFY_KINDS`）。
- 前端 `AIPreAnnotateJobsPage`：确认 `kind=prediction_retry` 在列表正确展示（payload 字段映射），或归入合适的 tab。
- **验证**：触发重试 → `async_jobs` 出现 `prediction_retry` 行，终态正确；历史页可见；终态产生通知。

## 5. 数据库迁移

- 若取消标记采用 `payload.cancel_requested`（JSONB）则**无 DDL**；若选专用列则需一支 alembic 迁移（实现时定）。
- `prediction_retry` 是 `async_jobs.kind` 新取值（自由 String），无需迁移。

## 7. 风险与回滚

| 风险 | 缓解 |
|---|---|
| revoke 半写入 / 状态不一致（参考 v0.10.49 video_tracker 双写漂移） | 不用 terminate；仅循环边界协作停止；result 记录精确计数；专门并发取消测试 |
| 取消标记与终态竞争（worker 已 complete 后才收到 cancel） | `mark_cancelled` 幂等（仅 pending/running 可转）；竞争时以先到终态为准 |
| prediction_retry 刷历史页 | 与现有重试通知合并语义，避免重复提醒 |

## 8. 验证总览（goal-driven）

1. 后端单测：取消并发用例 + retry 入表用例全绿（`uv run pytest`）。
2. 手动：大批量 predict 取消在边界停止、计数正确、通知到达；retry 在历史页可见。
3. worker 改动后按 CLAUDE.md §8 `docker restart` celery-worker 验证最新代码生效。
