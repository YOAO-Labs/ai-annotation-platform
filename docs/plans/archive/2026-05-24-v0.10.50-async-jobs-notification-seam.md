## 1. 背景与问题

后台任务（`async_jobs`）与个人通知（`notifications`）两套能力各自成熟，但**接缝割裂**：

- `export.ready/failed`、`failed_prediction.retry.*` 走了通知系统；但 **`batch_predict`、`video_tracker` 完成/失败只靠 `JobsBell` 每 5s 轮询**，不产生 notification。
- 结果是用户面对两个"任务感知"入口——`JobsBell` 任务铃铛 vs `NotificationsPopover` 通知铃铛，体验割裂、实时性差（5s 延迟、无主动提醒）。

伴随的低垂缺口：
- 多个已上线的通知类型（`task.reopened` / `batch.review_reopened` / `batch.admin_locked` / `failed_prediction.*` / `export.*`）**未进 `KNOWN_NOTIFICATION_TYPES`** → 用户在设置页看不到、无法静音、列表无标签。
- 通知**只能读不能删**，历史越积越长。

## 2. 目标 / 非目标

**目标**
- P1-1：所有"用户发起的"后台任务终态（完成/失败/取消）统一产生个人通知，复用现有 WS + Redis pubsub 推送链路。
- P1-2：补全 `KNOWN_NOTIFICATION_TYPES` 与前端标签，让所有现存通知类型可见、可静音。
- P1-3：通知删除（单条）+ 清空已读 的 API + UI。

**非目标（移至 v0.10.51 / Phase 3）**
- `batch_predict` 取消、`retry_failed_prediction` 入表 → v0.10.51。
- 邮件 digest / SMTP、@mention、按 kind 粒度静音、分组浏览 → Phase 3。

## 3. 设计决策（实现前必须遵守）

1. **统一终态通知不耦合进 `mark_complete/mark_failed/mark_cancelled`。**
   这三个是纯索引状态方法（`services/async_job.py`），不该承担通知职责（通知文案依赖 `kind`/`payload`）。新增独立 helper：
   ```python
   # services/async_job_notify.py（新）
   async def notify_job_terminal(db, *, job_id) -> None:
       # 读 job → 若 user_id 为空则跳过（系统级 beat 任务不发）
       # kind 不在 TERMINAL_NOTIFY_KINDS 白名单则跳过
       # 按 status 映射 job.completed / job.failed / job.cancelled
       # target_type="async_job", target_id=job.id
       # payload 取 kind / display 字段 / result 摘要 / error_message
       # 调 NotificationService(db).notify(...)；整体 try/except 仅 log 不阻断
   ```
   在各 worker 终态点 `mark_*` 之后显式调用，事务由 worker 现有 `db.commit()` 一并提交。

2. **排除已有专属通知的 kind，避免双发。**
   `export` 已发语义化的 `export.ready/export.failed`（带 `download_url`），**不**再发 `job.completed`。
   `TERMINAL_NOTIFY_KINDS = {"batch_predict", "video_tracker", "predictions_import", "audit_archive"}`；`export` 不在内。

3. **通用终态通知类型**：新增 `job.completed` / `job.failed` / `job.cancelled` 三个类型，payload 带 `kind` 让前端区分文案（"批量预标完成"/"视频追踪失败"等）。新增 job 类型时无需再加通知类型——与 async_jobs"默认进统一表"的底线一致。

4. **静音粒度**：上述三类进 `KNOWN_NOTIFICATION_TYPES`，用户可整类静音（MVP 不做按 kind 静音）。

## 4. 实施步骤

### Step 1 — 统一终态通知 helper（核心）
- 新增 `apps/api/app/services/async_job_notify.py`：`notify_job_terminal(db, *, job_id)`，含 `TERMINAL_NOTIFY_KINDS` 白名单与 `status → type` 映射，payload 从 `job.payload`/`job.result`/`job.error_message` 取摘要字段（display_id、kind、success/failed_count 等）。
- 接入点（每处在对应 `mark_*` 之后、`commit` 之前调用）：
  - `apps/api/app/workers/tasks.py`（batch_predict：complete/failed 分支）
  - `apps/api/app/workers/video_tracker.py:76-95`（按专表终态同步 async_jobs 后）
  - `apps/api/app/workers/signals.py`（task_failure / task_revoked 兜底：`find_by_celery_task_id` 拿 job 后补发）
  - `predictions_import` / `audit_archive` 的终态点
- **验证**：`tests/test_async_jobs.py` 新增用例——带 `user_id` 的 job complete/fail/cancel 后断言 `notifications` 表新增对应 `job.*` 行；`export` kind 不产生 `job.completed`；无 `user_id` 的 job 不发通知。

### Step 2 — 补全通知类型注册 + 前端标签
- `apps/api/app/api/v1/notifications.py:27` `KNOWN_NOTIFICATION_TYPES` 增补：
  `task.reopened`、`batch.review_reopened`、`batch.admin_locked`、`failed_prediction.retry.started/succeeded/failed`、`export.ready`、`export.failed`、`job.completed`、`job.failed`、`job.cancelled`。
- 前端 `apps/web/src/components/shell/NotificationsPopover.tsx`（type → 文案映射）+ `apps/web/src/pages/Settings/SettingsPage.tsx:757` `NOTIF_TYPE_LABELS` 同步补齐所有新类型中文标签。
- **验证**：设置页渲染出全部类型开关；通知中心对新类型显示正确文案（非 fallback 原始 type 串）。

### Step 3 — 通知删除 + 清空已读
- 后端 `apps/api/app/api/v1/notifications.py` + `services/notification.py`：
  - `DELETE /notifications/{id}`（owner-scoped）
  - `POST /notifications/clear-read`（删除当前用户所有已读，返回 `{deleted: n}`）
- 前端 `apps/web/src/api/notifications.ts` + `useNotifications.ts` 增加 mutation；`NotificationsPopover` 加单条删除（hover 出 ✕）+ "清空已读" 按钮。
- **验证**：删除后列表/未读数刷新正确；删未读会同步减未读计数；清空已读不影响未读条目。

## 7. 风险与回滚

| 风险 | 缓解 |
|---|---|
| 终态通知与现有通知双发（export 等） | helper 白名单排除 export；单测覆盖 |
| worker 内发通知失败影响主流程 | `notify` 内部 publish 已 try/except；helper 整体 try/except 仅 log，不阻断 mark_* |
| 通知量激增 | 仅 `user_id` 非空（用户主动发起）的 job 才发；系统级 beat 任务无 user_id 不发 |
| 老用户被新类型刷屏 | 新类型默认 in_app=true 但可静音；终态通知是用户自己发起的任务，预期可接受 |
