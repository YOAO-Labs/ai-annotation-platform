# v0.19.3 · 两层校验对称收口（保存编排 + config-time batchable + 跨端契约）

状态：**已实现**（WS1+WS2+WS3 全部落地，后端 42 测 + 前端 55 测通过）。未决项拍板：
WS1 软提示 / WS1 纯函数吃 model_caps / WS3 fixture 落 apps/web/src。
接 v0.19.2「ML 能力字段消费」之后，**补齐 v0.19.2 直接暴露的三处不对称**。
全是低成本收口，无 alembic，无新依赖。

## 背景

v0.19.2 给 AI 预标注派发期加了两条能力 422（`batchable=false` 拒批量 / 分类阶段模型不产 `class` 拒），
并把画布属性落点校验泛化。但留下三处「两层模式（config-time warn + dispatch-time 422）」没闭合的缝：

| 缝 | 现状 | 后果 |
|---|---|---|
| **保存编排不校验能力** | `services/pipeline_template.py::validate_saved_pipeline` 只做结构 / 树形校验，不碰 v0.19.2 的能力判据 | 用户能把 `batchable=false` / class-less 模型的编排**存进库**，到执行 `trigger_preannotation` 才 422 —— 延迟报错 |
| **config-time 缺 batchable 预警** | dispatch-time 有 422，但前端源模型选择器没有红字预警（`downstreamModels` 已过滤 `is_interactive` 挡掉大部分下游，但源阶段与边界 case 没兜） | 用户配置期看不到，跑了才知道 |
| **校验判据两份手写** | WS1（TS 警告）与 WS2（Python 422）各写一份 batchable/class 判据 | 易漂移：改一边忘改另一边，警告与拦截脱节 |

## 目标

把上述三处补成对称的两层校验，并加一道防漂移的契约测试。

---

## WS1 · 保存编排路径补能力校验（后端）

`services/pipeline_template.py::validate_saved_pipeline` 当前仅复用 `schemas/preannotate.py::PreannotateRequest` 结构校验。
本项把 v0.19.2 的两条能力判据（`_assert_batchable` + 分类阶段 class 检查）抽成可复用函数，保存路径也调用。

**已定（软提示，不硬挡）**：保存路径产出**响应内 `capability_warnings: [...]` 软提示**，dispatch-time 422 仍是最终闸。
决定性依据（探查证实）：`validate_saved_pipeline`（`services/pipeline_template.py`）只拿到 stage ID，不带 backend/model 实体——
能力快照须在保存时现查（同 dispatch 的 `_stage_model`），是天然的配置中途态、可能滞后；硬挡会误伤
「先存草稿、之后换 backend」的合法流。语义分层：保存 = 配置期 = warn 层；执行 = 拦截层，两层不串。
升级为「保存即阻断」留待用户反馈（见「不在范围」）。

落点：
- 抽 `_assert_batchable`(projects.py:1429) + class 检查(projects.py:1485-1506) → `app/services/pipeline_validation.py`
  （新文件，**纯函数，吃已解析的 `model_caps` dict** —— 即 `_stage_model(backend, model_id)` 的返回，
  含 `resource_profile` / `output_attribute_types`；再吃 `is_source` / `writes_attributes` 两个角色标志），
  返回 violation 列表。`_stage_model` 解析仍留 projects.py，函数本体不碰 backend 实体 →
  保证真·纯函数，WS3 的 pytest 可直接喂 fixture。trigger（dispatch 路径）与保存路径共用同一函数。
- `validate_saved_pipeline` 对每个 stage 只做结构校验；能力 warning 仍由项目配置路径结合 `_stage_model` 计算，不把能力检查塞进共享结构校验。
- 保存入口是 **`PATCH /projects/{id}`**（projects.py:627，非 `PUT`），响应模型 `ProjectOut`(schemas/project.py:147)
  在 `_serialize_project`(projects.py:209-214) 动态补 `capability_warnings` 字段，**无 DB 列**。前端编排面板渲染该字段。

风险：低（读 health_meta，不写库）。须回归既有保存流不被误挡。

验收：保存一条含 `batchable=false` / class-less 下游的编排 → 按选定方案出 warnings 或 422；合法编排静默通过。

## WS2 · config-time batchable 预警（前端）

补上 dispatch-time 422 对应的配置期预警，让 batchable 也成完整两层。

落点（路径经探查修正）：
- 源模型选择器：`apps/web/src/pages/AIPreAnnotate/components/usePreannotateConfig.ts`（**在 `components/` 非 `hooks/`**）
  —— 选中源 model `resource_profile.batchable===false` 时给非阻断预警「该模型为交互/有状态模型，不能用于批量预标」。
- `StageCard.tsx` 下游：**实现偏差（已采纳）** —— 未改 `downstreamModels` 过滤器排除 `batchable===false`，
  改为与 v0.19.2 `producesClass=false` 先例**严格同构**：模型保留可选 + 标红警示（`showNotBatchableWarning`），
  而非静默从列表消失。理由：`producesClass=false` 的模型本就不被过滤、只标红，batchable 同构更诚实、更简单、
  且让 `stageWarning` 的 batchable 分支真正生效（过滤掉则该分支对下游永不触发）。`is_interactive` 过滤维持原样。
- 复用 v0.19.2 已建的 `StageCaps`（`apps/web/src/pages/AIPreAnnotate/utils/pipelineGraph.ts:81-94`，已有 `producesClass?`）：
  加 `batchable?: boolean`，`stageWarning`(同文件 line 103-118) 增一条 batchable 分支（与 producesClass 同构）。
- 注：`useCapabilityValidation` 在 `pages/Workbench/state/`（管几何/属性落点校验），**不是** AIPreAnnotate 内的编排校验；
  本 WS 的源模型预警是 AIPreAnnotate 内新增、复用 `pipelineGraph.ts` 的 `StageCaps`/`stageWarning` 模式，不动 Workbench 那支。

风险：低（纯前端、非阻断）。

验收：源/下游选到 `batchable=false` 模型时配置期即出预警，与后端 422 判据一致。

## WS3 · 跨端契约测试（防漂移）

判据 SSOT 难跨语言共享，改用**共享 fixture + 双端断言**：一份 JSON fixture 列若干
`{model_caps, expect_warn, expect_reject}`，vitest（断言 TS 警告判据）与 pytest（断言 422 判据）各读同一份，
任一端漂移即测试红。

落点：
- fixture **放 `apps/web/src/__fixtures__/capability-validation-cases.json`**（已定，否决 `docs-site/dev/examples/`）。
  依据：vitest 受 tsconfig `include:["src"]` + alias `@/→src` 约束，**无法直接 import `src` 外的 JSON**，
  放中立位会逼着在 vite.config 加 test alias、破 tsconfig 边界；而 pytest 读任意文件路径无碍。
  故 fixture 落 `src` 下：vitest 走 `@/__fixtures__/capability-validation-cases.json`，
  pytest 走文件路径常量 `apps/web/src/__fixtures__/capability-validation-cases.json`，**零构建配置改动**。
  （`__fixtures__` 仅被测试引用、不进 app import 图 → 不会打进生产包；JSON import 需 `resolveJsonModule`，vite 项目默认开。）
- vitest：喂 `stageWarning`(pipelineGraph.ts) 断言 warn 结果（batchable/class 判据本体在此，非 Workbench 的 `useCapabilityValidation`）。
- pytest：喂 `pipeline_validation` 纯函数断言 reject 结果。

风险：低。fixture 同时被 vitest（`@/` import）与 pytest（路径常量读文件）消费，已确认无需改构建配置。

验收：故意改单边判据 → 对应端契约测试红。
