# v0.18.27 · 项目编排持久化（`Project.preannotate_pipeline` 单列 JSONB · 方案 A）

> 草案 (2026-06-26). **交互工具栏重设计 epic 第 2/3 版**。给项目加一条「已保存的编排」，供 [v0.18.28](2026-06-26-v0.18.28-popover-run-project-pipeline.md) popover「运行当前题（按项目编排）」读取。
>
> Epic 总览见 [v0.18.25](2026-06-26-v0.18.25-interactive-ai-toolbar-redesign.md)。上游 [多阶段预标注编排 epic](../../ROADMAP/2026-06-23-staged-preannotation-pipeline-roadmap.md)。方案 B（多命名编排表）延后见 [ROADMAP §A·AI/模型](../../ROADMAP.md)。

## 1. 背景 / 缺口（源码核对）

今天**无任何地方记得「这个项目的编排长什么样」**：

- `Project` 模型只有 `ml_backend_id` + `default_variants`（`apps/api/app/db/models/project.py:50`），无 pipeline 列。
- 多阶段 `pipeline_stages` 仅挂 `apps/api/app/schemas/preannotate.py::PreannotateRequest`，**按请求传、跑完即弃**。
- 前端命名预设只是 variant+params 的**单阶段**快照（`usePreannotateConfig.ts`），非多阶段 pipeline。

本版补地基：让 `/ai-pre` 把当前编排**存到项目**，一项目一条「当前编排」（方案 A）。

## 2. 目标 / 非目标

**目标**
- `Project` 加 `preannotate_pipeline JSONB nullable`，存一条 `pipeline_stages` 形状的编排。
- 项目 PATCH/GET 读写该列。
- `/ai-pre` `ProjectDetailPanel` 加「保存为项目编排」（含「清除」）。

**非目标**
- popover 执行项目编排（→ v0.18.28）。
- 多条命名编排（方案 B，ROADMAP）。
- 不改 `PreannotateConfigForm` / `usePreannotateConfig` 内部（统一 picker 单一事实源）。
- 不改 worker / 协议（执行链已就绪，本版只存不跑）。

## 4. 设计与改动

### 4.1 后端

1. **模型列**（`db/models/project.py`，紧随现有 JSONB 列后）：
   ```python
   # 项目级「已保存的编排」(方案 A, 一项目一条); 形状 = pipeline_stages 数组 (ml_backend_id 存 str)。
   # NULL = 未配编排 → popover 不出「运行项目编排」入口。
   preannotate_pipeline: Mapped[list | None] = mapped_column(JSONB, nullable=True)
   ```
2. **schema**（`schemas/project.py`）：
   - `ProjectUpdate` 加 `preannotate_pipeline: list[dict] | None = None`（`exclude_unset` 区分「不改」与「清空=显式 `[]`/`None`」；约定**显式 `null` = 清除**）。
   - `ProjectOut` 加 `preannotate_pipeline: list[dict] | None = None`。
   - 用 `dict` 而非 `list[PipelineStage]`：存储态 `ml_backend_id` 是 str，且要回吐原样 JSONB；结构校验通过 `services.pipeline_template.validate_saved_pipeline` 复用 `schemas/preannotate.py` 的请求 schema。
3. **PATCH 回写**（`api/v1/projects.py:update_project`）：通用 `setattr` 循环对 JSONB list 直接可用；`preannotate_pipeline` 非空时调用 `services.pipeline_template.validate_saved_pipeline`，非法则 422；显式 null 清除、字段缺省保持不变。
4. **迁移** `0107_project_preannotate_pipeline.py`：`op.add_column("projects", sa.Column("preannotate_pipeline", postgresql.JSONB(astext_type=sa.Text()), nullable=True))`；down 删列。

### 4.2 前端

5. **项目类型/API**（`api/projects.ts`）：`ProjectUpdatePayload` + `ProjectResponse` 各加 `preannotate_pipeline?: PipelineStagePayload[] | null`（复用 `usePreannotation.ts:89` 的 `PipelineStagePayload`）。
6. **`/ai-pre` 保存按钮**（`ProjectDetailPanel.tsx`，`onRun()` 旁，`:468-489`）：
   - 「保存为项目编排」：复用 `onRun` 里**同一套 `pipelineStages` 拼装**（`:472-489`），改为 `projectsApi.update(projectId, { preannotate_pipeline: pipelineStages ?? [argsToStage(baseArgs,0)] })`（单阶段时也存成单元素数组，保持「一项目一编排」语义）。成功 toast + invalidate 项目查询。
   - 「清除项目编排」：`projectsApi.update(projectId, { preannotate_pipeline: null })`，仅当项目已有编排时显示。
   - 项目已有编排时给个小标识（如「已保存编排 · N 阶段」）。

## 5. 测试

- 后端：PATCH 项目带 `preannotate_pipeline`（单阶段 / 多阶段）→ persist + GET 原样返回；显式 `null` → 清除；非法 stage（重复 stage 序号 / 无源阶段 / 坏 uuid）→ 422。
- 前端：点「保存为项目编排」→ 以正确拼装的 `pipelineStages` 调 `projectsApi.update`；「清除」发 `null`；已有编排时标识渲染。
- 回归：现有 `/ai-pre` 跑预标注不受影响（本版不碰 `buildArgs`/`onRun` 的执行路径，只加旁路保存）。

## 6. 验收

- `/ai-pre` 配好 pipeline（单或多阶段）→ 点「保存为项目编排」→ 重进项目，`GET /projects/{id}` 返回 `preannotate_pipeline`。
- 「清除」后该字段回 `null`。
- `curl -s localhost:8000/health` 报 0.18.27。

## 7. 风险

- **存储形状一致性**：务必复用预标注端点的 stage 归一化（`projects.py:1405-1457`，uuid→str），别两处各拼一套导致 v0.18.28 读出来对不上。
- **校验复用**：`_validate_pipeline_stages`（`:1270`）当前是 `PreannotateRequest` 的 model_validator；抽成独立函数供 PATCH 复用，或在 PATCH 就地构造一个临时 `PreannotateRequest` 触发校验。
- **清除语义**：`exclude_unset` 下「不传」vs「传 null」要分清——约定显式 `null` 清除、不传不动。
- **版本号收尾**：CLAUDE.md §10 → 0.18.27（4 文件 + uv.lock + openapi 快照钩子生成）；新增 API 字段 → openapi 快照会变（钩子自动），同步 `docs-site/api` 由钩子处理。新增功能 → 记 CHANGELOG。
