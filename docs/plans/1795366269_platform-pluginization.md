## 1. 目标与非目标

维护者在 2026-11-23 的讨论中确认了以下方向：

| 编号 | 目标                                                                                                                             |
| ---- | -------------------------------------------------------------------------------------------------------------------------------- |
| G1   | **后端设计解耦**：每个模块有唯一数据 owner、语言无关公开契约和一致性检查，未来可以把选定模块（尤其是计算热点）换成其他语言实现。 |
| G2   | **默认模块化单体部署**：自托管默认只运行少量进程；模块边界始终保持可拆出，只在有具体理由时拆出。                                 |
| G3   | **插件化**：核心能力是随平台发布的内置模块，扩展能力通过版本化扩展点安装；推理扩展提供“直连”和“安装”两档接入。                   |
| G4   | **第二个扩展点**：用通知渠道（飞书私信）验证插件契约不只适用于推理。                                                             |

非目标：

- 不把“每个模块独立构建、部署”作为默认部署或完成门槛。
- **暂缓**跨语言替换实现，Go 月报实验（[ADR-0090](../adr/0090-module-languages-and-audit-summary-process.md)）维持实验状态、不进入真实路径；保留语言无关契约和一致性检查。
- 不建设通用插件市场、热加载、通用事件总线或前端插件 SDK，等出现具体用例再定。
- 不重做已验收的 owner 边界，不改写历史证据、冻结引用或收据。
- 不处理生产容量、多卡并发、第三方许可发布等上线门槛；这些门槛保持独立。

## 2. 核心决定（正式记录见 ADR-0186）

| 决定                     | 含义                                                                                                                                                                   | 保持不变的约束                                           |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------- |
| 契约是边界，进程不是     | 模块之间只通过 PostgreSQL 固定函数能力、JSON Schema 和 HTTP 协议交互；同一进程内也调用同一 owner 能力。普通运行账号只持有 owner 函数的 EXECUTE，权限边界不依赖进程拓扑 | 单一写入 owner、调用方事务语义、撤权串行化、最终写入复核 |
| 边界“可拆出”而非“已拆出” | 拆出前提见 §2.1；满足前提即可按需拆出，不要求预先拆分                                                                                                                  | 拆出时仍走“契约冻结 → 第二实现 → 明确切换 → 删除旧实现”  |
| 按需拆出                 | 只有资源隔离（GPU、FFmpeg、大内存）、安全隔离（第三方代码、独立凭据）、经实测的独立扩缩、或实际选定的语言替换，才构成独立进程的理由                                    | 已拆出且有上述理由的服务保持独立                         |
| 两个部署档位             | **all-in-one**：默认档，自托管和日常开发使用。**split**：只为有理由的服务提供 opt-in overlay                                                                           | 两档运行同一套代码和契约，不维护两套业务实现             |

### 2.1 可拆出边界的条件

1. 公开操作的输入输出可以 wire 序列化，不携带 ORM 对象、`AsyncSession`、`Request` 或异常类型。
2. 跨边界没有私表读写；需要同事务的操作由 owner 的固定 SQL 能力承担，并明确标注“拆出需要另定协调方案”。
3. 有不依赖 Python 实现的一致性检查（现有 Node peer、冻结 SQL、JSON Schema fixture 均可）。
4. 凭据和外部状态（表、对象前缀、Redis key）的归属明确。

满足这些条件，就满足 G1 的“将来可替换”。是否真的拆出或换语言，按 §2 的理由另行决定。

| 工作项           | 内容                                                                                                                                                                                                                                                                                                 |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| M1a 直连档       | 把“`yoao-plugin dev` 或任意 HTTP 服务 → 模型市场按 URL 和 Token 注册 → 项目启用”写成正式入门路径，并说明非托管实例不具备的能力（GPU 仲裁、受控训练模型部署等，以实际校验为准）。先核实一个疑似卡点：文档写明 `yoao-plugin dev` 只监听 loopback，而注册表拒绝 loopback 地址，平台在容器内时可能连不上 |

### M2 部署收敛：默认模块化单体

1. **M2a 盘点**：逐个列出 §3 中的 overlay 服务，记录嵌入路径是否存在、拆出理由、依赖凭据和数据库角色、受影响的 CI 选择器与文档，形成“保留独立／合并回默认档”决定表并请维护者确认。初步判断（以盘点结果为准）：

   | 初判       | 服务                                                                                                                        |
   | ---------- | --------------------------------------------------------------------------------------------------------------------------- |
   | 保留独立   | 推理插件与 Inference GPU 控制面、media-probe、Assets 媒体／图片 worker（FFmpeg 与大内存）、training-executor、storage-agent |
   | 合并回默认 | Workspace 各操作服务、Labeling class-query、Identity admission、Jobs queue／relay、Audit maintenance                        |
   | 待盘点决定 | Notifications publisher／socket、Identity mail、Assets source／catalog／import／cleanup、Labeling video-writer／mask-gc     |

2. **M2b 合并**：默认档改用已有的进程内 owner 路径；只服务按操作拆分的 overlay、CI 选择器和文档一并退役。模块代码、契约、冻结 SQL 和一致性检查保留。
3. **M2c 日常环境迁移**：仅在维护者明确授权后，按维护窗口、存量数据库和存储身份核对、切换、真实业务验证的顺序执行。此次维护者明确选择原地迁移且不备份；代码合并不触发其他部署迁移。

验收：新 checkout 以默认档冷启动，完成登录、建项目、导入、标注、审核、通知、预标注（任一插件）的真实业务冒烟和约定的恢复；LAN 内嵌、LAN 远程 issuer 的普通消费者、工作树生成的普通运行 LOGIN，对所有模块私表（含列、分区、外表与物化视图）和序列均无有效权限。保留的独立服务须以实际 split overlay 冷启和取证。拓扑、凭据边界与通过范围见[进程清单](../../docs-site/dev/concepts/module-deployment.md#deployment-convergence)。

### M3 通知渠道扩展点：飞书私信

**场景**：审核员驳回任务后，标注员在飞书收到卡片“任务 #123 被驳回 · 项目 A · [打开工作台]”。

| 职责         | 平台（Notifications owner）                                                                 | 渠道插件                                   |
| ------------ | ------------------------------------------------------------------------------------------- | ------------------------------------------ |
| 收件人与授权 | 计算收件人，投递前复核账号有效、目标可见、偏好开启                                          | 不接收用户列表，不判断权限                 |
| 持久性       | 与业务同事务写入收件箱行和渠道 outbox 行；提交后领取租约、发布、确认；按 `delivery_id` 去重 | 对重复 `delivery_id` 保持幂等              |
| 内容         | 生成 ADR-0025 版本化信封；载荷不含评论正文                                                  | 把信封转成渠道消息格式                     |
| 外部调用     | —                                                                                           | 使用插件自己保管的飞书应用凭据调用飞书 API |
| 运维         | 渠道安装、启用、停用、退役、审计、限速                                                      | 报告 `delivered`／`retryable`／`permanent` |

插件契约草案：`GET /setup` 声明渠道 ID、显示名和用户地址的 JSON Schema（如 `{open_id}`）；`POST /deliver` 接收信封、收件人地址和语言并返回结果；可选的 `POST /verify-address` 在用户绑定时发送测试消息。插件不获得数据库、用户 JWT、平台管理凭据或任意用户列表。

工作项：

1. **M3a 设计决定**（写入 ADR）：插件安装身份放在宿主级扩展注册表，还是由领域 owner 各自维护；manifest 中哪些字段跨扩展点通用，推理专属的 `models`、`pools`、GPU 字段改为能力专属。
2. **M3b 平台侧**：偏好策略增加渠道键（同步 `preferences.policy.json` 与 owner SQL）；用户渠道地址绑定归 Notifications 所有；把持久 outbox 扩展到外部渠道投递；投递 worker 复用现有租约与可见性复核。
3. **M3c 插件侧**：用 Plugin-SDK 之外的最小实现（任意语言）完成飞书插件，验证直连档即可接入；按需提供镜像走安装档。

验收：业务回滚不发送；插件不可用时重试并最终记失败；`permanent` 不重试；投递前撤权或目标不可见时不发送；停用渠道后不再投递且历史保留；重复投递不产生重复消息；用户解绑后不再投递。契约检查可以使用隔离环境中的飞书 API 替身；最终用维护者提供的测试应用验证真实飞书一次。

### M4 由扩展点带动的 owner 收口与统一装配

- **M4a 内置模块统一装配**：在 M2、M3 明确实际需要之后，把路由、Celery 任务、迁移和 Compose 的静态列表改为声明式装配；不提前建设空的通用框架。
- **M4b 下一个扩展点**：由维护者从格式适配器、训练器、数据源连接器中选择。
- **M4c owner 收口**：只收口所选扩展点实际触及的 Assets、Learning、Insights 边界（例如格式适配器需要先移除 `Session`／`Project` 参数）。

## 6. 风险

| 风险                             | 处理                                                                                                           |
| -------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| 合并进程时破坏最小权限或事务语义 | 边界本来就是 PostgreSQL 固定函数能力，进程内调用同一能力；用受限角色验证私表仍不可直接访问                     |
| 维护者日常环境中断               | 单独确认切换窗口与是否备份；无备份的原地迁移不承诺回滚，不触碰其他部署                                         |
| 飞书外部依赖与凭据               | 契约检查用替身；真实验证使用维护者提供的测试应用，凭据不进仓库                                                 |
| 计划和台账再次膨胀               | 本计划只写目标、决定和去向；运行证据写入 `docs/plans/evidence/1795366269_platform-pluginization/` 下的运行账本 |
