# 0180 — 可安装推理插件与组合式检测开发包

- **Status:** Proposed
- **Date:** 2026-10-28
- **Deciders:** 维护者授权实施，代理记录设计与验证
- **Supersedes:** ADR-0038（拟替代其“仅共享 schema、不提供可组合实现层”的限制）

## Context

[ADR-0038](archive/0038-defer-ml-backend-base-class.md) 选择共享协议与模板，避免用万能父类约束差异很大的后端。现在需要让外部开发者独立交付真实检测模型，并把 LibreYOLO 原生训练产物交回同框架的 GPU 推理插件。复制 YOLO 服务会同时复制模型池、认证、取消与 GPU 生命周期；仅新增 manifest 又不能解决安装身份、项目权限、模型发布和安全卸载。

现有 Inference 已拥有 Registry、服务池、路由和资源准入；Learning 拥有不可变训练产物、部署、试用与发布；Jobs 拥有执行快照与提交围栏。插件不能建立第二套这些账本。具体范围见仓库中的实施计划 `docs/plans/1793156248_libreyolo-inference-plugin.md` 和能力边界研究 `docs/research/51-plugin-capability-boundaries-and-ecosystem.md`；两者不属于文档站页面。

## Decision

### 核心保持治理与业务状态，插件提供模型执行

- 插件在独立进程／容器内使用既有 Inference HTTP 契约，不在 API 进程加载第三方 Python，不增加训练 `/fit` 入口。
- Registry owner 管理安装身份、版本、制品摘要、资源绑定和状态。安装不等于项目启用，也不等于训练模型发布；这些动作继续走各自 owner 的权限与事务边界。
- 公开安装 manifest 声明供应方、许可、固定 OCI 摘要、SDK 兼容性、能力、资源与资产来源。先保留停用的实例身份，再启动和核验服务，最后激活；不能由第一份执行许可决定实例身份。
- 管理员客户端在明确选定的本地主机操作容器，API 不挂载 Docker socket、不执行任意宿主机 hook。Token 与 GPU 签名校验材料单独供给，不进入公开 manifest 或通用日志。
- 停用和卸载依赖持久状态、业务依赖与运行时排空证据。路由关闭或观察模式不是绕过安装状态的许可；取消业务任务也不能证明设备工作已经停止。
- 受控进程重启复用安装与模型目录，但必须先终止旧 boot，再以新容器与 boot 重新完成路由、GPU 初始化和激活；证明与候选启动身份在私有收据中保留。意外退出没有可信旧进程终止证明时不自动恢复，Docker 管理操作须由该安装器独占。
- 路由管理围栏与 GPU 终止证明独立。GPU owner 可从已授权的持久安装终止意图取得精确端点，只准发送带签名的终止排空请求，不取得普通路由准入。Native 仅为经过安装 owner 核验的单调停用、证明及退役更新提供事务绑定标记；路由配置修订如实递增，未确认的控制与尝试记录不被删除或伪装为完成。
- 新 boot 的路由 incarnation 通过受终止证明约束的替换能力取得，不放宽普通 reconcile 的 incarnation 比对。绑定冻结安装修订、精确端点、容器、boot 和确定性控制 ID；重试沿用原挑战与 epoch，已完成绑定仅在当前 ready 状态仍吻合时重放。相同启动收据与资格的重放不改写配置修订，以免未确认的控制无法恢复。

### 检测开发包采用组合，不采用统一后端继承体系

提供独立可分发的 `aap_inference_plugin` 开发包。检测作者实现模型加载、检测和关闭；外壳组合既有协议模型、受控资产读取、结果转换、模型池、认证与生命周期组件。包不依赖 Torch、LibreYOLO、API ORM、Celery 或数据库管理凭据。

真实 LibreYOLO 插件与生成模板采用相同作者接口。开发工具覆盖生成、显式资产准备、本地开发、真实 HTTP 契约检查和构建。运行时不自动下载模型、不换模型、不在 CUDA 失败时静默回退 CPU。现有交互式、视频或开放词汇后端不被迫迁移到这个窄接口，也不为未来能力预先增加空抽象。

### 训练身份与部署执行资格分离

保留既有 CPU 来源资格、权重摘要、类别顺序、历史收据和冻结引用。新增 CUDA FP32 执行资格，不把物理 GPU UUID 或逻辑 ordinal 写进不可变训练身份；物理卡属于实例资源绑定。

新 GPU 部署必须重新安装、试用并人工发布。试用后运行时漂移、原地改变已就绪部署的资格、把缺少 runtime 的旧引用默认为 GPU，均须拒绝。预训练资产的来源版本与训练回流版本分别验证，不能因为同属 YOLOv9 就共享宽松加载条件。

旧 LibreYOLO 部署先停止新引用，再处理冻结执行和重试依赖，最终以明确退役状态保留历史。混合服务实例中的 Ultralytics 不随之整体停用。迁移完成后移除旧服务中的 LibreYOLO 执行分支，不保留永久代理或第二份 loader。

## Consequences

正向：

- 外部作者只承担模型逻辑，可从真实模板完成检测与打包，不必复制平台内部服务。
- 安装、项目启用、训练发布和设备执行有独立且可审计的权威边界；复用现有账本，避免插件市场成为第二个平台。
- 共享生命周期保持一个实现，包含构建中对象、借用、取消、CUDA 同步及所有模型池，降低“HTTP 已取消但 GPU 仍执行”的错误释放风险。
- CPU 历史身份不变，GPU 资格需要真实设备证据而非依赖包名称。

负向：

- 运行时、开发包与插件需要独立可分发的依赖和制品；源码可运行不能替代干净外部环境的验收。
- 固定实例、资源与运行时资格意味着升级不能偷偷替换训练部署；管理员需要明确完成重新试用和发布。
- 安全卸载需要同时核验 Learning／Jobs 依赖和 Inference 排空，不是一个删除 Registry 行的操作。

## Alternatives Considered

- **只保留复制模板：** 无法避免重复 GPU 状态机与安全边界，新增插件很快与内置实现分叉。
- **统一 `MLBackendBase` 并迁移全部后端：** 扩大任务范围；交互式、视频与检测差异无法由当前切片证明应当统一。
- **API 内导入插件或执行安装 hook：** 第三方代码获得核心进程或宿主机权限，破坏隔离与可审计部署边界。
- **第二套插件 Registry／发布表：** 重复已有 owner，产生路由、授权与历史外键不一致。

## Notes

本记录处于实施验收中，尚不宣告 ADR-0038 已被正式替代，也不退役旧后端解耦计划。最终状态取决于独立分发、真实 GPU 训练回流、生命周期和产品操作验收；未触及模块的部署目标继续由原台账管理。
