# 0186 — 模块化单体部署、语言无关契约与按需拆出

- **Status:** Proposed
- **Date:** 2026-11-23
- **Deciders:** 项目维护者确认方向，代理记录
- **Supersedes:** —（替代归档计划 `docs/plans/archive/1792160873_backend-module-decoupling.md` 中“每个模块独立构建、部署并完成语言替换”的总目标）

## Context

原后端解耦计划要求所有逻辑模块独立构建、部署，并通过语言无关协议完成实现语言替换。执行中，单一写入 owner、固定 PostgreSQL 函数能力、JSON Schema 和 Node 一致性检查等契约工作取得了实际成果；同时，Workspace、Labeling、Identity、Jobs、Inference、Assets 等模块被拆成多个按操作划分的独立服务，仓库累积了 44 个 compose 文件、约 59 个服务。

维护者在 2026-11-23 澄清：目标是**后端设计解耦**，使将来能把选定模块换成性能更好的语言；**不是**让每个模块默认独立部署。自托管用户的部署成本是插件化和易用性的直接障碍；值得换语言的部分通常是计算热点（媒体、Mask、点云、导出），而不是以数据库为瓶颈的业务模块。

| 选项                                | 主要卖点                               | 主要劣势                                                 |
| ----------------------------------- | -------------------------------------- | -------------------------------------------------------- |
| **模块化单体 + 可拆出边界（选用）** | 部署简单；契约与权限边界保留；按需拆出 | 需要把已拆出的服务合并回默认档，并维护“可拆出”条件       |
| 所有模块默认独立部署（原目标）      | 拆分和换语言的前提已经就位             | 部署与运维成本高；大多数拆分没有资源、安全或扩缩上的理由 |
| 放弃语言无关契约，回到普通单体      | 短期改动最少                           | 丢失已验收的边界，未来换语言或插件化需要重做             |

## Decision

1. **契约是模块边界，进程不是。** 模块之间只通过固定 PostgreSQL 函数能力、JSON Schema 和 HTTP 协议交互，同一进程内也调用同一 owner 能力。普通运行账号只持有 owner 函数的 EXECUTE，不直接读写其他模块的私表，权限边界不依赖进程拓扑。
2. **边界必须可拆出。** 公开操作可 wire 序列化，不携带 ORM、`AsyncSession`、`Request` 或异常类型；跨边界无私表读写；同事务需求由 owner 固定 SQL 能力承担并标明拆出时需另定协调；有不依赖 Python 实现的一致性检查；凭据和外部状态归属明确。
3. **按需拆出。** 只有资源隔离（GPU、FFmpeg、大内存）、安全隔离（第三方代码、独立凭据）、经实测的独立扩缩，或实际选定的语言替换，才构成独立进程的理由。没有理由的按操作拆分合并回默认部署。
4. **两个部署档位。** all-in-one 为默认档；split 只为有理由的服务提供 opt-in overlay。两档运行同一套代码和契约。
5. **语言替换暂缓。** 保留契约和一致性检查；[ADR-0090](0090-module-languages-and-audit-summary-process.md) 的 Go 月报维持实验状态。实际替换某个模块时，仍按“契约冻结 → 第二实现 → 明确切换 → 删除旧实现”执行。

实施与逐项去向见 `docs/plans/1795366269_platform-pluginization.md`。

## Consequences

正向：

- 自托管默认部署回到少量进程，降低安装、升级和排障成本。
- 已验收的单一 owner、固定函数能力和最小权限边界全部保留，未来换语言或拆出时不必重做。
- 插件化可以按扩展点推进，不再以全模块独立部署为前置条件。

负向：

- 需要逐个盘点并合并已拆出的服务，退役对应 overlay、CI 选择器和文档，并单独迁移维护者的本机日常拓扑。
- 进程内调用失去了进程隔离带来的故障隔离，故障边界依赖契约和权限检查而不是进程。
- “可拆出”条件需要持续由一致性检查守护，否则边界会在单体中逐渐退化。

## Alternatives Considered

**所有模块默认独立部署**：多数拆分没有资源、安全或扩缩上的实测理由，而部署成本由每个自托管用户承担，与插件化降低使用门槛的目标冲突。

**回到普通单体**：会放弃已经验收的数据归属与最小权限边界，使未来的语言替换和扩展点重新依赖内部 ORM。
